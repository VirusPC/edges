# README 尚未充分表达的设计思想

这份材料为 [Edges README 优化项目](INDEX.md)提供文案依据：从仓库内的架构决策、项目记忆、Skill、实现和测试中，提取首页尚未充分解释的重要设计理由。它是研究与候选表达，不是已确认的 README 改稿。

核对日期：2026-11-02。代码基线：`main@7c7bcdd`；研究分支已合入这一基线。下文的“已实现”指该版本可由代码或测试支持的机制；“协议”指需要 Agent 或外部平台遵循的工作约定；“实验”不代表已证明产品收益。来源链接使用仓库内相对路径，行号仅供本次核对定位。

## 先说发现

[当前根 README](../../../README.md)已经讲到目录作用域、递归 harness、普通文件、跨 Agent 接续，以及观测和评测。主要缺口不是少列了几个功能，而是很多有价值的**约束、取舍和设计理由**藏在其他文件里：为什么递归不会无限扩大读取范围，为什么引用不等于归属，为什么一次执行成功不等于目标完成，为什么开放文件仍需要受控写入。

这些理由比增加一张功能清单更能解释 Edges 的设计。以下是综合多个来源后得到的归纳，不是仓库已经发布的一套官方原则。

## 1. 上下文分成“必须先知道”与“值得再去找”两层

**设计与价值。** 有些规则一旦没读到就可能做错，例如公开仓不能写入凭据；这类约束直接进入 `AGENTS.md`。其他材料先提供地址和用途描述，由 Agent 根据当前问题选择正文。描述因此承担检索路由的职责，需要让读者判断“什么时候该读这份材料”。这同时照顾了关键规则的可见性和背景材料的按需消费。

还有一层减少漂移的取舍：本层材料只在 `.edges/README.md` 登记，`AGENTS.md` 指向它，不再维护两份相同清单。

**README 缺口。** Memory 与设计依据已说明先读索引，但没有讲透为什么硬约束不能藏在一次可选检索后面，以及为什么索引应只有一个维护位置。

**证据与边界。** [Memory 协议](../../../packages/skills/edges/references/memory/references/PROTOCOL.md)第 35–43 行规定硬约束直接可见、按描述选择材料；[ADR 0035](../../../docs/adr/0035-harness-readme-as-layer-material-index.md)解释集中索引并否决双写；[本仓 AGENTS](../../../AGENTS.md)与[材料索引](../../README.md)给出实际形态。这是内容组织和使用协议，仍以宿主加载入口、Agent 遵守约定为前提，不能称为程序化强制执行。旧材料的“固定两跳”不宜沿用。

**候选表达：** 必须遵守的规则直接可见，其余材料按用途描述检索；让 Agent 先知道边界，再为当前问题补充背景。

## 2. 递归的是维护能力，默认读取却有停止条件

**设计与价值。** 一个 Skill 可以拥有自己的反馈、任务和改进材料；但使用这个 Skill，不需要自动进入它的维护系统。使用方法与维护方法是两种工作。递归结构提供持续改进的空间，读取边界防止每次使用都展开“维护材料的维护材料”。

例如，执行调研需要调研 Skill 的方法正文；修改调研方法时，才需要进一步读取它积累的纠正与设计讨论。这里的边界取决于维护关系，而不只是目录深度。

**README 缺口。** 已说明 Skill 或 harness 也可以有 harness，却没有解释这种递归为何不会默认变成无限扩大上下文。

**证据与边界。** [作用域与 harness 决策](../../../.edges/memory/projects/project_scoped_systems_and_harness/INDEX.md)第 31–37 行明确不自动进入下一层维护系统；[ADR 0024](../../../docs/adr/0024-scope-first-content-ownership.md)把组成与 harness 分开；[遍历实现](../../../packages/cli/src/domain/operations/traverse.ts)第 84–90 行只有在 `includeHarness` 为真时跟随 harness，默认仍遍历登记的组成 children。关系模型和遍历边界已实现；不能据此宣称自动复盘、自动采纳或无人监督的递归优化已完成。

**候选表达：** 每份方法都可以积累自己的改进材料；使用它时读取方法，维护它时再进入它的维护上下文。

## 3. 归属、发现和维护是三种关系，目录承载内容的完整生命周期

**设计与价值。** 物理目录回答内容归谁；索引引用回答从哪里能找到它；harness 回答维护它时需要什么。内容被更多入口引用，不会因此多出几个所有者。局部材料可以在根入口被发现，而不必搬到根部保存。

这也解释了为什么采用“入口 Markdown + 同目录附件 + 可选维护材料”：一条简单笔记以后可以长出截图、证据、脚本，不必反复从单文件改造成另一种对象。移动内容时应带上属于它的资源；删除一个引用方，不应顺带删除被引用原文。目录约定因此影响生命周期，而不只是文件排版。

**README 缺口。** 已讲局部归属、引用和附件同目录，但尚未把三种关系与移动、删除、内容成长连起来解释。

**证据与边界。** [ADR 0024](../../../docs/adr/0024-scope-first-content-ownership.md)第 29–41 行解释唯一 parent、独立 harness 和目录生命周期；[目录资源单元决策](../../../.edges/memory/projects/project_node_resource_unit_decision/INDEX.md)说明避免反复转换内容形态的动机；[节点缓存](../../../packages/cli/src/services/node/node-cache.ts)分别计算物理 parent 与 harness；[生命周期测试](../../../packages/cli/test/services/directory-lifecycle.test.ts)验证移动资源和维护材料、删除引用方保留被引 Skill。这里是底层能力，不代表各模块 CLI 都已提供全部 move/import 命令；普通附件也不因此成为领域节点。引用不传播写权限和全部来源约束，见 [Memory 协议](../../../packages/skills/edges/references/memory/references/PROTOCOL.md)第 74 行；这部分语义仍需 Agent 遵守。

**候选表达：** 一份内容可以从多处被发现，仍在自己的目录中维护；正文、附件和维护材料共同成长，引用不会改变原文归属。

## 4. 接入是有选择的登记，不要求先把整个仓库变成同一种系统

**设计与价值。** 文件存在、正文里出现一个链接，不意味着它自动进入组成图。重要目录可以先建立维护入口，其他目录继续保留原样；截图、历史稿、脚本也无需全部建模。团队可以从最需要的一个局部接入，然后随实际维护需要扩展。

这是一种渐进采用方式：工具尊重已有文件组织，登记关系表达“哪些内容参与当前组织”，而不是要求把所有磁盘内容重新分类。

**README 缺口。** “按需拥有 harness”已有表述，但没有明确文件存在与纳入组成图之间的区别，也没有展开这种选择如何降低接入成本。

**证据与边界。** [CONTEXT 的内容模型](../../../CONTEXT.md)开头区分组成登记、普通链接和资源；[选择维护目录的反馈](../../../.edges/memory/feedbacks/feedback_harness_markers_not_task_project_indexes/INDEX.md)要求按重点目录建立维护入口；[遍历实现](../../../packages/cli/src/domain/operations/traverse.ts)按登记 children 遍历。系统根发现仍会扫描目录，因此不能写成“从不扫盘”，也不能把登记关系当成限制 Agent 读文件的安全沙箱。

**候选表达：** 从需要长期维护的目录开始登记，保留已有组织；其他文件不必为了接入而全部改造成节点。

## 5. 记忆优先保存无法轻易重建的判断依据

**设计与价值。** 代码与 Git 能回答的事实，复制进记忆后容易过期；真正值得保留的是为什么这么选、什么时候适用、用户纠正了什么、哪些意图已被确认。以后遇到相似但不完全相同的问题，理由能帮助重新判断，孤立结论则容易被机械照搬。

这意味着“更多记忆”不是天然更好。长期记忆需要筛选，临时工作日志、通用常识与可直接恢复的实现事实各有其他位置。可重复执行的方法还应进入 Skill，使判断与操作流程各自保持合适的形态。

**README 缺口。** 已提到 Edge 包含判断、理由和适用边界，但没有充分解释主动不存什么，以及这种克制怎样减少陈旧背景。

**证据与边界。** [edges-memory-remember](../../../packages/skills/edges-memory-remember/SKILL.md)第 15–36 行规定写入门槛、排除可从代码或历史恢复的事实，并要求记录理由；[edges-memory-ask](../../../packages/skills/edges-memory-ask/SKILL.md)按描述按需检索。这是 Agent 执行的记忆维护策略，尚不能宣传为自动识别重复、自动发现过期内容或自动清理的产品能力。

**候选表达：** 留下以后难以重建的判断、理由和纠正，让下一次工作能重新理解取舍，而不只继承一个结论。

## 6. Task 保存目标，Run 保存尝试；任务可以逐步变清楚

**设计与价值。** 一次执行失败，目标仍可能值得继续；一次工具执行成功，也不等于目标已经达到。将 Task 与 Run 的状态分开，才能在重试、更换 Agent、跨会话接续时保留稳定目标和尝试历史，避免执行日志淹没任务背景。

同样的克制体现在任务捕获：背景与目标必须有依据，动作和完成标准允许以后补齐。先保存可信的意图，再逐步明确方案，比要求 Agent 立即填满所有栏目更适合尚在形成的想法。事实、假设和已确定做法要分开。

**README 缺口。** Tasks 已写 Task/Run 与逐步澄清，但没有充分解释状态为什么独立，以及为什么允许未定事项保持未定。

**证据与边界。** [Task 组织说明](../../../.edges/tasks/README.md)明确 Task 状态不从 Run 状态直接推导；[状态类型](../../../packages/cli/src/domain/models/tasks/types.ts)分别定义两套状态；[CONTEXT](../../../CONTEXT.md)的 Run 约定使用稳定 `run-id` 与独立追加记录；[delete 命令](../../../packages/cli/src/commands/tasks/delete.ts)拒绝删除并提示改为 cancelled；[对话转任务 Skill](../../../packages/skills/edges-conversation-to-tasks/SKILL.md)第 19–31 行规定必填门槛和事实区分。模型与查询已存在，Run CLI 为只读；自然语言内容质量依赖 Skill，不能宣传为已有自动调度器或自动验收系统。

**候选表达：** 保存稳定的目标，记录每一次尝试；让尚未确定的方案继续澄清，让执行结果成为判断目标是否完成的证据。

## 7. 人的审阅有可执行的交接格式

**设计与价值。** Agent 提出分类建议，审阅页展示并允许人调整，确认结果再由 CLI 应用。人不必逐条描述文件操作，界面也不必另写一套修改仓库的业务逻辑。结构化结果把“看过了”变成明确的操作输入，使建议、采纳与写入的边界可检查。

这里值得讲的是决策过程，而不只是生成 HTML 的能力。人可以在合适的界面集中审阅，Agent 根据采纳结果继续完成具体工作。

**README 缺口。** Artifacts 已讲预览、发布和写回分步，但没有解释这种拆分怎样连接人的判断与工具执行。

**证据与边界。** [任务分类 Skill](../../../packages/skills/edges-tasks-classify/SKILL.md)规定 Agent 判断、页面只渲染，收到导出的 JSON 后再校验并通过 CLI 应用，`keep` 不写盘；[review-page 命令](../../../packages/cli/src/commands/tasks/project/review-page.ts)只读取输入、渲染、返回路径。此流程已存在，但结果仍需复制回聊天，并非自动回传；也不能从这一具体工作流推导出所有操作都必须额外审批。

**候选表达：** Agent 整理建议，人集中调整和确认，再由工具按确认结果执行；审阅结果本身就是可继续工作的输入。

## 8. 多个 Agent 入口，共享一套执行规则

**设计与价值。** Skill 讲何时做、怎样做；CLI 承担可检查的操作；无 shell 的宿主可以通过 MCP 复用 CLI。接入更多宿主时，尽量不再维护一套内容写入逻辑，路径、正文、返回值和错误规则也更容易保持一致。

例如，同一条 Note 从编码环境和聊天环境写入，入口不同，但应落到相同的内容服务。这是跨 Agent 接续背后的实现约束，而不只是宣称支持更多客户端。

**README 缺口。** 已有 CLI、Skill、MCP 职责说明，但没有展开复用同一执行契约对避免分叉的价值。

**证据与边界。** [ADR 0004](../../../docs/adr/0004-capability-surface-cli-skill-mcp.md)提出三种能力面；[new-note 的 CLI adapter](../../../packages/mcp-servers/new-note/src/cliAdapter.ts)实际调用 `notes create` 并解析 JSON；[命令层结构测试](../../../packages/cli/test/commands/notes-skills-crud-nodeservice.test.ts)检查命令不保留直接文件写入等旁路。现有 MCP 不是所有 CLI 命令的完整镜像，ADR 中其他历史实现安排也不能直接当作现状。

**候选表达：** 换 Agent 时，变化的是调用入口；内容的校验和落盘规则尽量由同一套实现维护。

## 9. 普通文件的开放性，与保护并行修改可以同时成立

**设计与价值。** 人和 Agent 可以直接阅读 Markdown，但常用变更仍需要统一维护正文、索引与生命周期。创建内容时补齐登记、删除内容时清理相关登记，不应交给每个调用方分别记住。

组织入口的自动维护还通过标记区块划定编辑边界，保留区块之外的手写内容，见 [Memory 协议](../../../packages/skills/edges/references/memory/references/PROTOCOL.md)第 43 行。这样一份文件可以同时容纳人的说明和工具维护的索引；这不是对任意正文更新或 YAML 格式完全保真的保证。

写入还要面对现实中的并行编辑：工具在一次操作中读取文件后，外部编辑器可能在保存前改动它。当前服务在写前核对原文和文件身份，协作锁减少同工作树命令互撞，单文件采用原子替换。Git 的历史提供事后追溯，这些机制则帮助发现同次操作中读取之后发生的外部修改。

**README 缺口。** 已说明文件可读、Git 可追溯，但几乎没有解释如何减少索引失配和旧内容覆盖新修改的问题。

**证据与边界。** [ADR 0030](../../../docs/adr/0030-content-leaf-crud-via-nodeservice.md)规定内容 CRUD 经统一服务；[NodeService](../../../packages/cli/src/services/node/node-service.ts)组织叶子与登记的保存计划；[文件写入实现](../../../packages/cli/src/services/node/node-files.ts)核对身份与原文、执行单文件替换并处理恢复；[锁实现](../../../packages/cli/src/services/node/node-lock.ts)与[并发身份测试](../../../packages/cli/test/services/node-files-atomic.test.ts)支持这一机制。快照不跨 CLI 命令保留：Agent 若基于更早一次读取生成陈旧正文，后续 update 会重新加载文件，无法据此识别正文的语义过期。保护作用于经过服务的操作，不拦截外部编辑器；多文件变更可尝试恢复，**不是多文件原子事务**，恢复也可能不完整。外部编辑文件不会自动刷新所有索引。

**候选表达：** 保留普通文件的开放性，也为常用修改维护内容与索引的一致；保存前核对本次操作读取的状态，发现期间发生的外部修改就停止写入。

## 10. 让结构问题显露出来，使修复成为明确动作

**设计与价值。** 已存在的内容缺少必要文件时，如果读取或更新悄悄补出一个，用户会误以为原有数据完整。将缺失、损坏和迁移需要显露出来，才能审阅修复的影响，并保留问题来源。为本次创建建立必需组织结构，则是另一种已明确请求的操作。

这体现出工具承担多少隐式工作的取舍：可以代办明确操作所需的维护，但不应以“成功”掩盖无法读取或损坏的既有状态。

**README 缺口。** 这个倾向分散在反馈、CLI 规则和 ADR 中，首页尚未表达它与可审阅、可信结果之间的关系。

**证据与边界。** [必要文件缺失时失败的反馈](../../../.edges/memory/feedbacks/feedback_cli_fail_on_missing_required_files/INDEX.md)解释理由和例外；[dated-leaf 服务](../../../packages/cli/src/services/node/dated-leaf.ts)区分叶子缺失报错与创建时建立组织清单；[ADR 0043](../../../docs/adr/0043-compose-readme-entry.md)为旧登记迁移提供默认预览、显式应用的安排。这是设计倾向，尚非所有命令的统一保证：Task Project list 会跳过坏条目，Compose 部分命令会确保材料入口存在。

**候选表达：** 让缺失与损坏可见，让修复与迁移可审阅；工具的成功应能对应到确实完成的变更。

## 11. Compose 共享来源，同时保留版本、归属和展开边界

**设计与价值。** 共享材料保留在原来的 Git 仓库，主仓用 submodule 记录版本，相关路径随仓迁移；本地形成的新认识可以写回来源，再由原生 Git 决定何时提交与推送。复用、文件修改与发布各自可见。

另一个容易遗漏的取舍是只展开当前仓直接登记的组合，不继续自动展开对方的 Compose。这让接入一个仓库的含义更明确，避免间接依赖持续扩大工作上下文。

**README 缺口。** Compose 已有 submodule、写回和各自历史的说明，但没有充分连接版本复现、路径迁移和有限展开的用户价值。

**证据与边界。** [ADR 0042](../../../docs/adr/0042-compose-on-git-submodule.md)解释采用 Git submodule；入口位置以后续 [ADR 0043](../../../docs/adr/0043-compose-readme-entry.md)为准；[ADR 0045](../../../docs/adr/0045-compose-checkout-writable.md)明确可写且提交推送交 Git；[森林实现](../../../packages/cli/src/services/node/system-forest-service.ts)限制嵌套 Compose 展开；[Compose 测试](../../../packages/cli/test/commands/compose.test.ts)和[写回测试](../../../packages/cli/test/commands/compose-write.test.ts)验证展开与写入边界。Compose 不提供隔离沙箱或权限系统；不递归展开不等于只读，也不等于自动同步或自动发布。

**候选表达：** 把共享积累带入当前工作，同时保留它的来源、版本和维护位置；复用到哪里、改了什么、何时发布，都可以检查。

## 12. Routine 引用持续维护的方法，并要求一次运行使用一致版本

**设计与价值。** 如果每个平台都保存一份完整提示词，方法改进后容易留下多个副本。Routine 记录执行定义并引用 Skill，平台保存来源和读取约定；运行时读取方法，需要复现时固定版本。

协议还要求将分支解析为本次 commit，并从同一个 commit 读取 Routine 与 Skill。这样一次运行不会混用更新前后的定义；读取失败则停止，避免静默退回陈旧规则。

**README 缺口。** 已提平台触发、每次读取和版本固定，但没有解释防止平台副本漂移与单次运行版本一致的理由。

**证据与边界。** [Routine 使用协议](../../../packages/skills/edges/references/routines.md)第 46–49 行规定同一 commit、读取失败停止与平台提示词的职责，第 59 行区分仓库记录、平台配置和实际运行验证；[例程实践决策](../../../.edges/memory/projects/project_routines_from_brain_practice/INDEX.md)说明避免日程与方法两边维护的动机。定义 CRUD 与协议已存在，实际执行依赖平台遵循约定；Edges 本身不提供内置调度器或平台配置自动同步。

**候选表达：** 平台负责触发，仓库持续维护方法；每次运行读取明确版本，使方法更新与执行来源可以追溯。

## 13. 观察到的反馈，经过判断和采纳后才成为新规则

**设计与价值。** 某次失败或一次纠正首先是新输入，需要识别事实、适用范围和可能原因，再决定是否形成记忆、方法或任务。直接把观察升级为长期规则，可能把偶发现象固化。日志数量增加，也不代表下一次工作会更好。

因此反馈应回到捕获与判断环节，再经过验证和采纳。观测记录发生了什么，评测检验改变是否有效，记忆与 Skill 保存被采纳的判断和方法。各部分有不同的可信程度和用途。

**README 缺口。** 已画出观测、评测和改进闭环，但尚未充分说明为什么反馈不能跳过判断直接沉淀，以及“有记录”与“有改进”的距离。

**证据与边界。** [反馈回到捕获的纠正](../../../.edges/memory/feedbacks/feedback_knowledge_loop_returns_to_capture/INDEX.md)明确这条边；[Observation 约束](../../../packages/observation/AGENTS.md)区分观测现象、已采纳决策与可复现评测；[CONTEXT](../../../CONTEXT.md)第 329–338 行对受控改进要求验证与采纳。[线上数据自动清洗与定期评测任务](../../../.edges/tasks/evaluation/backlog/2026-11-02--Personal-Evaluation自定义目标线上数据自动清洗与定期评测/INDEX.md)仍在 backlog，因此这里是模块分工和工作方法，不能写成通用自动闭环已完成。

**候选表达：** 反馈成为新的输入，经过判断、验证和采纳，再进入下一轮的方法与记忆；改进要能说明依据和效果。

## 14. Harness 需要证明净收益，也要允许实验否定自身设计

**设计与价值。** 要评价文件型记忆，应该让真实 Agent 自己找到并使用目录材料。把全文提前塞进提示词后答得更好，不能直接证明索引检索与维护机制有效。测试链路跑通，也只是具备继续测量的条件。

更完整的标准还包括成本和副作用：质量是否提升，token 与时间是否可接受，无关任务是否退化。一次可信的负结果可以帮助删掉无效复杂度，所以实验完成不应以得到正向结果为条件。

**README 缺口。** 已有固定条件、质量、成本和约束命中的对照说明，但尚未鲜明表达真实消费方式、无关任务不退化，以及允许否定当前方案的立场。

**证据与边界。** [文件记忆消融实验](../../../packages/evaluation/experiments/harness_memory_ablation/README.md)要求 Agent 自读目录而非全文注入，同时说明目前只是评测冒烟；[判分实现](../../../packages/evaluation/experiments/harness_memory_ablation/score.py)要求相关 gate 均通过才判断值得默认开启；[ADR 0008](../../../docs/adr/0008-evaluation-smoke-is-not-benchmark-proof.md)解释评测链路与有效性证明的区别；[核心价值实验任务](../../../.edges/tasks/evaluation/backlog/2026-10-27--完成-Edges-核心价值实验并整理结果报告/INDEX.md)明确不以正向结果为完成条件。已有实验与判分工具，正式收益报告仍待完成；`conflict-stale` 当前只报告，尚非硬门槛，不能写成已经证实收益或全面覆盖退化风险。

**候选表达：** 用真实工作方式检验 harness：既看质量，也看成本与对其他任务的影响；结果可以支持保留，也可以支持删减。

## 怎样转成 README 修改

建议先做一轮小幅补写，再判断是否需要独立设计文档，不把研究报告直接搬进首页。

1. **前部价值表达：** 从第 1、2、3、5 点选出少量能说明使用体验的句子，连接现有目录与递归配图。保留用户能理解的场景，具体模型、字段与测试留在来源文档。
2. **“设计依据与使用边界”：** 补第 9 点的开放文件与写入保护，以及第 3 点的发现和归属区别；第 10 点作为修复边界的简短补充。不要把它们扩写成安全或事务保证。
3. **模块折叠说明：** Tasks 补目标与尝试独立，Artifacts 补结构化审阅交接，Compose 和 Routine 补版本与维护来源，Evaluation 补真实消费和允许负结果。
4. **导航而非复制：** 较长的理由链接 ADR、CONTEXT 或模块文档；已过时的来源先核对修正，再作为现行操作指南推广。候选句只提供编辑起点，尚未获得逐句采纳。
