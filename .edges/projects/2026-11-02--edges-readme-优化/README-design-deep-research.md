# Edges 深层设计研究：设计演化、责任边界与尚未兑现的承诺

本稿接续[首轮 14 个设计点](README-design-findings.md)，为 [README 优化项目](INDEX.md)进一步回答：这些选择为什么反复出现，曾经否决什么，彼此怎样配合，又把哪些工作留给了维护者和 Agent。

研究日期：2026-11-02。实现基线为 `main@7c7bcdd`，研究分支已合入该基线。方法是交叉核对当前代码、现有测试、ADR、公开项目记忆与 Git 历史。本轮未运行端到端工作实验、故障注入或收益评测；文中“测试覆盖”指已检查仓库中的测试断言。文末的验证方案均未执行。

**下文六条主线是研究归纳，不是仓库已经命名的官方原则，也不构成独创性或效果优于其他系统的主张。** 历史决定与当前实现分别标注；拆仓前的过程主要由归档文档支持，不能把框架仓的初始导入提交当作思想产生的时间。

## 研究结论：重要的设计藏在“什么不应被自动等同”里面

仓库反复处理几类容易混淆的关系：共享实现不意味着集中所有经验；能发现材料不意味着拥有它；内容已保存不意味着结论已验证；人审过不意味着适用于最新状态；有观测记录不意味着已证明收益。

因此，值得讲清的共同设计可以概括为：**把经验放在明确的维护对象旁，保留重新判断它的依据，并对使用、修改和采纳分别交代边界。** 目录、索引、CLI、审阅和评测各解决其中的一部分。

| 深层主线 | 跨模块证据 | 它避免的混淆 | 付出的主要代价 |
| --- | --- | --- | --- |
| 先确定维护对象，再组织上下文 | 局部记忆归属、递归 harness、scope/super | 内容类型或目录深度自动决定用途 | 语义归属仍需判断；路径承担更多契约 |
| 减少平行维护的规则，比统一外表更重要 | 删除第二次扫描、统一模块入口、Schema 生成 | 抽出 helper 就等于消除重复 | 迁移、构建与分发成本可能增加 |
| 不同的“成功”需要不同证据 | Note、Edge、Task/Run、评测受理与判分 | 文件存在、执行结束、效果成立是一回事 | 状态更多，消费方要解释其含义 |
| 提炼仍保留返回原材料的路 | 笔记取舍、来源引用、记忆理由、历史更正 | 更短的总结必然更有用 | 材料更长，来源与现行结论都要维护 |
| 工具边界清楚，外部责任也必须可见 | Git、NodeService、审阅页、Routine | 开放接入等于端到端自动受控 | 跨命令、跨平台交接仍可能出错 |
| 评测本身也必须接受证据约束 | 缺失值、遥测分离、真实 worktree 对照 | 有分数或报告就足以证明收益 | 条件控制、样本质量和采纳仍需工作 |

## 一、维护对象是组织的起点，类型与目录只是表达手段

### 从一次真实翻案理解它

早期设计曾以“独立目标、决策和验证责任”判断一个目录有没有资格成为节点。结果，一些模块的局部记忆被上收到根层。用户否决了这个门槛：一个对象可以是上层工作的组成，同时拥有自己的维护空间。纠正记录写明，随后将 43 条公开记忆恢复原归属。

这里的价值不只是“支持子目录”。它保护的是：**共享工具由根层维护，局部经验仍跟着它服务的对象走。** 将实现集中与将上下文集中分开，才能让通用能力服务多个模块，而不抹掉它们各自的条件和历史。[归属纠正记忆](../../../.edges/memory/projects/project_scope_first_content_ownership/INDEX.md)、[纠正计划](../../../docs/superpowers/plans/2026-10-05-recursive-node-ownership-correction.md)、[ADR 0024](../../../docs/adr/0024-scope-first-content-ownership.md)支持这条历史链。数量来自计划和记忆记录，本轮没有重放拆仓前的迁移。

### 递归的意义是可以重新选择维护对象

使用一套调研 Skill 时，它为调研工作提供方法；改进这套 Skill 时，Skill 自己成为工作对象，它的反馈、任务和试验才进入当前维护上下文。系统一／系统二是相对角色，不是两类永久文件。增加一层目录只提供表达空间；只有改进实际进入下一轮工作，才谈得上改进能力的递归使用。[作用域与 harness 决策](../../../.edges/memory/projects/project_scoped_systems_and_harness/INDEX.md)、[CONTEXT](../../../CONTEXT.md)中的相对角色定义和[遍历实现](../../../packages/cli/src/domain/operations/traverse.ts)共同支持这一解释。

这也解释默认读取的停止条件：组成可以继续展开，但不会自动进入组成对象自己的 harness。维护关系、发现关系和物理归属各有含义，不能用一个“多层目录树”统统代替。

### 简单参数并没有消灭布局成本

`scope`、`super`、`all` 试图用少数选择表达主体、视角和查询范围，避免再保存 purpose、index-group 等另一套用途分类。2026-11-02 的 notes/projects 修正就是具体例子：默认直写 scope 根的模块特例，曾迫使调用者把 scope 改成 `.edges`，把“维护哪个对象”混成“文件往哪放”。[范围约定](../../../.edges/memory/feedbacks/feedback_scope_super_all/INDEX.md)与[ADR 0046](../../../docs/adr/0046-content-face-org-list.md)记录了修正及拒绝默认双读新旧目录的理由。

**代价与反证。** 语义的一部分进入了路径，因此自定义路径会影响类型识别、查询、父索引和生命周期，而不只是创建文件的位置。当前[材料定位](../../../packages/cli/src/domain/config/edges-materials.ts)把 super 材料放在 scope 直属目录，但 [Super 查询根](../../../packages/cli/src/services/node/super-root.ts)优先读取 `.edges/README.md`；[dated-leaf 查询](../../../packages/cli/src/services/node/dated-leaf.ts)因此仍显式补查 super 的根模块。这是当前确实存在的两种策略，不直接等同于新发现的 bug，却足以反驳“使用了相同参数名，所有消费者就已完全一致”。[高优路径任务](../../../.edges/tasks/edges-extensions/backlog/2026-11-02--统一各模块路径规则默认受控并保留显式兜底/INDEX.md)仍未完成。

**README 应讲到的深度：** 经验贴近对象保存，换一个维护问题可以进入对应上下文；不要承诺目录结构能自动判断全部适用范围，也不要将任意路径能力写成既有统一契约。

## 二、真正的减法，是减少同一规则需要维护的份数

### 最近的目录修正提供了一次可见的小实验

notes/projects 统一路径后，如果原查询和新增的组织清单扫描同时存在，排除规则、Compose 展开边界、scope 限制就必须在两条路径中分别正确。只是抽一个辅助函数，还不能消除两条路径之间的偏差。

提交 [41c37e8](https://github.com/VirusPC/edges/commit/41c37e8f8ee647140cb3c565027a8a9077c5bee9)删除重复的默认扫描，让默认查询复用登记树，`--all` 复用森林；不同视角需要的 super 查询仍保留。该提交总计新增 28 行、删除 42 行，但更重要的是减少了一条需要独立保持正确的发现路径。[当前查询](../../../packages/cli/src/services/node/dated-leaf.ts)和[范围回归测试](../../../packages/cli/test/commands/dated-leaf-scope.test.ts)展示了被保留的边界。

由此可以提出一个比“代码越少越好”更精确的评判标准：**加入或修改一条规则后，需要同步修改多少处独立判断？** 这是研究判断，仓库尚未用量化数据证明它减少了维护成本。

### 统一入口，也不等于所有业务都变成一种对象

Compose 从特殊区块与虚拟节点，改为普通模块 README 的特化；Task 也不再为索引保留另一套正常运行格式。目标是让统一遍历、筛选和生命周期能够工作，专属业务仍由各自的节点和服务解释。[ADR 0043](../../../docs/adr/0043-compose-readme-entry.md)与[职责简化记忆](../../../.edges/memory/projects/project_node_shared_state_simplification/INDEX.md)说明了这项取舍。

**反证：形状一致尚不等于完整插件机制。** 当前仍有[README 特化表](../../../packages/cli/src/domain/models/readme/specialize.ts)、[材料路径表](../../../packages/cli/src/domain/config/edges-materials.json)、[排除模块枚举](../../../packages/cli/src/domain/config/exclude.ts)和[类型识别规则](../../../packages/cli/src/domain/config/layout.ts)。新模块还涉及多个契约点。[模块插件化任务](../../../.edges/tasks/edges-extensions/backlog/2026-10-21--harness-模块插件化/INDEX.md)仍在 backlog。共同入口提供收敛条件，不能写成只登记一次就可自动加载的扩展系统。

### “单一真源”应按职责理解，而不是要求所有东西只存一份

TaskDoc 以 TS 契约生成 JSON Schema，避免手写两份字段定义；发布包携带生成结果，消费者通过 CLI 读取。与此同时，Markdown 的可选头部、领域校验、完整 JSON 输入分别有不同边界，不能把 API 必填字段直接强加到所有文档上。[ADR 0025](../../../docs/adr/0025-typescript-source-generated-json-schema.md)、[TaskDoc 契约](../../../packages/cli/src/domain/models/tasks/task-doc-contract.ts)和[Schema 契约测试](../../../packages/cli/test/schema/contract.test.ts)记录了这种分工。

生成产物与源定义可以同时存在，只要谁维护、怎样生成、怎样验证明确；正文与索引也可以同时存在，前提是不要各自成为独立维护的内容来源。反过来，把所有材料强行塞成一种正文或 Schema，会丢掉真实职责。

**接受的成本。** Schema 生成增加构建、分发、方言兼容与消费者验收；统一入口增加迁移工作。仓库也主动取消过 YAML 样式与注释完全保真的额外目标，退回 gray-matter 默认行为，保留领域校验。[frontmatter 演化记录](../../../docs/superpowers/plans/2026-10-04-optional-frontmatter.md)与[现行 codec](../../../packages/cli/src/utils/markdown/document.ts)说明：减少复杂度有时来自明确不再支持什么，不能宣传成所有保证都保留而代码自然减少。

**README 应讲到的深度：** 模块共用发现和写入规则，各自保留业务含义；把维护来源与派生表示讲清即可，生成器和类层次放到技术文档。

## 三、身份、执行状态、证据强度与采纳是不同维度

### 仓库在多个位置抵制“前一步成功，后一步就成立”

| 对象或结果 | 它能说明什么 | 它不能单独证明什么 |
| --- | --- | --- |
| Note | 一段材料已被捕获，可继续研究 | 已形成可靠结论 |
| Edge | 形成了可复用、带边界的判断 | 已经过现实验证 |
| Memory | 某种意图、纠正或判断被保存供后续使用 | 它是永远有效的事实或硬约束 |
| Task | 目标有稳定落点，可以继续澄清与推进 | 已有成熟方案或已经达标 |
| Run | 一次执行尝试及其记录 | Task 目标完成 |
| HTTP 202 / `run_ok` | 请求受理／运行链路达到相应状态 | harness 值得默认启用 |
| verdict / `worth_default_on` | 按当前输入和门槛形成了判分结果 | 已获采纳、已部署或适合其他任务 |
| 审阅导出 JSON | 人对这份建议表达了操作选择 | 选择仍基于当前文件版本 |

以上不是同一套已实现状态机，而是对多个现有合同的对照。来源包括 [CONTEXT 的 Note、Edge、Task 与 Run 定义](../../../CONTEXT.md)、[记忆写入门槛](../../../packages/skills/edges-memory-remember/SKILL.md)、[任务目标与循环验收](../../../.edges/memory/projects/project_tasks_align_goal_and_loop_engineering/INDEX.md)、[评测服务结果说明](../../../packages/services/evaluation/README.md)及[判分代码](../../../packages/evaluation/experiments/harness_memory_ablation/score.py)。

### 不强迫捕获时成熟，但进入验收时需要补齐依据

允许 Note 没有结论、Task 暂缺完成标准，不是放弃质量要求。它把“先留下可信的意图”与“具备开始循环验收的条件”分开：动作不能代替完成标准，用户所述与已验证事实不能混写。这样可以降低捕获成本，而不要求 Agent 用想象补齐尚未确定的内容。

更深的价值是保留不确定性。当前消融评测在证据缺失时会产生 `unscored`，而不是强造分数。但 `worth_default_on=false` 本身仍可能代表证据不足，也可能代表没有达到质量、成本或无关任务退化的门槛；消费方还得查看各项 gates、错误记录与判分结果，不能只看总布尔值或答案是否正确。

**代价与反证。** 多种状态增加解释成本，CLI 不会自动理解自然语言里的“假设”“已验证”是否名副其实。这个设计是否减少过早宣布完成、把猜测当事实等错误，还需要真实任务对照；仅仅存在这些字段，不能证明使用者正确区分了它们。

**README 应讲到的深度：** 想法可以先留下，目标继续澄清，尝试与证据分别记录；不要用“已保存”“已执行”替代“已完成”“已证明有效”。

## 四、提炼的目标包括保留未来纠错的可能性

### 为何有时宁可更长，也不只保留结论

笔记 Skill 要求过程保留真实取舍，所学与行动指南再补充适用判断；原材料引用也不能省略。它明确接受更长的笔记，拒绝用一段漂亮总结替换讨论过程。原因是后来遇到新条件时，需要知道当时比较过什么、为什么没选、哪些依据如今不再成立。[取舍不压缩过程的 ADR](../../../packages/skills/edges-create-notes/docs/adr/0008-tradeoffs-supplement-not-compress.md)、[原始材料引用 ADR](../../../packages/skills/edges-create-notes/docs/adr/0010-keep-source-material-refs.md)明确记载了这一决定。

这与“记忆不要复制代码事实”并不矛盾。笔记保留一次认识形成的材料，Memory 保存后来工作仍需调用的判断与理由，Skill 保存可重复执行的方法；它们回答不同问题。减少重复维护，不意味着把过程证据也删掉。

### 历史记录和现行规则需要不同的更新方式

一个具体例子是定稿周复盘：后续评论、更正写到同目录 `COMMENTS.md`，保留当时判断与后来变化。[复盘更正反馈](../../../.edges/memory/feedbacks/feedback_retro_comments_in_separate_file/INDEX.md)说明了适用范围。这不能推广为所有 Memory 都只能追加、不能更新；现行约定仍需要可找到的有效版本。

本次研究本身提供了一个小例子：[首稿](README-design-findings.md)曾将 Compose 的 submodule 版本能力说得过宽。继续查代码后，发现还有本地目录与仓外 clone 路径，因此本轮修正首稿并在深研稿保留修正原因。研究稿的判断可以更新，依据和变化仍应可回看。

### 知识也有持续维护成本，退出活跃上下文是正常操作

[历史架构文档](../../../docs/architecture.md)将无法重新找到、不能影响行动的材料视为持有成本；[CONTEXT 的 Archive 定义](../../../CONTEXT.md)将归档视为退出活跃空间、保留恢复可能的机制。结合当前按需检索和评测清理方向，可以作出一个研究推断：**新增经验与减少无效背景是同一项维护工作。** 没有统一的知识 ROI、自动过期判断或自动归档系统可据此宣称已存在。

**代价与反证。** 过程、指南、现行记忆可能部分重复；原会话链接可能失效；只读旧正文而漏看更正仍可能误用结论。现有目录与引用提供可追溯的机会，不保证来源永久有效，也不是完整事件溯源或自动知识血缘系统。

**README 应讲到的深度：** 保留的不只是答案，还有以后改变答案所需的理由和来源；积累可以被更新、收窄或移出活跃上下文。

## 五、工具少承担一项责任，这项责任并不会自动消失

### Compose：把 Git 工作交回 Git，也放弃了代管整条发布链

[ADR 0039](../../../docs/adr/0039-compose-worktree-and-sync.md)曾设想自动 worktree、`compose sync`、提交推送与 PR 清理；[ADR 0042](../../../docs/adr/0042-compose-on-git-submodule.md)撤回 sync 并采用 submodule；[ADR 0045](../../../docs/adr/0045-compose-checkout-writable.md)又去掉组合仓只读及专门挂载机制。后续实现还删掉了组合仓专用父索引边界和空检出写入检查。

这条历史支持的归纳是：Edges 不再维护一套与 Git 竞争的工作流控制，仓库检出、分支、提交与发布责任交给原生 Git 和调用者。它不能被解释为增加了更强隔离。几个具体边界必须同时说明：

- [Compose 服务](../../../packages/cli/src/services/compose/service.ts)允许无 remote 的本地登记，仓外路径可回退普通 clone。**只有真正纳入主仓 submodule 的路径，才由主仓 gitlink 固定版本。** 相对路径本身不能保证换机恢复。
- [update 结果合同](../../../packages/cli/src/commands/compose/git-result.ts)允许部分成功时退出 0，同时逐项返回 failed。调用方必须检查条目结果，不能把退出码当作全部更新完成。
- add 的代码顺序包含确保材料入口、Git 操作和保存登记；这些跨文件、Git 暂存区的副作用不组成一项统一事务。某一步失败后需要检查已完成部分。

### NodeService：用短生命周期共享状态简化，不承诺长驻协同编辑

[身份简化设计](../../../docs/superpowers/specs/2026-10-06-node-identity-simplification.md)放弃多个可编辑副本的自动合并，改为同一 Service、同一路径共享实例。关联保存会写入本次受影响节点的完整当前状态；无关缓存节点不顺便保存。[节点缓存](../../../packages/cli/src/services/node/node-cache.ts)与[身份测试](../../../packages/cli/test/services/node-identity.test.ts)体现了这个合同。

因此，两个库调用者拿到的不是独立草稿，一个调用者的改动可能随另一个触发的关联保存落盘。CLI 的锁、单文件原子替换、多文件恢复又是三种不同保证；直接调用 NodeService 不等于自动取得 CLI 命令锁。[scope session](../../../packages/cli/src/services/node/scope-session.ts)、[CLI 编排](../../../packages/cli/src/program.ts)、[写锁](../../../packages/cli/src/services/node/node-lock.ts)及[文件保存](../../../packages/cli/src/services/node/node-files.ts)界定了范围。

**这里没有跨命令的编辑会话版本。** 写前核对能发现同次服务操作加载后的部分外部变化，却不能识别 Agent 根据更早一次读取生成的陈旧正文；外部编辑也不受协作锁强制约束。未来若做长驻多人编辑，不能无成本沿用当前前提。

### 审阅和 Routine：协议可移植，但协议不是自动执行保证

审阅页不直接改仓库，确认结果交给 Agent 调 CLI；Routine 不内置调度器，平台读取仓库里的定义与 Skill。这减少了页面与平台各维护一套业务逻辑的需要，却把交接质量变成关键依赖。

[审阅导出](../../../packages/apps/tasks-review-app/src/export.ts)包含 stem、current、suggested 等字段，没有基线 commit 或内容哈希；[Task update](../../../packages/cli/src/commands/tasks/update.ts)也没有 expected-current 参数。**代码与协议推断：** 如果导出后任务已被别人重新分类，后来照旧结果应用，这条交接本身没有版本拒绝机制。人审表达了选择，Agent 仍需核对当前状态；本轮未执行陈旧结果覆盖的写入重现。

[Routine 协议](../../../packages/skills/edges/references/routines.md)要求同次运行从同一 commit 读定义与 Skill，读不到就停止，并分别报告仓库记录、平台配置和实际运行验证。平台若不遵守，文件正确也不能保证行为正确；改日程还要改平台配置。默认读最新降低副本漂移，但会改变下次行为；固定版本提高可复现性，也带来升级工作。

**README 应讲到的深度：** 人、Agent、工具、Git 与触发平台各有明确职责；开放的文件和协议方便组合，可靠运行仍需要接入与交接得到验证。

## 六、检验 harness 的工具，也必须说明自己的证据缺口

### 把实验结果与遥测传输分开

[ADR 0038](../../../docs/adr/0038-observation-trace-exporter.md)要求评测依赖通用 TraceExporter，把 Langfuse 字段留在映射层。当前消融 runner 在上报失败时向 stderr 报错，本地报告仍保留，分数不因遥测故障被改写。这有一个容易被 README 忽略的价值：网络或监控后端失效，不应偷偷改变“实验测到了什么”。[运行实现](../../../packages/evaluation/experiments/harness_memory_ablation/run.py)支持这一分离。

分离不代表故障无影响：集中观测会不完整，本地证据还需要保存。报告 payload 不包含 export 结果，若未保存 stderr，仅靠报告不能确认观测是否完整。传输机制可复用，样本含义、评分和何时上报仍由具体实验维护；实现分支提交 [31df326](https://github.com/VirusPC/edges/commit/31df326fdac013d1c2f71195e60b5d99ba807578)按实验目标拆分，相关文件随主干提交 `0acebff` 纳入，体现了“共享机制、保留各自语义”。

### 缺失值需要保留，但当前实现还未覆盖全部情形

[answer.py](../../../packages/evaluation/experiments/harness_memory_ablation/answer.py)在整条事件流没有任何 usage 记录时保留 `None`；但一旦存在 usage，未提供的单项仍可能保留累计初值 `0`，当前实现并未覆盖全部字段缺失情形。[score.py](../../../packages/evaluation/experiments/harness_memory_ablation/score.py)在证据不足时保留 `unscored`。这支持状态分离的设计方向，也暴露了尚未统一的口径：没有观测到成本，不等于成本是零；没有判分，不等于证明没有收益。

这些机制保护结果含义，却不自动解决实验有效性。当前报告记录 commit 与 dirty 布尔值，没有保存 dirty diff 的完整快照；未提交实验条件因此不能仅凭报告完全恢复。runner 也没有自动证明 A/B worktree 只差 Memory，条件控制仍依赖准备者。

### 结构存在、流程跑通、真实收益是三种证据

NodeService 测试能支持某个保存边界；runner 跑通能支持可以执行实验；要证明 harness 帮助长期工作，还需要构念匹配的题集、对照条件、可靠判分、成本与退化观察。库中已经用 [ADR 0008](../../../docs/adr/0008-evaluation-smoke-is-not-benchmark-proof.md)拒绝将冒烟分数直接当作记忆有效性的证明。

**更强的研究判断：** 如果最终要宣称“持续自我改进”，证据还得跨越采纳和下一轮使用：有问题、有修正、有更好的一次运行仍不够，需要说明改进被纳入了下一轮工作的实际方法，并在合适条件下继续有效。当前的通用自动数据清洗与定期评测仍见[闭环规划任务](../../../.edges/tasks/evaluation/backlog/2026-11-02--Personal-Evaluation自定义目标线上数据自动清洗与定期评测/INDEX.md)。

**README 应讲到的深度：** 可以围绕自己的目标检验 harness，并保留否定当前方案的可能；不要用框架自用、测试数量、报告存在或单次提分替代收益证据。

## 把一个闭环拆开看：哪里已经连接，哪里仍需人和 Agent

假设一次维护中，Agent 反复使用过时约定。这是一个说明交接的场景，**不是本轮已执行的真实案例**。

| 步骤 | 现有材料或机制 | 谁还需要完成什么 | 不能偷换的结论 |
| --- | --- | --- | --- |
| 发现重复问题 | 真实会话、文件、Observation 记录 | 人或 Agent 识别问题，确定适用对象 | 有 trace ≠ 已知根因 |
| 保存证据与疑问 | Note、来源引用 | 脱敏、保留原料、区分事实与猜测 | 有笔记 ≠ 已有可复用判断 |
| 明确改进目标 | Task、背景与完成标准 | 澄清成功条件与不改范围 | 已开卡 ≠ 可立即自动验收 |
| 形成修正候选 | Memory/Skill 改稿、可审阅产物 | 判断应改哪一层、保留什么历史 | 生成候选 ≠ 已采纳规则 |
| 构造实验 | case、criterion、condition、trial | 准备代表性样本、固定差异和判分条件 | runner 能跑 ≠ 对照有效 |
| 审阅并采纳 | 对话、审阅 JSON、PR 与版本 | 检查证据、当前状态和变更范围 | 分数过门槛 ≠ 自动获准部署 |
| 下一轮使用 | 按 scope 检索，或 Routine 读确定版本 | 消费端真的加载并遵循新方法 | 仓库更新 ≠ 客户端已采用 |
| 再次检验 | 新会话与后续实验 | 比较收益、成本和其他任务退化 | 一次改善 ≠ 长期持续收益 |

这条链有多个可自动执行的局部，但连接它们的语义判断仍有人工和 Agent 工作。[笔记转任务交接](../../../packages/skills/edges-create-notes/docs/adr/0009-open-items-to-conversation-to-tasks.md)、[任务分类流程](../../../packages/skills/edges-tasks-classify/SKILL.md)和 Routine 协议已经规定了一些交接；在本轮检查的 Task runlog、消融 runner 与 trace 映射中，未发现通用的“Task Run → 真实会话 → 评测样本 → 采纳 commit”自动关联合同，不能从模块同时存在推断它已经连通。

有价值的下一份公开案例应展示这一整条证据链，同时记录人工介入、失败与耗时。相比继续补模块图，它更能检验组合是否真的帮助工作。

## 接下来怎样把“设计很有价值”变成可检查的主张

下表是后续研究候选，不是本轮新建的任务或已执行的验证，也不要求收益必须为正。

| 待检验主张 | 最小比较方式 | 需要观察的结果 | 什么结果会削弱主张 |
| --- | --- | --- | --- |
| 局部上下文比集中历史更适合相关任务 | 同一任务、同一 Agent，比较按 scope 读取与平铺材料；保留跨模块题；另加相近预算、同等可用内容的对照 | 约束遗漏、误用规则、读取量、任务质量；区分减少背景与组织方式各自的作用 | 相关材料持续漏召回；控制预算后，无法支持关于组织方式的额外收益主张 |
| 记录理由与弃因有助于跨时间接续 | 给新 Agent“仅结论”和“结论＋原料＋弃因”，加入条件变化题 | 识别失效条件、重做判断的准确率与成本 | 读了更多材料仍机械照搬旧结论 |
| 结构化人审降低落地误差 | 对比普通文字确认与结构化结果；两组均包含确认期间已变更的任务 | 建议与应用是否一致，是否识别陈旧状态，人工修正量 | 决策正确但旧导出覆盖新状态，或误差与成本不优于文字确认 |
| 共用发现机制降低规则偏差 | 用相同夹具覆盖默认/super/all、exclude、Compose 嵌套 | 各视图是否满足各自明确合同 | 新模块仍要另写边界规则，或同一语义在视图间不一致 |
| 自用改进确实改善后续工作 | 保存一次 trace→case→改稿→采纳版本→复测的全链 | 达标率、token、时间、无关任务退化、人工介入 | 只有单题改善，额外维护成本超过收益，或无法复现 |
| 评测结论不受遥测故障污染 | 重放固定 Agent/Judge 输出，只改变 exporter 结果；另设完全缺 usage、部分字段缺失样本 | 本地 verdict 一致，缺失口径明确，保存 stderr 后能识别上报失败 | 上报故障改分数，字段缺失被当成零，或错误没有进入可回查材料 |

做这些实验之前，应保存条件差异、题库与判分版本；未提交 worktree 还应有可恢复的差异快照。否则精细分数会掩盖实验输入不可复现的问题。

## 对 README 的具体启发

最值得补的不是六个新标题，而是把现有叙事里的理由写得更具体：

1. **从“材料放回目录”进一步解释归属。** 共享实现不要求集中局部经验；维护对象变了，才切换对应维护上下文。用现有 Skill 递归图表达即可，不再增加一套抽象术语。
2. **从“长期积累”进一步解释可纠正性。** 下一次 Agent 能接续目标，也能找到当时的理由，判断什么已经不适用。保留与清理都服务于未来工作，而不是只追求更多文档。
3. **从“工具可接入”进一步解释责任。** 普通文件、Git、统一执行和外部平台各解决一段问题；用一个边界清楚的真实案例展示怎样连起来，胜过暗示整条链已自动完成。
4. **从“可以评测”进一步解释什么才算证据。** 固定任务、实际消费、检查成本与退化，并允许负结果；不要把实现测试或自用事实直接转译为效果承诺。

可供下一轮改稿采用的短段落如下，仍是研究候选：

> 经验留在它服务的对象旁，下一次工作既能找到结论，也能理解当时的理由。维护一个项目、一个模块或一套方法时，按需要进入相应上下文；目标与尝试分别记录，新的反馈先保留依据，再经判断与必要验证决定是否采纳。这样，积累可以继续使用，也可以在条件变化时被修正或移除。

这段候选还需要配合当前能力说明，不能独自替代接入、作用域和实现边界。按照[根 README 当前方向](../../../.edges/memory/projects/project_root_readme_direction/INDEX.md)，首页仍保留三条主线与已有五张图；机制细节进入折叠说明和来源文档。
