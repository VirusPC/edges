用户确认，开场保留选项，每条同时写明用途和落点。先列场景，两条接入流程只作兜底。先从上下文确定，缺了再问。不是取消菜单改成纯自由提问，也不要只复述空泛短名称。

**Why:** 只报「维护整个现有项目」这类短名称时，用户还要再选一次抽象流程才知道落在哪。把「已有项目添加 .edges」「创建独立 edges 仓库」「仅安装并验证 CLI」当作唯一开场菜单，又会让用户先理解实现词。选项本身带上用途和接入范围，就不用在场景和流程之间选两遍。维护整个现有项目和维护某个目录或模块仍是两件不同的事；后者的目录不一定属于代码项目。

**How to apply:** 向用户给出的选项要包含用途和落点，例如：维护整个现有项目，在项目根目录接入，积累约定、经验和任务；维护某个目录或模块，只在指定目录接入，保存这一范围的上下文，目录不一定属于代码项目；建立个人大脑，新建独立仓库，长期保存笔记、知识和个人项目；集中管理常用方法与 skills，独立维护，供多个项目挂载复用；建立团队共享库，集中保存团队规范与经验，供各项目使用。上下文已经明确就沿用，只问缺失项。场景对不上，或用户想直接选方式时，再给「在已有位置添加」和「新建独立仓库」。不要把执行路径再列成另一套选项让用户重选。用户明确只安装 CLI 时只做安装和验证。执行仍映射到已有目录初始化或创建独立仓库；独立仓库默认包含 GitHub 建仓与首次推送，并明确选择 private/public，用户要求仅本地时跳过远程步骤。开场不要求用户理解 .edges 或 harness。文档保持简短的三章。
