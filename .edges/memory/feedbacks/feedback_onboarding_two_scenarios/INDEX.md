用户确认，开场要按完全不了解这套系统的人来写。保留选项，每条用日常结果说明用途和范围。先列这些结果，两条接入流程只作兜底。上下文已经说清就不要再问。不是取消菜单，也不要只报空泛名称。

**Why:** 新用户回答不了 Edges、harness、.edges、个人大脑、skills、挂载这些词。只给「维护整个现有项目」这种短名称，用户还得再选一次抽象流程才知道落在哪。整个项目和某一个文件夹是两件不同的事；后者的文件夹不必属于代码项目。另外三件要让人听出差别：长期整理自己的笔记、知识和个人项目；把常用做法放在一处给多个项目用；把团队规范和经验放在一处给各个项目用。

**How to apply:** 向用户给出的选项写成他想留下什么、记在哪，例如：让整个正在做的项目记住约定、经验和接下来要做的事，记在这个项目所在的文件夹里；只让某一个文件夹记住这一范围的内容，且它不必属于某个代码项目；单独有一个地方，长期整理自己的笔记、知识和个人项目；单独有一个地方，放经常要用的做法，让以后多个项目都能拿去用；单独有一个地方，放团队共同的规范和经验，让各个项目都能用。对不上，或用户想直接说放哪儿时，再问加到已有文件夹还是新建一个单独的地方。用户明确只想安装命令时，只做安装和验证。文件夹路径、GitHub 账号和仓库名、公开还是仅限获授权的人，只在当前选择确实需要且上下文没有时再问，并用白话说明。新建一处仍默认包含 GitHub 建仓与首次推送，公开范围必须由用户明确选择，不能替用户假定；用户要求仅本地时跳过远程步骤。执行路径不要再列成另一套选项。文档保持简短的三章。
