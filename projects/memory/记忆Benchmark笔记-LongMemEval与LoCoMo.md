# Agent 记忆 Benchmark 笔记（面试向）

> 覆盖三个数据集：**LoCoMo**、**LongMemEval**、**FinanceBench**。
> 重点是 LongMemEval 的实验设计（面试可直接回答），并与 LoCoMo 对照。
> 整理日期：2026-06-24

---

## 0. 三个 benchmark 在测什么构念（先看这张）

**什么是"构念(construct)"**：你真正想测、却无法直接观测的那个**潜在能力**；只能通过任务表现去间接推断。**构念效度**就是——这个任务的分数在多大程度上**只反映那个目标能力**，而没被别的能力（confound）带跑。对比 benchmark 的正确轴不是长度/题量/模态，而是"**它的目标构念是什么、测得干不干净**"。

**把"记忆"这个构念定义清楚（操作化）**：当一条信息**已离开当前输入焦点**（被新内容淹没，或超出上下文窗口）后，系统能否
① **写入/编码**它 → ② 需要时**检索**回来 → ③ **正确使用**。
要把它和三件**不该算进记忆**的能力分开：(a) 通用长文本**阅读理解**、(b) 复杂**推理**（多跳/时间/数值）、(c) 模型自带的**世界知识**。一个高效度的记忆基准，应让"答错"几乎只可能因为①②③出问题，而不是 a/b/c。

| Benchmark | 想测的**目标构念** | 实际混入的 **confound** | 对"记忆"的效度 |
|---|---|---|---|
| **LoCoMo** | 超长多会话对话后，对**早期对话信息的回忆与使用**（长程对话召回） | 长对话阅读理解、多跳/时间推理、**世界知识**(open-domain 类)、词面匹配；写入被固定 → 单一 F1 不可归因 | ✅ 但**低** |
| **LongMemEval** | 5 个**明确的记忆子构念**：事实召回(IE)、跨会话聚合(MR)、**更新后信息的一致性(KU)**、时间推理(TR)、负向召回/拒答(ABS) | 多跳/时间推理仍混入；LLM 裁判偏差。但用 oracle/recall@k 能把**检索 vs 阅读**拆开 | ✅ **较高** |
| **FinanceBench** | 从财报中**检索证据并据此作答**（grounded 金融 QA）—— 与记忆无关 | **数值计算**、表格解析、领域知识、数据污染；但 closed/oracle/vector-store 三设定可拆检索 vs 推理 | ❌ **非记忆** |

> 读法：第 2 列是"benchmark 声称在测的潜在能力"，第 3 列是"分数里实际还掺了什么"——两列差得越远，效度越低。逐题型的构念拆解见 §3.2。
> 注：`Mafin2.5-FinanceBench` 是评测结果仓库，不是论文；底层论文是 FinanceBench（arXiv 2311.11944）。

## 1. LongMemEval（面试主角）

### 1.1 动机
现有长期记忆基准两个毛病：
- **历史太短**（几千 token，长度不可调，系统变强即饱和）。
- **能力覆盖不全**：普遍不考"助手说过的信息"、"用户信息被更新"、"复杂时间推理"。LoCoMo 也有这些缺口。

→ 目标：长度**可无限扩展** + 能力**覆盖完整**的记忆评测。

### 1.2 Benchmark 设计
核心是"大海捞针"升级版：证据藏进很长的用户—助手历史，系统**在线逐会话接收**，看完后回答。

- **500 道全人工问题**，覆盖 **5 种核心能力**：信息抽取(IE)、多会话推理(MR)、知识更新(KU)、时间推理(TR)、拒答(ABS)；展开成 **7 种题型**（含"助手侧信息"题、30 道假前提拒答题）。
- **构造三步**：
  1. 人工写问题 + 把答案拆成"证据陈述"（可带时间戳）；定义 164 个用户属性本体生成背景。
  2. self-chat 把每条证据**不经意地**嵌进任务型会话（刻意不直说，增加难度），人工校验并打散位置。
  3. 把证据会话插进大量**无关填充会话**（ShareGPT / UltraChat + 模拟对话），拼成带时间戳的完整历史。
- **两个标准档**：
  - `_S` ≈ **11.5 万 token**（约 50 会话）——能塞进长上下文模型当 baseline。
  - `_M` ≈ **150 万 token**（500 会话）——**故意超出任何上下文窗口**，逼用记忆系统。

> **构念效度设计**：三个关键选择都是为了让"记忆"分数只反映记忆——**间接植入证据**(堵掉词面匹配捷径)、**在线逐会话**(逼出真实写入、而非纯阅读)、**不依赖世界知识**(剔除参数知识 confound)。对应构念拆解见 §3.2–3.3。

### 1.3 统一记忆框架（实验骨架，面试重点）
任意记忆系统 = **key-value 存储 + 三阶段**：**indexing（写入/建索引）→ retrieval（检索）→ reading（阅读作答）**。
沿线设 **4 个控制点（CP）**，实验逐点消融：

- **CP1 Value（存什么粒度）**：整段 session / 拆成 round / 再抽 summary 或 fact
- **CP2 Key（用什么做索引）**：value 本身当 key vs 额外抽 fact/关键词/时间戳扩展 key
- **CP3 Query（查询怎么构造）**：朴素相似度 vs 时间感知的查询扩展
- **CP4 Reading（怎么读）**：直接读 vs Chain-of-Note / 结构化(json) 格式

> 还把 9 个已有系统（MemoryBank、HippoRAG、RAPTOR、MemWalker、ChatGPT、Coze…）套进框架对照，证明通用性。

### 1.4 实验设置
- Reader：GPT-4o、Llama3.1 70B/8B。
- 检索器：Stella V5（1.5B 稠密检索）。
- Indexing：Llama3.1-8B 抽 summary/fact/时间戳。
- Reading 默认开 Chain-of-Note + json；检索结果按时间戳排序。
- 在 `_M` 上**按 token 预算公平比较**各设计。

### 1.5 核心发现（4 条优化结论 = "so what"）
1. **Value：round 是最优粒度**。拆成"一问一答"明显优于整段；再压成 summary/fact 会因信息丢失变差——**唯一例外**：多会话推理题抽成 fact 反而更好。
2. **Key：扩展 key 有效**。value 之外再抽 user fact 扩充索引：recall@k **+9.4%**、QA **+5.4%**。
3. **Query：必须时间感知**。朴素检索处理不了"上周推荐的那家餐厅"；给 fact 关联时间戳、按时间范围缩检，时间推理 recall **+6.8%~11.3%**。
4. **Reading：读同样关键**。即便检索全对，长上下文也未必用对；Chain-of-Note + 结构化格式让 QA 最多 **+10 个百分点**。

外加两个有冲击力的结论：
- 商用系统（ChatGPT/Coze）在比 `_S` 还简单 10 倍的设定下也只有 **30%~70%**；ChatGPT 会**覆盖旧信息**，Coze 记不住**间接透露**的信息。
- 长上下文模型硬读整段历史，比 oracle 掉 **30%~60%** → **光靠长上下文 ≠ 有记忆**。

### 1.6 指标设计
- **端到端**：**LLM-as-judge（gpt-4o），每题型独立 rubric，与人类一致率 >97%**，汇报 accuracy；拒答题判是否正确说"不知道"。
- **中间**：因有**人工标注的证据位置**，可算 **Recall@k / NDCG@k** 看检索。
- **参照系**：
  - **Oracle**（只喂真证据会话）= 完美检索上界，隔离 reading 段。（注：是 ML 术语"开上帝视角的理想组件"，**不是甲骨文数据库**。）
  - **Offline reading**（整段历史灌进长上下文）= 硬读 baseline。
  - **%Drop vs Oracle** → 把错误归因到"没检索到"(recall 低) vs "检索到没用对"(recall 高但 oracle-gap 大)。

### 1.7 电梯版（30 秒可背）
> LongMemEval 是长度可扩展的"大海捞针式"长期记忆基准，500 道人工问题覆盖信息抽取、多会话推理、知识更新、时间推理、拒答五种能力，把证据隐蔽地埋进最长 150 万 token 的在线聊天历史。它把记忆系统统一抽象成 indexing→retrieval→reading 三阶段、四个控制点并逐点消融，得出四条结论：**存储用 round 粒度、索引扩展 user fact、查询要时间感知、阅读用 Chain-of-Note**。评测用与人类 97% 一致的 LLM 裁判算 accuracy，配合 Recall@k 和 oracle 上界把错误归因到检索还是阅读。核心信息：**长上下文硬读 ≠ 有记忆，真正可扩展的是写入-检索-阅读的记忆系统。**

### 1.8 可能的追问 & 答法
- **为什么 round 比 session 好？** session 太长、混多个话题，信噪比低，检索和阅读都受拖累；round 粒度细、定位准，又不像 fact 那样丢信息。
- **为什么不用 EM 用 LLM 裁判？** 答案形式灵活（短语/数字/开放偏好），EM 会误判；LLM 裁判按题型 rubric 打分，且做了元评测（与人 >97% 一致）保证可信。
- **150 万 token 怎么进上下文？** 不进。`_M` 故意超窗口，逼记忆系统在线消化成记忆库，提问时只检索 top-k（几千 token）进 reader——1.5M 是被检索的草堆，不是 prompt。
- **它和 RAG 什么关系？** 它就是把"长期记忆"当作在线 RAG（context compression 视角）来评测：indexing≈写库、retrieval≈召回、reading≈生成。

## 2. LoCoMo（对照）

### 2.1 它到底测什么（构念视角）
**不是"记忆系统"评测，而是"模型长期记忆能力"的 QA 数据集。**
你看到的 memory+reflection 模块在**数据生成流水线**里（造对话用），不在被测对象里。
被测的是三种朴素配置：Base LLM（截断）/ 长上下文 LLM / 固定 RAG（DRAGON 检索 + GPT-3.5-16k 阅读，只换检索单元：对话轮 / observation / 摘要）。

**构念上**：写入被固定（observation/摘要预建），一个 F1 把"**召回 + 长对话阅读 + 多跳/时间推理**"裹在一起、不可归因；且 open-domain 类还引入**世界知识 confound**（答错分不清是记忆还是参数知识）。
→ 它回答"**给定已建好的记忆，模型能否取回并用对**"，**不研究记忆怎么写入/巩固**；作为"记忆"构念是**低效度探针**（详见 §3）。

### 2.2 数据集
- **50 段**合成（LLM 生成 + 人工编辑）双人多会话多模态对话。
- 平均：19.3 会话/段（最多 35）、~300 轮、**9,209 token/段**、32.3 张图、24.2 个事件。
- 构造：persona（取自 MSC）+ 时间事件图 G（6–12 月、≤25 事件、带因果）+ generative-agent 架构生成；图片网络检索 + BLIP-2 caption；人工改约 15% 轮、替换/删 19% 图。
- 标注：**QA 共 7,512 题**（单跳 36% / 多跳 14.6% / 时间 20.6% / 开放域知识 3.9% / 对抗 24.9%，每题标证据 turn ID）；事件图 ground truth；observation（18.2 tok）与 session summary（127.4 tok）。

### 2.3 三个评测任务与指标
1. **QA**：5 类推理，**F1 部分匹配**；RAG 另报 **recall@k**。
2. **事件摘要**：对比事件图 G，**FactScore（原子事实 P/R/F1）+ ROUGE**。
3. **多模态对话生成**：训 MiniGPT-5 三变体，**MM-Relevance + BLEU**。

### 2.4 主要结论
GPT-4-turbo 最强 base 仅 ~32 vs 人类 87.9；长上下文易幻觉（GPT-3.5-16k 对抗题掉到 2.1%）；RAG 用 observation 存储最有效（~+5%），检索块太多反伤（信噪比）；**时间推理和开放域知识最难**。

## 3. 构念效度对比（核心）

### 3.1 claimed vs actual：每个 benchmark 到底量什么

| | 目标构念 | 能干净隔离的 | 主要 confound | 对"记忆"的效度 |
|---|---|---|---|---|
| **LoCoMo** | 长对话记忆（笼统） | 几乎不隔离（单一 F1） | 阅读理解、世界知识、词面匹配 | **低**：写入固定、记忆与推理/知识纠缠 |
| **LongMemEval** | 5 个记忆子能力 | 检索 vs 阅读（oracle / recall@k）、写入（在线） | 多跳/时间推理仍混入；裁判偏差 | **较高**：构念拆细且可归因 |
| **FinanceBench** | 文档 QA（检索+数值推理） | 检索 vs 推理 vs 参数知识（closed / oracle / vector store 三设定） | 数值计算、表格解析、数据污染 | **不适用**（非记忆） |

### 3.2 题型 → 它实际在测的构念

**LoCoMo（5 类）**
- single-hop → 单会话召回（≈IE）
- multi-hop → 跨会话聚合 × 多跳推理
- temporal → 时间推理
- **open-domain knowledge → 对话信息 + 世界常识混用 → 构念污染**（答错分不清是记忆还是参数知识）
- adversarial → 不可答检测（≈拒答）

**LongMemEval（5 能力 / 7 题型）**
- IE（用户/助手）→ 最纯的事实召回；含**助手侧召回**这一被忽略的构念
- MR（多会话）→ 多 needle 检索 + 聚合（记忆 × 多跳）
- **KU（知识更新）→ 信息被覆盖时的记忆一致性**（时间优先级）—— 独立且少见
- TR（时间推理）→ 检索 × 时间算术
- ABS（假前提）→ 负向召回 / 拒答校准
- preference → 把存下的偏好用于个性化生成

### 3.3 构念空间覆盖（差异的本质）

LoCoMo 与 LongMemEval 在 IE/MR/TR/拒答上重叠；但 **LoCoMo 缺 KU、助手侧召回两块构念，又多了"开放域世界知识"这一污染项**。
LongMemEval 主动**砍掉世界知识**、用**间接植入证据**堵掉词面匹配捷径、用**在线逐会话**逼出真实写入——这三点都是 construct validity 意识的体现：它在尽量让"记忆"分数只反映记忆。

### 3.4 指标层面的效度

- LoCoMo **F1 部分匹配**：奖励逐字照抄、罚改写 → 有一半在测词面重叠，而非"答对没"。
- LongMemEval **LLM-judge（与人 97% 一致）**：measure 对齐"语义答对"；配 Recall@k/NDCG@k + Oracle 做**阶段归因**（错在没检索到 vs 检索到没用对）。
- FinanceBench **人工三分类（对 / 错 / 拒答）**：专门把"幻觉 vs 拒答"这个构念量出来。

### 3.5 对研究的落点

- 论证"**某记忆机制更优**"（写入/索引/检索哪种好）→ 用 **LongMemEval**（能隔离记忆、按阶段归因）。
- 想要"**真实长对话整体表现感**"→ LoCoMo 可辅助，但别拿单一 F1 当"记忆"强弱的结论。
- 测"**长文档检索 + 抗幻觉**"→ FinanceBench（注意数值推理是混入项）。

> 表面维度对照（题量/长度/模态等）见各章正文；本节只按构念效度比较。

## 4. FinanceBench（金融 QA / RAG，非记忆基准）

> arXiv 2311.11944，Patronus AI·Contextual AI·Stanford，2023。`Mafin2.5-FinanceBench` 仓库即基于它。
> 和记忆无关；对本项目是**长文档检索 / 抗幻觉的对照基准**。

### 4.1 它测什么（构念视角）
真实财报上的**开卷金融问答**：LLM 能否从财务文件里**检索 + 数值/逻辑推理**作答。
**构念上**：它是"**检索 × 数值推理 × 表格理解 × 领域知识 × 拒答**"的捆绑——最大 confound 是**数值计算**（检索和理解都对、只是算错也会判差）。与记忆无关；对本项目是**检索接地 / 抗幻觉**的对照。

### 4.2 数据集
- **10,231 条**，每条 = 问题 + 答案 + **证据串(evidence string)** + 页码（部分含"计算依据 justification"）。
- 覆盖 **40 家美国上市公司、361 份公开文件(2015–2023)**：10-K / 10-Q / 8-K / 财报。
- 带公司、GICS 行业、文档类型/年份等标签，便于细粒度分析。
- **三类问题（按来源）**：
  - **domain-relevant**：每家 25 道通用题（是否分红、利润率是否稳定等），分析师设计。
  - **novel generated**：分析师手写、贴公司/行业，要求真实+多样+需推理，共 **1,323** 道（均 36/家）。
  - **metrics-generated**：从三大报表（利润表/资产负债表/现金流量表）抽 18 个基础指标、8 年，模板化生成（含跨表计算），共 **7,983** 道（均 249/家）。
- **难度分类法**（applied n=8,908）：信息抽取(28%) / 数值推理 / 逻辑推理。
- 重人工：13 名分析师写题、2 名抽指标、资深分析师复核，~10% 抽查。

### 4.3 实验设置
人工评测子集 **150 道**（domain/novel/metrics 各 50），16 个配置全人工核对，**n=2,400**。
4 个模型（GPT-4、GPT-4-Turbo、Claude2、Llama2）× 5 设定 × 2 prompt 顺序 = **16 配置**：
- **Closed book**：不给任何资料（最朴素）。
- **Oracle**：直接给证据页 → 去掉检索难度，上界。（同样是 ML 术语 oracle，不是数据库。）
- **Single vector store**：每篇文档一个向量库（搜索范围小、偏易、不现实）。
- **Shared vector store**：全部 360 篇共用一库（Chroma + Langchain + ada-002，**最贴近真实**）。
- **Long context**：整篇财报塞进窗口（GPT-4-Turbo 128k / Claude2 100k，超长截断到 ~10 万 token）。
- 两种 prompt 顺序：Context-First / Context-Last。

### 4.4 指标
**无自动指标**，人工把每条回答判成三类：**正确 / 错误 / 拒答(failure to answer)**。允许单位、微小四舍五入等小偏差；答案对但逻辑与证据矛盾也算错。

### 4.5 核心结论
LLM 在金融 QA 上明显不足：**GPT-4-Turbo + 共享向量库有 81% 题答错或拒答**；长上下文有帮助但企业不现实（延迟高、250 页财报塞不下）；普遍有幻觉和拒答。
> 设计借鉴：oracle vs 向量库 = "检索 vs 推理"的拆分思路（和 LongMemEval 的 oracle 归因异曲同工）。

## 5. 评测集"好不好"的一般标准（讨论沉淀）
分布只是其中一根支柱。优先级大致：
1. **构念有效性**：真的在隔离"记忆"这一能力，没被推理/检索器/prompt/答案抽取等 confounder 混淆（最关键）。
2. **标注与指标可靠性**：ground truth 无错无歧义，指标真反映对错（LongMemEval 的 97% 元评测就是干这个）。
3. **区分度**：能拉开强弱、不饱和、防刷分捷径。
4. **防数据污染**：合成数据有优势，但牺牲真实分布。
5. **数据分布/代表性**：决定能否外推到真实部署（外部有效性）。

> 取舍示例：LoCoMo 为了"长+可控+不泄漏"选了合成数据，代价是分布真实性下降——所以"分布最重要"在它身上恰恰不成立。
> 结论：想说"能上线/真实更强"→ 看分布；想说"某记忆机制更优"→ 看构念有效性 + 区分度。
