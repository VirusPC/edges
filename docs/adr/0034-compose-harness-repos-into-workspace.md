# 工作空间由就地 harness 加若干被组合的 harness 仓库构成

2026-10-17 的 grill 确认：edges 接入其他工作空间时，不把 edges 当成一个要挂进去的独立记忆库。项目自己的知识在项目里就地 init；大脑、团队库、规范库、组件库这类跨项目的 harness 仓库，用同一套机制叠加进来，统称「组合（compose）」，对应 Devin Agent Memory 文章里的 composable。一个工作空间 = 自身就地的 harness + 若干被组合的 harness 仓库。被组合的仓库按「是不是工作空间里的本地文件」分成本地和远程两类，远程记忆仓库由服务端持有，经 MCP 读取，只由 dream 写入。

本 ADR 补全 ADR 0032 的「接入方式」（code agent 经用户级配置接入大脑仓库、personal agent clone），并部分取代其 Consequences 里「其他仓库里的 code agent 接入大脑 harness」「团队这一层的 harness 仓库」两项未实现说明：接入方式改由本 ADR 规定，实现仍待做。大脑归入远程记忆仓库后，默认经 MCP 读取，不再要求各 Agent 各自 clone。`--super` 跨多个仓库不在本 ADR 范围内。

**Status:** accepted（ADR 0034；grill 确认于 2026-10-17，同日经两轮修订，被推翻的做法见 Considered Options）

**See also:** ADR 0032（大脑是虚拟目录）、ADR 0004（MCP 子进程调 CLI）

## Decision

1. **术语与两类记忆**：大脑、团队库、规范库、组件库都叫被组合的 harness 仓库，动作叫「组合」。不用「外部记忆」「挂载」，这两个词会让人以为 edges 是一个独立记忆库，和「harness 任何目录」冲突。按「是不是工作空间里的本地文件」分两类，不按团队、项目或个人分：
   - **本地记忆**：项目内就地的 `.harness/`，跟代码走，规模小。AI 顺着目录读本地文档，不建索引。
   - **远程记忆仓库**：团队库、规范库，以及大脑。服务端持有仓库并离线维护索引，客户端经 MCP 读取，不拉取到本地。
2. **组合清单**：格式是 JSON。用户级 `~/.harness/compose.json`，放跟人走的仓库（如大脑），不强加给同事；任意目录都可以有自己的 `.harness/compose.json`，随代码提交，协作者一致，和「harness 任何目录」一致。生效时从工作目录向上逐层收集各级 `.harness/compose.json`，再加上用户级清单；同名仓库离工作目录越近越优先，用户级最低。每项写名字、仓库地址和 MCP 地址，例如 `{ "name": "team-kb", "repo": "<git url>", "mcp": "<https url>" }`。`mcp` 用来读；`repo` 用来定位来源（检索结果链接回 git 原文）、确定 dream 往哪个仓库开 PR，以及服务端不可用时的兜底。只填 `repo` 不填 `mcp` 的项按本地仓库处理：clone 后顺着目录读，小仓库不必起服务。
3. **远程记忆仓库的读取**：服务端持有仓库，通过 MCP 暴露几类工具支撑客户端检索：读一层索引、读原文、`search`，以及写入用的 `remember`（见第 8 条）。代码 Agent 和 ChatGPT 这类对话框走同一套远程工具，客户端不再把远程仓库拉到本地。服务端仍用 CLI 实现这些工具，MCP 子进程调 CLI（遵循 ADR 0004）。服务端不可用时，可以按 `repo` 临时 clone，顺着目录读。clone 位置（只用于只填 `repo` 的项和这种兜底）是 `~/.edges/repos/<name>`，是否改到 `~/.harness/` 下另议。ChatGPT 这类没有本地 harness 的宿主，组合清单用服务端默认清单。
4. **远程检索借 PageIndex 的思路，不用它的代码**：远程库可能有几千篇、每篇 300–1000 字，难点不在速度，而在同义词漏检和单层索引太长读不完。PageIndex（VectifyAI/PageIndex）不用向量，给文档生成带摘要的目录树，检索时让模型顺着树推理。短文档单篇建树没有意义，需要全库一棵树；Edges 的目录层级加各层 `README.md` / `AGENTS.md` 组成登记里的 name / description，本身就是这棵带摘要的树。索引就是这些入口文件（可选再加各目录的汇总摘要），留在同一个记忆仓库里、随 PR 审核，不另设构建产物或向量库。索引离线建、由 dream 维护，检索时只读。维护要求：每层子节点控制在几十个以内，过多就拆目录；摘要要能帮模型判断该走哪个分支。`search` 按 PageIndex 的方式从根层读索引，选分支、逐层往下，最后读原文，结果附上 `repo` 里的原文位置。本地记忆规模小，不建索引。
5. **`edges context` 命令**：从工作目录向上收集各级清单，再加用户级清单，按覆盖规则合并。对本地 harness（项目自身，以及只填 `repo` 的项），用现有 traverse 的 `localOnly` 取根 `AGENTS.md` 的「本层硬约束」区块和本层系统维护信息索引（name / description）；只填 `repo` 的项本地没有就 clone，有就带超时 `git pull`，失败时沿用旧版本并告警。对远程记忆仓库，调用它的 MCP 取根层硬约束和一级索引。按「项目自身 harness、由近到远的各级目录组合、用户级组合」的顺序拼成 Markdown，每段标明来源仓库和路径；有字数上限，超出时先截索引、保留硬约束，并提示精简；输出到 stdout。深处的内容靠检索。服务端的 MCP `context` 工具给对话框用，按服务端默认清单返回同样格式的内容。`--super` 用的 `harness-materials.json` 只列同仓相对路径、不挂其他系统的 `AGENTS.md`，不能拿来当组合清单；组合清单是新概念。
6. **开场注入先从简**：不做 hook。只在代码 Agent 客户端的用户级配置或 ChatGPT 自定义指令里写一句「开场先运行 / 调用 `edges context`」。对话框类宿主无法保证开场注入，MCP 工具只在模型决定时才被调用，只能尽力而为。
7. **写入规则**：本地记忆由人和 Agent 直接写进项目自身的 `.harness/`，写在哪由目录决定，随代码提交。远程记忆仓库只有一个写入口：服务端离线运行的 dream，产出一律走 PR，由维护者审核。个人和 Agent 都不能直接写远程仓库，只写自己项目的 `.harness/`，由 dream 挑选提升。代价是经验要等 dream 下一轮跑完、PR 合并后才对他人可见，可能要隔天。
8. **`remember` 只进收件箱**：ChatGPT 这类没有本地 harness 的宿主，用远程 MCP 的 `remember` 工具记东西，但它只写进服务端的收件箱（待处理区），不直接改仓库。dream 下一轮统一消化并开 PR，写入口仍然只有 dream。
9. **dream 的输入、触发与职责**：输入是各项目 harness 主分支的变化，加上收件箱。每 24 小时检查一次，只有自上次运行以来有变化才运行（项目 harness 主分支有新提交，或收件箱非空），没有变化就跳过。这样省成本，也把一天的变化攒成一批。职责是：把项目 harness 里可跨项目复用的内容提升到大脑或团队库；消化收件箱；维护第 4 条的树状索引（拆目录、更新摘要）。产出一律走 PR，由维护者审核。
10. **dream 在哪运行另议**：GitHub Actions 定时任务或自建机器上的 cron 都可以，不是本 ADR 的重点。
11. **分支记忆不做特殊标记**：分支上的记忆留在该分支自己的 `.harness/`，分支丢弃就随之消失；合入项目主分支时和代码在同一个 PR 里被审到。远程记忆仓库只经 dream 写入，dream 只看项目 harness 的主分支，分支上的零碎经验到不了远程仓库。中心化方案（Mem0、OpenViking、Hy Memory 等）所有写入进同一个库，只能靠事后打标签（如 `workspace_id`、`branch`）隔离，这是 git 分布式方案的一个优势。

## Considered Options

- **把 edges 当外部记忆库挂进各个工作空间：** 否决。与「harness 任何目录、记忆离被 harness 对象最近」冲突；项目知识应就地 init。
- **按团队 / 项目 / 个人划分记忆的接入方式：** 否决（2026-10-17 同日修订）。真正决定接入方式的是「是不是工作空间里的本地文件」；大脑虽是个人的，也按远程处理。
- **被组合仓库一律 clone 到 `~/.edges/repos/<name>` 本地读写，由 `edges context` 负责 clone / pull；代码仓库拉本地、对话框走远程：** 否决（2026-10-17 同日修订）。大库拉到每台机器上，各自读不完也建不好索引，代码 Agent 和对话框还要走两套路径；改为服务端持有远程仓库，两类宿主走同一套远程工具。本地 clone 只留给只填 `repo` 的小仓库和服务端不可用时的兜底。
- **`edges search` 作为本地命令为主：** 否决（2026-10-17 同日修订）。远程仓库不再拉到本地，检索改为远程 MCP 工具，服务端用 CLI 实现。
- **用户明确要求时，按普通文件写进被组合仓库并开 PR：** 否决（2026-10-17 同日修订）。这会让远程仓库有多个写入口、PR 零碎；改为只由 dream 写入。
- **`remember` 直接改远程仓库或直接开 PR：** 否决。绕过 dream 这个唯一写入口；改为只进收件箱。
- **git submodule：** 否决。会把别人的仓库塞进项目历史，同事被迫跟着拉。
- **让用户手动 clone 并在配置里写路径：** 否决。路径因人而异，清单无法随代码提交，也没法统一更新。
- **用中心化记忆服务做真相源（Mem0 一类）：** 否决。远程 MCP 只是 git 仓库之上的读取和收件层，仓库仍是唯一真相源，人可读、可审、可回滚，服务可以从仓库重建。（初稿写的是「主路径直接调中心化远程服务」，同日修订为现在的远程 MCP 方案。）
- **复用 `--super` 的 `harness-materials.json` 作为组合清单：** 否决。它只列同仓相对路径，不挂其他系统的 `AGENTS.md`。
- **组合清单只放项目根、用 YAML（`.harness/compose.yaml`、`~/.edges/compose.yaml`）：** 否决（2026-10-17 同日修订）。只放项目根与「harness 任何目录」不一致，monorepo 的子目录没法有自己的组合；改为任意目录的 `.harness/compose.json` 加用户级 `~/.harness/compose.json`。
- **组合清单每项只写 git 地址：** 否决（2026-10-17 同日修订）。远程仓库要经 MCP 读，需要 `mcp` 字段；`repo` 仍保留，用于来源定位、PR 目标和兜底。
- **用会话启动 hook 保证注入：** 暂缓。各宿主的 hook 不统一，先用一句配置指令。
- **给分支记忆打标签隔离：** 否决。分支自己的 `.harness/` 已经天然隔离。
- **检索时在线现建索引：** 否决。每次检索都要读大量原文，成本高、结果不稳定；索引改为离线建、由 dream 维护。
- **向量加 BM25 混合检索，索引作为 CI 构建产物另存：** 暂不采用。索引不在同一个记忆仓库里、不能随 PR 审核，与第 4 条不符；可作为以后补充召回（如同义词漏检）的方向。
- **直接用 PageIndex 开源代码：** 否决。开源版按单篇长文档建树（主要是长 PDF，也支持 Markdown），和「几千篇短文档、全库一棵树」不匹配；跨文档库的 PageIndex File System 只在云服务里提供。
- **dream 按固定周期无条件运行，或每次有变化都立即运行：** 否决。前者在没有变化时白花成本，后者 PR 太碎、审不过来；改为每 24 小时检查且有变化才运行。

## Consequences

- 以下都未实现：远程 MCP 服务（读一层索引、读原文、`search`、`remember`、`context`）；服务端收件箱；dream 本身（提升、消化收件箱、维护索引）及其调度（每 24 小时检查、有变化才运行；运行位置另议）；组合清单（各级目录和用户级的 `compose.json`，`repo` 与 `mcp` 字段）；`edges context` 合并本地 harness 与远程仓库的上下文。
- 远程仓库里的经验要等 dream 下一轮和 PR 合并后才对他人可见，可能隔天。
- 读远程仓库依赖服务端在线；服务端不可用时只能按 `repo` 临时 clone 顺目录读，没有索引辅助。
- 对话框类宿主的开场注入只能尽力而为，不能保证每次会话都带上组合后的上下文。
- 检索质量依赖目录结构和摘要写得好不好：每层子节点要控制在几十个以内，摘要要能帮助分支判断。纯树状推理检索对同义词漏检的缓解程度还没有验证，如果不够，再考虑补充向量召回。
- 还没定的：远程 MCP 的鉴权；dream 要看哪些项目仓库的主分支、怎么拿到读权限；服务端开 PR 用的写权限。
- 术语见 `CONTEXT.md` 的「组合（Compose）」「组合清单（Compose List）」。
