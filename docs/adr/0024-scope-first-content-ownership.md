# 内容按作用域归属，在作用域内区分类型

Edges 的递归目录以作用域作为内容归属的主轴：项目专属的笔记、任务和可复用判断归该项目工作区，根级内容归根作用域；跨作用域检索与看板负责汇总，复用关系通过引用连接。用户于 2026-10-02 确认这一取舍，目的是让人和 Agent 进入一个作用域后能够接手完整的工作上下文，避免仅因内容类型不同而将同一项目的内容分散在全局目录。

完整目录、索引与迁移交付要求见[整体设计](../superpowers/specs/2026-10-03-recursive-scope-layout-design.md)，用户于 2026-10-03 整体确认目标目录，尚未实施。

## 任务与知识容器

任务是工作项，不作为知识资产容器的内容类型收纳。目标布局中，根作用域的领域任务放在顶层 `tasks/`，维护任务归对应维护空间的 `tasks/`，子作用域的领域任务归子作用域自身的 `tasks/`。根看板可以汇总各处真源，但不能因汇总而把全部子域任务重新集中到根。

用户确认将 `projects/`、`teaching/` 提升为顶层工作区集合，与 `tasks/`、`knowledge/` 并列：前者以问题解决与交付为目标，后者以学习进展与能力获得为目标。工作区可按实际需求拥有知识、任务和自身维护空间；`knowledge/` 收敛为所属作用域的知识内容，不再作为所有业务对象的兜底。此决定确定目标布局，逐项迁移、站点入口与调用适配仍待设计。

## 自身维护空间

用户确认现有 Tasks 混淆了通过 Edges 完成领域工作的任务与维护 Edges 自身的任务，并确认对存在独立维护需求的作用域，应为维护它自身的工作设立明确的归属空间，与领域工作区分。该空间统一组织本作用域承担系统二职责的对象；任务管理等能力仍可共用，不能把 Task、Skill 或 Memory 这样的类型整体固定为系统一或系统二。

自身维护目录采用 `.harness/`。用户于 2026-10-03 将此前候选名 `.edges/` 改为 `.harness/`，用职责表达本作用域的支撑、维护与改进空间，减少对工具品牌的绑定；模块划分、入口规则与共享实现位置保持。该目录是默认维护材料落点，工具约定路径可通过索引接入；目标结构尚未创建或迁移。

“自身维护空间”仍是适用于个人、Agent、团队等主体的通用概念；`.harness/` 是其默认本地目录名称。系统二是相对职责角色，Agent Harness 是 Agent 的支撑机制，二者不因此变成同义词，也不要求将所有相关实现放进该目录。

历史 runa 工具曾使用同名 `.harness/` 存放另一种记忆布局；新设计使用它作为维护空间容器，维护知识仍位于内部 `memory/`。已有同名目录须按实际结构识别并检查冲突，不能据目录名自动接管或认定迁移完成。

## 共享实现与固定入口

用户确认 Q2.2，并在 Q8 补充工具产物的路径例外：本作用域自有的维护状态、材料与配置默认集中存放在自身维护目录；根 `AGENTS.md` 等固定入口，以及已有有效 Skill 或工具路径约定的材料，可以保留原位，通过索引接入。共享能力实现通过引用接入，不因被使用而复制到每个维护空间。

用户提出共享实现可以由 Edges 仓库本身提供。“外部”描述它与消费作用域维护空间的关系，不要求代码位于另一个 Git 仓库。实现真源、安装分发位置与本次操作目标需要分别识别；共享代码不意味着共享所有作用域的任务与记忆。具体安装、引用和调用方式尚未选定。

Edges 当前同时承载个人实践与能力实现。用户澄清：即使采用各作用域就近维护、上层负责整体协调的方案，现有整套 `edges` CLI 仍归根作用域拥有和维护；其维护任务与知识归根维护空间，子作用域使用它产生的领域内容仍归子作用域。`extensions/cli/` 是源码组织位置，不能仅据此推导出独立的维护责任作用域；不能仅按源码目录为 `extensions/` 建立独立维护空间。

用户进一步确认 Q10：`extensions/`、`shared-extensions/`、`apps/`、`scripts/` 保留实现真源的位置，其维护任务和知识先按实际职责归根维护空间。已有局部记忆须逐项判断维护对象，不机械整包合并；局部入口、工具路径约定和必要的上下文关系仍需保留。仅在某部分确有独立管理目标、决策和验证的需要时，再明确划出子作用域。

这确定了当前实例的责任归属，不代表 CLI 已支持任意子作用域，也不把仓库改成纯实现仓或要求迁出个人内容。

## 根层评测与观测

用户确认 Q9：现有 `evaluation/` 与 `observation/` 分别迁至 `.harness/evaluation/` 与 `.harness/observation/`，归根作用域的维护工作。它们是当前 Edges 实例采用的模块，不进入各作用域默认必建目录。

当前评测模块的执行器、用例、测试、报告与外部基准挂载一同纳入迁移，须同步适配仓根定位、submodule 路径、忽略规则及相关引用；已有局部维护上下文逐项处理，不因新物理层级自动建立新的责任作用域。当前观测目录只有说明和占位，迁移不意味着部署任何观测后端。评测迁移也不改变既有结果的证据边界。

## 通用约定与作用域特有目录

用户要求区分可用于各作用域的通用目录约定与某个作用域自己的扩展目录：当前通用部分有限，不能把 Edges 根目录的完整实例推广成每个作用域都应复制的模板。目录由哪个作用域拥有、承担领域工作还是维护工作，以及其约定是否可跨作用域复用，是分别判断的问题；作用域特有目录同样可以承担系统二职责。

通用约定不等于必建目录，可复用模块继续按需采用。局部扩展先由所属作用域说明职责，只有从实际使用中确认共性后，才通过架构复盘提炼为通用规范；不因目录出现过就宣布为通用模块，也不据此预设新的插件注册或安装机制。

通用默认推荐模块确定为 `memory`、`skills`、`tasks`，由用户按作用域需要选择，未采用的模块不预建目录。Edges 根实例另外采用 `evaluation`、`observation`，共五项；后两项当前属于实例扩展，其他作用域也可按需接入。推荐集合保持开放，不等于每层必建集合。

模块采用与内部类型选择分别处理：选用模块后按其内容契约组织；Memory 与 Skills 再选择各自所需 type。Task 的初始化与业务规则仍由任务模块负责，不交给 Project Memory 的类型初始化。新建时的推荐清单不用于补齐或重置已有项目，迁移保留已采用的模块与内容。

用户确认本次延续 Project Memory 的扩展设计，区分通用组织规则、按需扩展与作用域的具体目录实例。沿用 [ADR 0006](0006-extensible-project-memory-types.md) 的边界：具体 Memory Type 由本层 LAYOUT 登记，六类种子不是类型闭集，不另建全局类型注册表；复用入口、索引与稀疏递归的组织方式，补齐各模块保留自身内容契约时的统一发现能力。

已核对现有实现：类型扩展及只索引、忽略提交、技能格式等选项已落地；任意外部内容目录接入仍是预留接口，当前只有 agent_skills 的外部内容映射。Task 的状态与 Run、Evaluation 的用例与报告不能靠注册同名 Memory Type 自动获得接入。现有 init 仍创建六类种子，下面的选择式初始化是目标行为，尚未实现。

用户确认 Q11 采用推荐清单供选择：启用维护记忆时，提供少量默认推荐类型并说明用途，由用户选择需要的项，再按选择建立类型目录和入口；提供推荐项不等于默认创建全部类型。后续自定义类型继续沿用本层登记的扩展机制，最小通用结构不绑定一套必建分类。

默认推荐清单先沿用现有四类维护知识：上下文与决策（project）、纠正与反馈（feedback）、参考资料（reference）、本地私有记忆（user）。展示名不直接决定目录改名；Q7 已独立组织的技能正文与已安装技能发现索引不混入维护知识选项。原位 ADR 等材料保持单一真源，私有记忆的正文与类型索引一并忽略提交。具体选项与交互形态可在实施方案中细化。

## 统一发现，保留模块内容契约

目录树表达存放与归属，AGENTS.md 的入口引用图表达发现路径；引用可跨物理目录层级，二者不要求逐层对应。额外总览和快捷引用不改写正式作用域关系、正文真源或约束继承，普通维护记忆的类型入口仍保留。

用户于 2026-10-03 进一步明确：observation 的目标入口也使用 `AGENTS.md`；AGENTS 是人和 Agent 的统一组织与发现入口，README 仅为可选说明，不承担核心发现链的必经转接。Tasks、Evaluation、Observation 保留各自的业务索引；Memory、Skills 仍由作用域入口直达各 type，不补容器总入口。模块拥有 AGENTS 不自动形成独立作用域。

实施时须同步撤换根 AGENTS 中“README 是唯一真理源”的旧约定。现有有效规范按职责保持单一真源，由 AGENTS 发现；硬约束直接保留在所属层入口，其他正文可继续原位引用。保留已有 README 不意味着它是新作用域必建文件，也不要求把全部正文写进入口。

用户确认 Q6：各模块统一入口、归属与发现方式，同时保留各自的内容规则。Task 继续按任务契约管理状态和 Run 记录，Evaluation 继续组织用例与报告，维护记忆继续按其内容契约组织；统一组织不要求将全部对象改造成同一种 Memory 条目。

用户进一步确认 Q5.1：自身维护空间内保留独立的维护知识分组，用于接手与判断所需的上下文、决策、纠正和资料指针；任务推进、运行记录、评测证据仍由各自模块管理，可复用结论引用其来源。该分组记录的是其所服务作用域的维护知识，不因多一层目录就自动成为新的作用域。

整体目录确认后，维护知识分组采用 `memory/`；内部类型继续按需选择，技能容器与类型入口见下节。ADR 等工具约定文档遵循下文的路径兼容原则。保留分组不意味着整包照搬旧 `.memory/`，也不要求把原始记录复制成记忆；实际接入与索引适配仍需设计。

## 技能与维护知识分开组织

用户确认 Q7：现有 `.memory/skills` 中的可执行方法正文从维护知识分组中独立，作为能力模块组织。“可执行”指人或 Agent 能照着完成的步骤与工作流程，不要求方法本身是代码。维护知识保留采用方法的理由、背景与适用边界，通过引用关联相应技能；技能正文负责说明如何执行。

共享技能继续保留共享真源，各作用域通过引用或安装使用；本作用域沉淀的方法可在本地维护。用户提出并同意继续细化 skills 与 agent_skills 共用一份 AGENTS.md 的方向：此前讨论涉及本地方法与原位接入技能的共同发现入口。

用户随后明确：Skills 像 Memory 一样继续往下分 type，当前可保留对应旧 skills 与 agent_skills 目录的两类，每类各有 AGENTS.md，由最外层作用域 AGENTS.md 跨文件系统层级直接引用。本方案采用这一结构，并已确认新名为 managed（受管技能）与 referenced（引用技能）：合并物理容器，保留两类职责、各自索引与原来的正文维护规则，不另建技能总入口，也不将两类压成单一类型。目录归类不要求导航逐层中转，类型集合仍开放；自定义类型与来源权限保留，尚未实施。

## Skill 产物的路径契约

用户指出 ADR、`CONTEXT.md` 与部分 `docs/` 文档由其他 Skill 生成，其路径属于生产与消费流程的约定。已核对：domain-modeling 约定作用域的 `CONTEXT.md` 与 `docs/adr/`，并支持多个 context；brainstorming 与 writing-plans 分别默认写入 `docs/superpowers/specs/` 与 `docs/superpowers/plans/`，同时明确允许用户指定其他位置。应区分既有路径契约与可覆盖的默认值，不能只按内容语义搬迁文件。

用户确认 Q8：遵循已有 Skill 或工具约定保留产物真源，通过所属作用域的入口与索引接入维护体系，不另复制一份正文或同内容摘要。`.harness/` 表示默认维护目录，系统二承担的职责可以跨出该目录；承担维护职责不直接推导出文件必须移入其中。索引接入保留层入口、类型入口等已有分工，不要求所有正文直接挂在根入口。

路径约定可以演进；将来确需调整时，必须同时适配生成、读取、发现和引用关系。`docs/` 中不同职责的文档分别判断，不能将整个目录固定归为系统一或系统二。当前保留 `CONTEXT.md`、`docs/adr/` 与 `docs/superpowers/` 的约定位置，索引接入的具体实现仍待设计。

## 升级与一次性迁移

用户确认 Q12：本仓迁移时同步升级受影响的 CLI、Skill 和脚本，生成、读取、索引、部署与引用一起适配，以新目录为唯一真源，不保留继续写入的旧目录。公开命令的使用方式尽量保持，不借目录迁移扩大接口变更。

用户否决 Q13 的新工具兼容旧布局建议：新版常规运行只支持新布局，旧项目通过一键迁移 Skill 完成切换。迁移 Skill 是本次改造的交付内容；旧布局的读取与转换逻辑只用于迁移，不成为常规命令的旧路径回退或双布局读写能力。具体 Skill 名称可沿用 project-memory 系列，暂建议 `project-memory-migrate`。

通用迁移负责所选范围内 Project Memory 的布局转换：保留原作用域、正文和元数据；旧 skills 与 agent_skills 分别改名为 managed 与 referenced 后归入技能容器，保持原有职责与权限；自定义类型身份不随此改名而改变。迁移本地技能及其附属文件，重建索引和忽略规则；安装入口路径和外部真源保持原位，仅按明确迁移映射更新指向已迁本地正文的链接目标。迁移应在写入前汇总映射与冲突，正常的确定性转换一次完成；有内容冲突或无法确定的归属时不静默覆盖或猜测。私有记忆包含被 Git 忽略的正文和索引，不能仅从已跟踪文件枚举，目标路径须先建立忽略规则。

迁移后验证内容完整、入口和引用可达、私有忽略规则有效，保留本次操作的恢复依据；重复运行不得重复搬运或覆盖迁移后新增内容。既有类型按明确映射迁移，未确定的分类不自动改写；选择式初始化只用于新建，不在迁移时重置为推荐类型。

Edges 自身的任务归属重分、projects/teaching 上移、evaluation/observation 搬迁以及构建与发布适配，属于本实例的迁移计划。它可以调用通用迁移器，但通用 Skill 不内置 Edges 的业务目录和任务归属判断。2026-10-03 已实现 `project-memory-migrate` 与新版运行时；Edges 实例已按审阅归属清单在独立工作树完成迁移并通过针对性验证。该结果不代表其他克隆的 ignored 私有材料已经迁移，操作与诊断边界见[迁移指南](../recursive-layout-migration.md)。

## 取舍与边界

- 相比全局类型目录优先，作用域优先提高内容与上下文的局部完整性，但要求跨作用域的检索、任务看板和调用接口支持聚合；这些能力仍需设计和实现。
- Notes、Edges、Tasks 等继续保留各自语义。现有 Task Project 是看板分组，不等于项目工作区，迁移时不能仅按分组名称机械建立作用域。
- 自身维护空间按需建立，不要求每个普通目录都具有一套维护结构。维护空间是否成为独立递归作用域、其自身维护如何表达，仍需明确。
- 目录框架与分类入口已确认；旧内容的逐项归属、共享实现的接入适配及具体迁移清单留待实施计划细化；兼容边界已确定为新版只支持新布局，旧项目使用一次性迁移 Skill。
- 本决策保留上述目标结构与取舍；2026-10-03 当前实例已完成清单内内容迁移，保护文章与 submodule 指针保持不变，两个原有 referenced 技能来源缺失诊断仍保留。整仓最终验收与其他克隆的私有材料升级分别处理；`knowledge/posts/` 仍受不得由 AI 自动修改或移动的约束。
