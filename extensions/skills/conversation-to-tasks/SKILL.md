从对话整理任务：**成文 → 交人审 → 落库**（人审可以是对话确认或 PR）。正文顺序：**背景 → 目标**（必填）→ **动作** → **完成标准**（后两栏可选；完成标准可留到 `grill-with-docs` 后再补）。与 `conversation-to-notes` 主题行动指南同序（背景 → 问题/目标 → 方案/动作 → 验收/完成标准），便于从笔记开卡平移。四栏同构 STAR（Situation / Task / Action / Result）：用来**制定任务**，尤其是派给 agent 的 brief；**不要**拿 STAR 写复盘（复盘走 `conversation-to-notes`）。

先确定内容所属的作用域 `SCOPE`。一般这就是主体系统，任务写在 `<SCOPE>/.harness/tasks`。主体是仓库之外的虚拟系统一时，再加 `--super`，任务写在 `<SCOPE>/tasks`。Task Project 只是该看板的分组，不决定作用域。后续命令使用 `--scope "$SCOPE"`，只有虚拟系统一才加 `--super`。仓内维护 Edges 时显式选仓根，不要依赖执行命令时的源码目录。CLI 在 `extensions/cli`。

`tasks list` 的范围只由 `--scope`、`--super`、`--all` 决定。不传 `--all` 时，从当前主体做一次 traverse，顺着 `AGENTS.md` 的 children 走到任务。`--all` 从当前 `--scope` 走森林。最全的一次查询是 `edges --scope <仓库根> --super --all tasks list`。不要为了列出任务再读 README 的 `project-entries`，也不要把 README 上的链接抄进 `AGENTS.md`。

`edges tasks` 只改文件，不执行 Git。看板变更要进受保护的 `main` 时必须开 PR，不要直接 push `main`。对话里确认文案不等于可以直推。

## 步骤

1. **判是不是任务。** 对话里是否已有可接力的下一步？若实质是复盘或耐久结论，改派对应技能，停在这里。一条对话可以整理出多条、一条，或零条。
2. **只读去重（可选）。** 用 `edges --scope "$SCOPE" tasks list`（虚拟系统一再加 `--super`；要各系统一起看再加 `--all`）和 `get` 看开放任务。同一意图已有卡 → 在输出里建议更新该条，不要近义新建。
3. **必填门闩。** 自检 **背景、目标** 是否都能从对话里有依据地写出。任一不足 → **先提问**（可一次问多栏，但问题要具体），等用户想清楚再继续；不要用「无」占位，也不要替人编。**动作**、**完成标准**缺了不必追问；对话里已谈清做法时再写入动作，已有可核对验收条件时再写入完成标准，否则整栏省略，并在交人审时注明「完成标准待 grill-with-docs 补」。
4. **按模板成文。** 写出标题、简介建议与正文；字段怎么写见下方「各栏要点」与模板。再用 `edges --scope "$SCOPE" tasks project list`（虚拟系统一再加 `--super`）建议已有项目（不要自造短名，除非先问人）；默认状态待办（`backlog`）；未点名负责人则不写。
5. **交人审阅。** 交出标题、简介、正文、建议的项目与状态，供人过目；可说明「若落库大致会是哪条路径」。人审方式任选：对话里确认，或整段在分支上落库后提 PR 审。对话确认路径：确认前不要写盘，也不调用 `create` / `update` / `status`。若已有完成标准且需导出 `/goal` 一句契约，用「目标 + 完成标准」，必要时补上背景里的约束；完成标准仍缺则不要硬造 `/goal` 契约。
6. **落库。** 用 `edges --scope "$SCOPE" tasks create` 新建（虚拟系统一再加 `--super`），或对已有卡用 `update`（及必要时 `status`）；用户改了草稿则按改后的内容写。对话确认路径：确认后再写。写完的看板文件要进 `main`，必须开 PR 并回传链接；不要直接 push `main`。

## 各栏要点

简介用一两句说明要解决的问题与预期结果。正文区分可核对的事实、尚未验证的判断与候选做法：事实写入背景，假设明确标注，已确定的做法再写入动作；不要把设想写成已发生的事实。缺少信息时遵循上面的必填规则，不额外增加必填字段。

- **背景：** 给人读。核心是 **产生本任务的对话过程**（当时在谈什么、怎么落到开这张卡、中间改过什么主意），再用短句补现状、约束、预期收益、非目标、关联。不要只有出处标签；不要把待做步骤清单塞进背景。
- **目标：** 做成后的方向，一两句。写「做成什么样」，不写步骤。预期收益放背景（除非收益本身就是可测成功指标 → 有完成标准时写入完成标准）。
- **动作（可选）：** 对话里已谈清「怎么做」时再写。没有就整栏省略；不要编步骤，也不要用动作顶替完成标准。
- **完成标准（可选）：** 可勾选、可核对的验收条件；优先能被命令、检查或明确观察证伪。放在动作之后，对应「做完怎样算完」。这是循环工程与 `/goal` 的核心输入，**开卡时能写就写**；对话里还定不下来就整栏省略，留给后续 `grill-with-docs`（或等价细化）再补，不要为凑栏而编。

## 正文模板

```markdown
**背景：**
（先写产生本任务的对话过程：当时在谈什么、怎么落到要开这张卡、中间改过什么主意；用连贯短句，让没参与对话的人也能读懂。）
- 相关现状或已有约束（可核对）
- 预期收益或价值动机（如有）
- 非目标：…
- 关联：对话 / 拉取请求 / 笔记 / 兄弟卡 …

**目标：**
做成后要达到的方向（一两句；不写步骤）

**动作：**（可选；对话未谈清做法时整栏省略）
- …

**完成标准：**（可选；对话未定清或留待 grill-with-docs 时整栏省略）
- [ ] 可核对条件一（优先能用命令或明确观察验证）
- [ ] 可核对条件二
- [ ] …
```

开头如需总述，可在栏目前加一句「解决什么 + 做成后怎样」，但不要用它代替完成标准。

## 约束

- 输出用中文；栏名与说明都用中文，不要中英混写栏名。
- 写给人审阅，白话完整句；不添加对话里没有的新需求。
- 不要把复盘四栏或记忆结论塞进任务顶替背景；不写执行流水。

新建父级登记跟着主体系统走，`tasks` 上没有 `--index-group`，调用方不再选择 local 或 descendant。已有登记保留原分组。缺失 owner 不代为初始化。生成结构内部已有的固定组成关系由 Service 执行，不逐桶询问。遇到 `task-projects` 旧标记时，先对用户选定范围运行 `scripts/migrate-agents-indexes.mts --root /absolute/scope --check`，明确执行迁移才加 `--write`；普通命令不自动迁移。
