# 命令行审查要点

这些是审查命令行程序时要看的重点。只用于 `extensions/cli/` 里的改动，这个目录是仓库的命令行程序。其他目录不用下面这些条。

## 命令名跟文件夹走

顶层命令的名字要和仓库里对应的文件夹一致，例如笔记用 `notes`，技能用 `skills`，不要恢复 `note`、`skill` 或 `edges-note` 这类旧名字。旧名字一旦还能运行，调用方就会有两套入口，以后改一处就会漏掉另一处。

## 三种用法共用一套约定

终端里的命令、给助手读的技能说明（告诉助手何时以及怎样调用），以及没有终端时客户端所用的接口，要使用同一套参数和同一种结果。三种用法是并列的，不要只改命令行，也不要另写一套字段。

## 内容名单写在说明页

按类型整理的目录，名单写在该目录的 `README.md`（给人看的说明页）里。`AGENTS.md` 是这一层给助手用的系统入口，只登记维护信息，不要把内容名单放进去，否则人和助手会去不同的文件里找同一份名单。

## 写入要连登记一起改

`tasks create` 这类会新建或改动内容的命令，要同时写下内容文件，并在父目录的名单里登记，而且登记的位置要和读取时用的是同一处。只写文件不登记，列表里就看不到；登记到另一份文件，读和写会对不上。

## 给程序读的结果保持稳定

给程序读的成功结果要用 JSON（一种程序之间传递数据的文本格式），说明和报错不要混进这份结果。已经公开的参数名和结果里的字段名不要改，调用方是靠这些名字对接的。

## 行为变化要带测试

命令的行为或参数有变化时，同一改动里要有对应的测试，并且类型检查要通过。没有测试的约定，下次改命令时很容易被悄悄改坏。

## 不要让名字在编译时撞车

同一个父命令下面，每个命令名只能注册一次，也不要把已经废弃的旧名字再注册进去。命令的代码文件不要和同名目录里的入口文件抢同一个编译结果，否则程序在编译阶段就会起不来。
