# CLI 审查要点

这些是审查 CLI（`edges` 命令行）时要看的重点。只用于 `extensions/cli/` 里的改动。其他目录不用下面这些条。

## 命令名跟文件夹走

CLI 顶层命令的名字要和仓库里对应的文件夹一致，例如 `notes/` 用 `notes`，Skill 用 `skills`，不要恢复 `note`、`skill` 或 `edges-note` 这类旧名字。旧名字一旦还能运行，人和 Agent 就会有两套命令名，以后改一处就会漏掉另一处。

## 三个能力面共用一套领域契约

CLI、Skill（教 Agent 何时以及怎样调用的说明）和 MCP（在无 shell 宿主上暴露能力的机器入口）是并列的三个能力面，要共用同一套领域契约。不要只改 CLI，也不要给 Skill 或 MCP 另写一套旗标（命令上的参数，例如 `--title`）和结果字段。

## 类型入口写在组织清单

类型入口（某一 Memory Type 或 Skills 类型的索引）是组织清单，写在该目录的 `README.md` 里，组成登记用 `project-entries-*`。系统入口 `AGENTS.md` 只登记系统维护信息，不要把这份组成登记写进去，否则人和 Agent 会去不同的文件里找同一份登记。

## 写入要连组成登记一起改

`tasks create` 这类会新建或改动内容叶子的命令，要同时写下内容叶子，并更新父级的组成登记，而且写进去的位置要和读取时用的是同一处。只写文件不登记，组织清单里就看不到；把该进 `README.md` 的 `project-entries-*` 写进系统入口，读和写会对不上。

## 给人和 Agent 的结果保持稳定

CLI 成功时给人和 Agent 的结果要用 JSON（一种程序之间传递数据的文本格式），说明和报错不要混进这份结果。已经公开的旗标和结果里的字段名不要改，人和 Agent 是靠这些名字对接的。

## 行为变化要带测试

CLI 的行为或旗标有变化时，同一改动里要有对应的测试，并且类型检查要通过。没有测试的约定，下次改命令时很容易被悄悄改坏。

## 不要让名字在编译时撞车

同一个父命令下面，每个命令名只能注册一次，也不要把已经废弃的旧名字再注册进去。命令的代码文件不要和同名目录里的 `index.ts` 抢同一个编译结果，否则 CLI 在编译阶段就会起不来。
