# CLI 审查要点

这些是审查 CLI（`edges` 命令行）时要看的重点。只用于 `extensions/cli/` 里的改动。其他目录不用下面这些条。

## 

注意 Commands => Services => Domain 三层架构划分和调用顺序。保持层次界限清晰，高内聚低耦合。禁止跨层调用。

## 命令名跟文件夹走

CLI 顶层命令的名字要和仓库里对应的文件夹一致，例如 `notes/` 用 `notes`，Skill 用 `skills`。

## 三个能力面共用一套领域契约

CLI、Skill（教 Agent 何时以及怎样调用的说明）和 MCP（在无 shell 宿主上暴露能力的机器入口）是并列的三个能力面，要共用同一套领域契约。不要只改 CLI，也不要给 Skill 或 MCP 另写一套 flag（命令上的参数，例如 `--title`）和结果字段。

## 创建要连目录索引一起改

`tasks create` 这类会新建或改动内容叶子的命令，要在写内容叶子的同时，更新父级的目录清单。

## 给人和 Agent 的结果保持稳定

CLI 成功时给人和 Agent 的结果要用 JSON（一种程序之间传递数据的文本格式）。

## 行为变化要带测试

CLI 的行为或旗标有变化时，同一改动里要有对应的测试，并且类型检查要通过。

## 不要让名字在编译时撞车

同一个父命令下面，每个命令名只能注册一次，也不要把已经废弃的旧名字再注册进去。命令的代码文件不要和同名目录里的 `index.ts` 抢同一个编译结果，否则 CLI 在编译阶段就会起不来。
