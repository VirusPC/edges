## Prompt Caching 提示缓存机制

**来源**: @RLanceMartin 文章（经由 @shao__meng 分享）  
**收录时间**: 2026-03-01  
**标签**: `#llm` `#inference` `#optimization` `#kv-cache`

---

### 核心原理

LLM 生成分为两个阶段：

| 阶段 | 工作 | 特点 |
|------|------|------|
| **预填充阶段** | 一次性处理整个输入，计算每个 token 的 K/V 向量，形成 KV Cache | 计算量大，但高度可复用 |
| **解码阶段** | 逐 token 自回归生成，只处理新增内容 | 计算量小 |

**提示缓存的本质**：服务器端持久化 KV Cache。后续请求前缀完全一致时，直接加载缓存的 KV 张量，跳过预填充。

### 关键特性

- **精确前缀匹配**：一个字符、空格、大小写差异都会导致缓存失效
- **存储的是 KV 矩阵**（非原始文本），规模可达数百 MB 至 GB
- **TTL**: 默认 5 分钟不活动失效，命中后刷新；可选 1 小时长 TTL
- **最低门槛**: Sonnet/Haiku ≥ 1024 tokens，Opus ≥ 2048-4096 tokens

**计费规则**：
- 常规输入: $3.00/百万 tokens
- 缓存读取: $0.30/百万 tokens (**仅 10%**)
- 缓存写入: 1.25× (5min TTL) 或 2× (1hr TTL)

---

### 手动缓存 vs 自动缓存

#### 1. 手动缓存（传统）
在 Messages API 的 content block 中显式添加 `cache_control: {type: "ephemeral"}`，最多 4 个断点。

**要求**：静态内容（系统提示、工具定义）放最前面，动态对话历史放最后。

**痛点**：
- 多轮对话后手动维护断点繁琐
- 修改历史消息、插入时间戳、调整工具列表都会破坏前缀
- 很多 Agent 框架"以为"缓存了系统提示，实际因消息编辑每次都失效

#### 2. 自动缓存（新功能）
请求顶层添加 `"cache_control": {"type": "ephemeral"}`

系统自动：
- 将最后一个可缓存块作为断点
- 对话增长时断点自动向前滑动
- 兼容手动断点（共用 4 个槽位）

**优势**：解决"断点管理错误"这一行业普遍痛点

### Claude Code 团队 7 条黄金准则

> "缓存命中率下降就是生产事故（SEV），会触发严重告警" — @trq212

1. **前缀稳定第一**：静态内容（system、tools、CLAUDE.md）永远放最前
2. **动态信息用消息注入**：用 `<system-reminder>` 标签插入当前日期，而非修改系统提示
3. **工具列表锁定**：中途绝不增删，改用 `defer_loading` 占位 + 动态搜索
4. **模型中途切换 = 缓存失效**：需用子 Agent 隔离
5. **特性设计围绕缓存**：Plan 模式用额外工具而非配置开关
6. **压缩复用父前缀**：上下文超限时自动总结旧对话，但系统+工具前缀完全复用（压缩成本从 $0.09 降至 $0.009）
7. **日志监控**：每次调用检查 `cache_read_input_tokens` 和 `cache_creation_input_tokens`，读数为 0 即告警

---

### 关键洞察

- 缓存命中率直接影响成本和延迟，是生产级 Agent 的核心指标
- 自动缓存解决了大部分手动管理的痛点，但理解底层原理仍重要
- 很多框架"声称"支持缓存，实际因实现细节导致频繁失效
