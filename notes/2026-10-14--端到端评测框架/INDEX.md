# 端到端评测框架

# 目的

验证使用了 memory 之后，模型的回复效果有提升，进而证明整个系统在实际场景中的业务价值，因此需要思考实际业务开发场景下，端到端评测业务价值的方案。

端到端的评测实际上是对整个 Agent 系统的评测，解构来看就是“观测 + 评测”，观测是基石，因为有了观测，才可以拿到完整轨迹，进而才可以分析中间步骤、进行全面评测。

而**实际场景中对于业务价值的端到端评测**， 相比于 benchmark 的端到端评测，区别在于这两个问题：

1. **线上数据回流**：企业怎样选择真实用户数据、加工成评测任务、构造 Ground Truth、验证任务完成情况，并持续维护 Benchmark

2. **真实业务价值指标**：有哪些业务指标，企业怎样采集和计算用户采纳、代码保留、研发效率、返工和成本等指标，以及怎样证明某个 Agent 能力确实创造了增量价值

# 观测

有许多观测系统，可以使用 Langfuse。需要观测的不仅有最终回复，还需要看中间轨迹，**观测角度**包括：

- 结果层：业务指标、任务是否完成、输出是否可用

- 过程层：规划是否合理、步骤是否稳定

- 效率层：耗时、token、工具调用次数

- 安全层：是否越权、是否误操作、是否存在安全隐患

# 评测

在实际业务中评测 Agent 系统的能力，主要从以下三个**评测维度**出发

- 业务维度：面向用户，评估是否创造业务价值。比如代码保留率、用户对回复的满意度等

- 能力维度：是否完成用户任务、是否稳定运行。考虑任务完成率、一次成功率、交付可用率、规划合理率、Tool/Skill 调用成功率、纠错成功率

- 模型维度（暂不考虑评测，但可以作为模型选型参考）：基座模型能力是否足够支撑，考虑推理、指令遵循、检索、长文本处理、代码能力

在确定好需要评估哪些指标之后。就需要确定**评测方式**，目前主要分成两种评测方式，分别是客观评测和主观评测：

- 客观评测：强调规则清晰、可自动化大规模执行，评测准不准，测出下限，用 code-based grader。比如以下指标：

  - 是否调用正确的 tool/skill、工具调用参数是否正确、是否生成了符合结构的调用命令

  - 是否生成符合格式的结构化结果

- 主观评测：强调深度理解、全面评估，评测好不好，测出上限，用 model-based grader。比如以下指标：

  - 最终回复是否解决了用户问题

  - 任务规划是否合理

  - 输出是否具有业务可执行性

  - 交互体验是否自然、可信

- 如果上述两种评测都失败，人类评测都兜底，用 human graders

除此之外，还要注意**评测类型**，以上都是都是 capability eval，但是当系统更新之后，可能会出现原本做对但更新之后却错误的情况，因此还需要进行 regression eval，可以在原本一些 good case 上测试新版本是否出现了能力退化。

> - capability eval：测试系统能力
>
> - regression eval：测试系统相对于原先版本下出现了哪些能力退化

# 端到端评测系统设计

1. **评测对象的三层拆解**：参考 Qoder 的「记忆生成 / 记忆检索 / 记忆生效」三层划分。检索召回评测属于第二层，端到端业务价值评测必须补上第三层「生效」，看召回的记忆是否真正影响了 agent 的最终输出，而不仅仅是被检索到。

2. **选择对照组实验还是线上 AB 实验**：

  - 线上 AB 实验：事前把流量随机切成两组，A 组用旧系统（无 memory）、B 组用新系统（有 memory），两组同时服务真实用户，然后直接比较指标差异。Cursor 下线 Semantic Search、以及测试更贵模型做 Context Summarization 都是典型 AB。优势是**随机分流保证两组同质，差异可直接归因于系统**，统计分析简单；劣势是需要分流基础设施、A 组用户要承担更差体验、小流量跑不出显著性。

  - 对照组实验：所有用户都走同一个系统（memory 开启），事后根据 trace 把会话切片——比如「召回了 memory vs 没召回」「召回且生效 vs 召回但未生效」，再比较各组指标。Qoder 用的就是这种做法，再由模型判断记忆是否实际影响了当前输出。优势是不用搭分流、不用让一部分用户用「故意更差」的版本、还能回看历史数据；劣势是分组不是随机的，存在选择偏差（会触发 memory 的会话本身任务分布就可能不同），必须靠**场景分层 + 多指标验证**来对冲，Qoder 的做法是「按 Top 5 场景类别分组统计」。

  - 对于端到端评测系统初期的选择：早期阶段用户规模小、功能迭代快、memory 又是默认开启的产品特性，不方便让一部分用户完全没有 memory，所以**先用对照组实验做日常监控和快速迭代**，在场景内比较「召回且生效 vs 召回但未生效」，综合观察保留率、不满意率、Token、轮次及任务质量，权衡用户收益与成本，将结果作为监控和迭代线索。由于分组不是随机的，即使多个指标同方向改善，也不能据此证明 Memory 的增量价值。等有了分流能力、或者关键决策点（比如全量上线）**再跑一次线上 AB 收口**。

3. **核心指标分类 + 两个监控：**

有三类比较具体的企业实践：

  - Cursor、Qoder：评价用户后续行为，以及某项 Agent 能力的线上增量价值。

  - GitHub Copilot：通过 PR 生命周期和代码采纳行为建立研发业务指标体系。

总结它们的指标设计来看，可以将指标分层为：

  - **功能使用**：Memory 使用率、Agent 调用率。衡量用户或 Agent 是否使用该能力（Cursor、Qoder、GitHub）

  - **输出采纳**：Code Acceptance、Keep Rate。衡量产出是否被接受或持续保留（Cursor、Qoder、GitHub）

  - **用户反馈**：Dissatisfaction、Correction、Resolution。衡量用户是否认可、纠正或继续追问（Cursor、Langfuse）

  - **任务交付**：Task Success、PR Merged。衡量开发结果是否满足任务验收条件（CursorBench、GitHub、Harbor）

  - **研发效率**：Time to Merge、Review Cycles。衡量开发流程是否更快、更少反复（GitHub、METR）

  - **资源效率**：Token、工具调用、执行时间。衡量完成任务需要多少系统资源（Qoder、Ramp、Arize）

  - **监控侧**：Session Engagement（启用 memory 的会话中实际触发 memory 的比例）、Memory Effectiveness（召回的记忆中被判定真正影响输出的比例）（Qoder）

真实业务指标解决的是“价值如何被观察”，受控比较解决的是“价值变化能否归因于 Memory”。两者缺一不可，才能形成较强的证据。

**价值和成本必须一起看**：Cursor 曾测试更昂贵的模型做 Context Summarization，质量提升了但线上增益不足以抵消成本，这是只看质量会误判的典型反例。

**用户信号检测直接复用 Langfuse 模板**：Langfuse 的 Detect User Disagreement 以及 User Conversation Signal 已经提供七类开箱即用的 LLM-as-Judge 信号——Rephrase、Correction、Repeat、Error Quote、Frustration、Human Handoff、Success Confirmation。可以直接接入，不用自定义「不满意」rubric。

Benchmark 的 Resolved Rate 可以评价 Agent 是否成功解决预定义任务，但对于实际 Coding Agent 产品，企业还关注：**开发者有没有使用最终产出？是否减少了返工？是否缩短了从需求到交付的时间？付出的成本是否合理？**

4. **线上数据回流流程**：

  1. 采集：从线上收 bad case、沉淀 good case，从失败案例起步，选取 20-50 个案例

  2. 清洗：去重、聚类、补上下文、修复脏数据

  3. 评测：人工评测 + AI 评测，rubric 尽量二元化

  4. 质检：用「人人一致率」降低方差、「人机一致率」校准 rubric 是否可信（美团做法）

  5. 分析归因：定位问题，归因，形成回归任务

5. **配合 Langfuse 的两类 Annotation Queue**——异常触发队列（由用户反驳、相关性异常等自动指标触发）+ 随机抽样队列（即使没有触发任何异常也抽样人工审核），覆盖「用户没抱怨但其实答错了」的盲区。这对团队资产场景尤其关键，因为错误的经验被静默采用是最危险的。

6. **每次更新都要跑 Regression Eval**：Claude Code 2026-04 披露的三类质量问题就是没被原有内部 eval 捕获，先由用户反馈发现的。capability eval 之外必须有 regression eval，在**历史 good case 上测新版本是否出现能力退化**，防止新经验污染旧场景。

# 参考工作

1. 方案调研 [端到端评测方案调研](../2026-10-14--端到端评测方案调研/INDEX.md)

  - **样本质量可能比简单扩充样本数量更重要**：Microsoft 通过智能采样减少低价值和近重复数据；Langfuse 同时使用异常样本与随机样本；OpenAI 的代码评测审查则说明隐藏测试本身也可能存在大量问题。这些公开实践共同支持一个结论：**真实线上数据不能未经处理直接作为高可信评测集。**其中包括两个不同的质量问题：

    - 样本是否具有代表性。

    - Ground Truth 和 Grader 是否能够正确判断任务成功。

  - 最值得修正的是对“业务价值成立”的判断：benchmark的各个指标相互独立，但已有业务场景中指标之间可能存在真实的权衡。例如，复杂开发任务可能因为 Memory 提供了更多约束，导致执行 Token 上升，却减少后续人工返工。因此，**业务价值并不等于所有资源消耗指标都必须下降，而是要权衡产出质量、用户收益和成本之间的关系。**
