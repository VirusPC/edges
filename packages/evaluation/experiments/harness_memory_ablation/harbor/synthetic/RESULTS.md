# 合成实验结论：区分了检索成本，召回率仍有天花板

在这套已冻结的合成场景中，**分层（scoped：按目录层级放记忆 + 发现索引）与平铺（root：全部放根目录）的 recall@5 均为 100%，分层没有显示召回优势；分层的平均总 token 少 35.75%，未缓存输入少 37.05%，Agent 时延短 15.87%**。因此这版数据具有资源开销方面的区分度，在当前模型和 180 秒预算下没有区分两组的检索质量。不能把这一结果写成真实场景整体收益已被证明。

正式 test 为 32 题 × 3 条件 × 3 次，共 **288/288 成功、零失败**；固定 12 路并发，整批 **28.31 分钟**，累计 **22,357,944 token**（含缓存输入，不含 dev）。此前 8 题的 24 次 dev 仅做执行与计量验收，没有据其分数修改测试题、标准答案记忆、seed 或并发。

### 观察：为什么检索目标在根目录时差距最大

表里的「少用」是两组之间的差距，不是各自的绝对开销。检索目标在当前工作目录时，问题点名了业务，平铺组可以按业务名把对应文件从一大堆里挑出来（词法基线在这类题上也是满分），所以平铺组只多查约 1.5 次（4.2 对 2.7）。检索目标在根目录时，要找的是根目录里的「统一行政约定」（归档规则、通知时限），存放位置和业务自己的目录无关；问题虽然写了业务名，但「归档」「通知」这些主题词同样指向根目录里其他业务的同类规则。分层组只需看根目录（10 个文件；4 题中有 2 题本来就从根目录出发），平均查 1.8 次；平铺组面对的是混在一起的 586 个文件，目标规则旁边还有 8 条其他业务的同名规则（归档规则、通知时限各 4 条），平均查 4.5 次。词法基线在这类题上 recall@5 只有 0.5：前 5 被 5 条「通知时限约定」占满，归档规则全部漏掉。可见问题里越缺少能直接定位的词，按目录分层的帮助越大。这一组只有 4 题，55% 这个数字还不稳定。

## 这次检验了什么

这套数据让所在目录、覆盖关系和时间条件明确，加入大量同名与过期规则，扩大了目录发现的开销差异；同时保留涉及另一个业务、目标在根目录及无检索目标的题作为控制。检索目标全在当前工作目录的题，词法基线本身就可满分；涉及另一个业务目录和目标在根目录的题，存在词法与结构 oracle 的差距，但 gpt-6.1-sol 在本轮预算内仍全部检索命中。**离线基线能区分构念，不等于模型质量一定被区分。**

平铺与分层得到同一批正文、所在目录和时间元信息；差异同时包含放置位置与发现索引。本轮支持的是这套具体导航协议在受控合成场景中的资源差异，不能单独归因于目录深度，也不是与所有经过检索过滤优化的扁平方案比较。工具轮次较少与资源降低同时出现，但没有通过额外消融验证机制；分层的平均正文暴露记忆数反而略高（6.84 对 6.30），不能解释成简单的“少读文件”。

此前[真实历史问题实验](../../../../reports/2026-11-09-harbor-memory-ablation.md)有 31 题，明确不在根目录的题仅 6 道；整体 recall、token 和时延差异区间均跨零。新合成集不在根目录的题更多、语料更大且每题应检索的记忆更少，是另一种受控分布；本次结果不替代或改写真实实验结论，也没有把两批题混合计算。

所有实体与事实均由程序生成；dev/test 实体隔离，但共享模板和解析规则，不代表未知任务模板或真实任务总体的泛化。仅使用一个模型别名、一个配置和一次固定矩阵；提供方缓存没有隔离，总 token 包括缓存输入，不是按价格计算的费用。12 路并发下的原生 Agent 时延含共享资源与提供方调度影响，不能等同独立执行时延或纯文件系统耗时。

若后续目标是区分检索质量，需要另立更严格预算或更复杂任务的协议及新数据版本，保留本版作为成本诊断；不能在看过本次 test 后修改本版，再继续称其为未见测试。
