Agent、Task、Crew、Flow：四层是怎么套在一起的

One mental model: who works, on what, as a team, inside which workflow.

本课唯一目标：读完后，你能用自己的话讲清楚两件事——

  1. 一个 Task 的输出是怎样流到下一个 Task 的；
  2. Flow 在 Crew 之上多加了什么。

应你的反馈：下面在每个概念旁附了很短的官方片段，方便建立体感。它们不是作业——不用安装、不用敲、不用跑；读懂字段名即可。

1. 先看总图

官方 Introduction · The CrewAI Architecture 把 CrewAI 分成两层：Flow 是骨架（backbone），负责步骤、逻辑和数据怎么在系统里移动； Crew 是干活的团队（intelligence），在 Flow 的某一步里被触发，去解决需要协作与自主性的复杂问题。 再往下一层，Crew 由若干 Agent（谁来做）和若干 Task（做什么）组成， 并按一种 Process（怎么排班）执行 （Crews · Crew Attributes）。

2. Agent：谁来做

Agents 页把 Agent 定义为一个“自主单元”：能执行任务、依据自己的 role 和 goal 做决策、使用工具、与其他 Agent 协作。 最核心的三个字段是“人设”：

  • role：在团队里的职能与专长；
  • goal：指导它做决策的个人目标；
  • backstory：给它背景和性格，丰富交互。

另外两个常见字段：tools（它能调用的能力，默认为空列表）和 llm（驱动它的语言模型） （Agent Attributes）。

文档里 llm 标为 optional，默认取 OPENAI_MODEL_NAME 或 "gpt-4"；但 JSON-first 教程里每个 Agent 都显式写了 "llm": "provider/model-id"（First Crew · Step 2）。

新项目里，每个 Agent 是一个文件 agents/<name>.jsonc，文件名就是在 crew.jsonc 里引用它的名字 （Agents · JSONC Configuration (Recommended)）。

3. Task：做什么，以及数据怎么往下传

Tasks 页说：Task 是由一个 Agent 完成的具体任务。 在 crew.jsonc 里，每个 Task 必须有 description 和 expected_output， agent 要对应 agents 列表里的某个名字 （Tasks · JSONC Configuration）。

  • description：这件事是什么；
  • expected_output：做完长什么样（交付物的规格）；
  • agent：派给谁；
  • context：要读取哪些前序 Task 的输出。

本课重点：Task → Task 的数据流

两条规则，都来自官方文档：

  1. 默认接力。在 sequential 流程中，Task 按列表顺序执行，“一个 Task 的输出作为下一个 Task 的上下文” （Processes · Sequential Process； 另见 Tasks · Referring to Other Tasks：“the output of one task is automatically relayed into the next one”）。
  2. 显式指定。用 context 列出前序 Task 的名字，就能精确指定读哪些（可以多个、可以不是紧挨着的上一个）。 JSON 里 context 只能引用之前的 Task，向前引用会被拒绝，“so sequential context stays explicit” （Tasks · JSONC）。

官方教程里的例子：analysis_task 写了 "context": ["research_task"]，于是 analyst 拿到 researcher 的研究结果，再写出 output/report.md （First Crew · Step 3、How It Works）。

我的类比（非官方说法）：context 像是“Task 级别的显式消息传递”——下游 Task 声明自己依赖哪些上游输出，而不是去一个共享记忆里自己找。这和你熟悉的 agent memory 是两回事；CrewAI 另有 memory 机制，以后单独讲。

还有一个“入口”数据：{topic} 这类占位符，由 crew.jsonc 顶层的 inputs 提供默认值，缺了 crewai run 会提示你填 （First Crew · Step 3）。 所以数据流可以概括为：inputs 填进占位符 → Task 1 产出 → 经 context 交给 Task 2 → 最后一个 Task 的输出（或 output_file）就是 Crew 的结果。

4. Crew 与 Process：怎么排班

Crew 是“一组协作的 Agent，一起完成一组 Task”，并定义执行策略 （Crews · Overview）。 关键字段是 agents、tasks 和 process，process 默认为 sequential （Crew Attributes）。 Processes 只有两种：

Process谁决定谁做什么要点
sequential你在 tasks 列表里预先排好，每个 Task 已指定 agent按顺序执行，前一个的输出做后一个的上下文
hierarchical一个 manager（经理）AgentTask 不预先分配；经理按能力分派、审核产出、判断是否完成。必须提供 manager_llm 或 manager_agent（Hierarchical Process）

5. Flow：在 Crew 之上多了什么

Flows 页：Flow 用来构建结构化、事件驱动的工作流，连接多个步骤、管理 state、控制执行流向。 Introduction 列出 Flow 提供的三样东西：State Management（跨步骤、跨执行持久化数据）、Event-Driven Execution（由事件或外部输入触发）、Control Flow（条件、循环、分支） （Introduction · Flows: The Backbone）。

  • @start() 标记入口步骤；@listen(x) 标记“当 x 产出输出时执行我”，并且能把 x 的输出当参数拿到 （Flows · Getting Started）。
  • self.state 是步骤之间共享的数据；可以是 dict，也可以是 Pydantic 模型（结构化 state） （Flow State Management）。@persist 能让 state 在重启之后保留（Flow Persistence）。
  • Crew 跑在 Flow 的某一步里：Quickstart 中 run_research 这一步调用 crew.kickoff(inputs={"topic": self.state.topic})，再把 result.raw 写回 self.state.report （Quickstart · How this run fits together；Flows · Adding Crews to Flows）。
对比一下两种“传数据”：Crew 内部 Task 之间靠 context；Flow 的步骤之间靠 @listen 的返回值和 self.state。Crew 的结果要进入 Flow，需要那一步把它写进 state 或 return 出去。

一句话：Crew 解决“一群 Agent 怎样协作完成一组 Task”；Flow 解决“整个应用分哪几步、按什么事件和条件推进、数据存在哪里”。 Introduction 的建议很直接：“For any production-ready application, start with a Flow”——用 Flow 定义整体结构、state 和逻辑，在需要自主协作的那一步里放一个 Crew （When to Use Crews vs. Flows）。

6. 两个“当前文档”事实（已核实）

  • JSON-first：新建 crew 项目（crewai create crew <name>）默认是 agents/*.jsonc + crew.jsonc，crewai run 直接加载；旧的 crew.py + config/*.yaml 布局需要加 --classic （First Crew · Step 1；Crews · JSONC (Recommended)）。网上很多旧教程是 YAML 写法，读的时候要知道它是 classic。
  • 生产推荐 Flow：Quickstart 原话 “Flows are the recommended way to structure production apps”（Quickstart），与 Introduction 的 “start with a Flow” 一致。
一个小不一致：Flows 页说 crewai create flow 生成的示例 crew（poem_crew）仍是 classic YAML 布局；Quickstart 则描述生成 crews/content_crew/ 并让你替换成 JSONC。概念上不影响，写代码时以实际生成结果为准。

8. 小测（检索练习）

点击选项即判定，每题只能作答一次；选项顺序随机。“重做”可清空重来。

Agent 的三个“人设”核心字段是哪一组？

  1. role、goal、backstory
  2. name、prompt、persona
  3. role、model、memory
  4. task、tools、process
Agent Attributes 表里前三项就是 role（职能）、goal（目标）、backstory（背景）；tools 和 llm 是另外的可选字段。见 Agents · Agent Attributes。

在 crew.jsonc 里，每个 Task 必须包含哪两个字段？

  1. description 与 output_pydantic
  2. expected_output 与 output_file
  3. description 与 expected_output
  4. human_input 与 output_pydantic
原文：“Each task must include description and expected_output.” 其余字段都是可选的。见 Tasks · JSONC Configuration。

Build Your First Crew 里，analysis_task 是如何明确拿到 research_task 输出的？

  1. 在 backstory 中预写入上步结果
  2. 在 context 中列出前序任务名
  3. 由 memory 自动检索之前输出
  4. 靠 inputs 占位符传上步结果
"context": ["research_task"]——context 指向前序 Task 的名字，analyst 因此收到研究结果。inputs 只负责填 {topic} 这类占位符的初始值。见 First Crew · Step 3。

hierarchical Process 和 sequential 最关键的区别是？

  1. 所有任务同时并行执行而不分先后
  2. 每个任务都必须先经人类逐条确认
  3. 只允许一个智能体去完成全部任务
  4. 由经理智能体分派任务并审核产出
hierarchical 中 Task 不预先分配，由 manager Agent（需 manager_llm 或 manager_agent）按能力分派、审核输出、判断完成。见 Processes · Hierarchical Process。

相比单独运行一个 Crew，Flow 主要额外提供了什么？

  1. 更多智能体角色与更长的背景故事
  2. 跨步骤的状态与事件驱动执行控制
  3. 把每个任务的输出自动保存为文件
  4. 让智能体自动选择最合适的大模型
Flow 提供 State Management、Event-Driven Execution 和 Control Flow（条件/循环/分支）。保存文件是 Task 的 output_file，与 Flow 无关。见 Introduction · Flows: The Backbone。

在官方 Quickstart 里，Crew 是在哪里被启动（kickoff）的？

  1. 在研究员智能体的背景故事字段里
  2. 在第二个任务的上下文依赖列表里
  3. 在一个被上一步触发的流程步骤里
  4. 在团队配置文件的默认输入对象里
run_research 用 @listen(prepare_topic) 标记，在 prepare_topic 完成后执行，在其中调用 crew 的 kickoff，并把 result.raw 写回 self.state.report。见 Quickstart · How this run fits together。
