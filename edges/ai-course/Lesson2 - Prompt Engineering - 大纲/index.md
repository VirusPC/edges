# Lesson2：提示词工程

> **目标**：理解 Prompt 如何影响模型行为，掌握 In-Context Learning 的底层机制，建立从问题定义到落地验收的系统化工程方法。

---

## 第一部分：从概率到确定性——Prompt 工程的本质

### 1.1 模型输出的不确定性从何而来

- 回顾 Lesson1：模型本质是"下一个 token 的概率分布预测器"
- Prompt 工程的核心挑战：如何让概率分布收敛到期望输出
- 四种收敛手段的底层逻辑：
  - 上下文约束（缩小可能性空间）
  - 示例引导（调整概率分布形状）
  - 结构化格式（锁定输出模式）
  - 推理链（COT）（延长思考路径，降低单步错误率）

### 1.2 In-Context Learning 的前沿研究解读

**核心问题**：模型是在"识别任务模式"还是"现场学习任务"？

- 前沿论文观点对比：
  - Task Recognition（模式匹配）：示例激活预训练中已见过的知识
  - Task Learning（上下文学习）：模型在推理时调整内部表示
- **工程启示**：
  - 示例数量的边际收益曲线（3-5 个通常最优，之后递减）
  - 示例质量 > 示例数量（相似度、多样性、错误案例的价值）
  - 示例顺序的影响（Recency Bias + Lost in the Middle）

### 1.3 常见反模式与失败机制

| 反模式         | 表现                       | 根本原因               | 修复方向         |
| ----------- | ------------------------ | ------------------ | ------------ |
| 过度拟人化       | "你是资深工程师，请认真思考..."       | 模型没有"态度"，只有概率分布    | 删除情感化表达，直接描述任务 |
| 角色宽泛        | "你是全能助手"                 | 缺乏约束，输出空间过大        | 具体化身份与边界     |
| 指令模糊        | "生成好的代码"                 | "好"无法量化           | 明确验收标准       |
| 矛盾约束        | "简洁但详细"                  | 模型无法解决冲突           | 分阶段或分任务拆解    |
| 示例过多 / 示例低质 | 10+ 个示例但效果不升反降           | 噪声掩盖信号 + 上下文过载    | 精选 3-5 个高质量示例 |
| 过度依赖 COT    | 简单任务也让模型"think step by step" | 浪费 output token 成本 | 按复杂度分层       |

## 第二部分：核心技术与成本模型

### 2.1 技术选型决策树

**问题**：给定一个任务，该用哪种 Prompt 策略？

| 技术              | 底层机制           | 适用场景       | 成本        | 典型失败点           |
| --------------- | -------------- | ---------- | --------- | --------------- |
| Zero-Shot       | 依赖预训练知识        | 通用简单任务     | 低（仅 input） | 任务超出预训练分布       |
| Few-Shot        | ICL 模式识别       | 格式化、分类、抽取  | 中（示例占 input） | 示例质量低 / 示例与任务不匹配 |
| COT             | 延长推理路径，降低单步错误  | 多步推理、数学、代码 | 高（output 长） | 简单任务浪费成本 / 推理漂移  |
| ReAct           | 交替推理与工具调用      | 需要实时信息 / 动作 | 高（多轮 + tools） | 工具调用失败未兜底       |
| RAG             | 外部知识注入         | 事实准确性、私有知识 | 中（检索 + input） | 检索质量差 / 上下文过载    |
| Prompt Chaining | 多阶段分治          | 复杂流程       | 中（多次调用）   | 中间步骤失败传导        |

**决策流程**：
```
任务复杂度 → 是否需要外部知识 → 是否需要推理链 → 是否需要工具调用 → 选择技术组合
```

### 2.2 成本量化与优化策略

#### 成本公式（来自 Lesson1）
```
总成本 = (Input × $input + Output × $output) × 调用次数
```

**Few-Shot 的成本-质量权衡**：
- 示例数从 0 → 3：质量跃升明显
- 示例数从 3 → 5：边际收益递减
- 示例数 > 5：成本线性增长，质量提升不明显甚至下降

**缓存优化（结合 Lesson1 的 Prompt Cache）**：
- System Prompt + Few-Shot 示例放在固定前缀 → 缓存命中后成本降 90%
- 动态内容（用户输入）放在后面
- **工程启示**：高频调用场景优先设计缓存友好的 Prompt 结构

### 2.3 结构化输出工程

**问题**：为什么 JSON Schema 比自然语言描述更可靠？

- 自然语言约束是"软提示"，模型可能偏离
- JSON Schema / Function Calling 是"硬约束"，部分 API 在解码层强制格式
- **工程实践**：
  - OpenAI Function Calling / Anthropic Tool Use 的协议差异
  - 格式验证 + 重试策略（最多 3 次，超过则降级为自然语言解析）
  - 错误处理：模型返回格式错误时，如何提取有用信息而非直接拒绝

## 第三部分：System Prompt 工程——从分层设计到缓存优化

### 3.1 分层架构与信息密度

**设计原则**：从抽象到具体，从全局到局部

```
1. 身份定义（谁）：角色 + 专业领域 + 核心能力边界
2. 工具资源（有什么）：可调用工具 + 外部数据源 + 权限边界
3. 行为约束（不做什么）：NEVER/ALWAYS 硬约束 + 优先级冲突解决规则
4. 输出格式（怎么输出）：结构化模板 + 验收标准
5. 示例（怎么做对）：3-5 个高质量 Few-Shot 示例
```

**工程视角**：
- 分层的好处：模块化、可测试、可迭代
- 信息密度控制：每个部分不超过 200 tokens（参考 Lesson1 的"分块产生信号"）

### 3.2 前沿实践：解析主流 Coding Agent 的 System Prompt

**案例分析对象**：Claude Code、Cursor、Copilot 的 System Prompt 设计

**共性规律**：
1. **工具描述设计**：JSON Schema + 使用示例 + 错误处理提示
2. **安全约束表达**：NEVER 列表（禁止操作）+ ALWAYS 列表（必须检查）
3. **反过度工程**：避免过度细节导致上下文过载
4. **失败模式预判**：提前告知常见错误（如"不要硬编码路径"）

**前沿趋势（2024-2025）**：
- Constitutional AI 式的约束表达（原则而非规则）
- Prompt Compression 技术（LLMLingua）在长 System Prompt 中的应用
- Multi-turn System Prompt（根据对话阶段动态调整）

### 3.3 System Prompt 与 KV Cache 的关系

**打通 Lesson1 的底层机制**：
- System Prompt = 固定前缀 → Prefill 一次，后续请求复用 KV Cache
- 缓存命中条件：前缀完全一致（字符级匹配）
- **工程决策**：
  - 高频场景：投入更多 tokens 在 System Prompt，换取后续降本
  - 低频场景：简化 System Prompt，减少首次 Prefill 开销
- 衔接 Lesson3：完整上下文 = System + History + Tool Output + User Input

## 第四部分：场景化 Prompt 模板与参数配置

### 4.1 代码场景的 Prompt 策略矩阵

| 场景       | Prompt 策略           | temperature | 关键约束          | 典型失败模式        | 验收指标        |
| -------- | ------------------- | ----------- | ------------- | ------------- | ----------- |
| 代码生成     | Zero-shot + 格式约束    | 0.2         | 完整可运行 + 依赖声明  | 幻觉 API / 语法错误 | 可编译率 > 90%  |
| 代码审查     | Few-shot (3个示例) + COT | 0.1         | 按严重程度分类 + 引用行号 | 漏检 / 误报过多    | F1-score    |
| 方案设计     | COT + Multi-turn    | 0.7         | 多方案对比 + 权衡分析  | 方案单一 / 缺少边界讨论 | 人工评审 + 覆盖度  |
| 测试生成     | Few-shot + 边界提示     | 0.3         | 覆盖边界 + 独立可运行  | 只覆盖 happy path | 分支覆盖率 > 80% |
| Bug 修复   | RAG (相关代码) + COT   | 0.2         | 最小改动 + 回归测试通过 | 过度重构 / 引入新 bug | 测试通过率      |
| 文档生成     | Zero-shot + 模板      | 0.4         | 结构化 + 代码同步    | 过时 / 与代码不一致   | 人工抽检        |

**参数配置原则（结合 Lesson1 的采样机制）**：
- temperature：确定性任务 ≤ 0.3，创意任务 ≥ 0.7
- max_tokens：代码生成类设上限（避免无限循环输出），对话类留余量
- top_p / top_k：大多数情况默认即可，除非需要极端确定性（top_p=0.1）

### 4.2 Prompt 模板库（开箱即用）

**设计思路**：提供"可 fork 的起点"，而非"必须遵守的教条"

- 模板 1：结构化数据提取（JSON 输出）
- 模板 2：多步推理任务（COT）
- 模板 3：工具调用型 Agent（ReAct）
- 模板 4：代码审查（Few-shot + 严重程度分类）
- 模板 5：批量任务处理（Prompt Chaining）

**每个模板包含**：
- 适用场景描述
- 完整 Prompt 示例
- 常见失败案例 + 修复方向
- 成本与延迟参考值

## 第五部分：评估、迭代与失败模式分析

### 5.1 评估方法论

**分层评估体系**：

| 层级   | 指标类型   | 具体指标                       | 工具 / 方法              | 适用阶段   |
| ---- | ------ | -------------------------- | -------------------- | ------ |
| 输出质量 | 客观指标   | 准确率、F1、BLEU、代码可编译率        | 自动化测试                | 开发 / 回归 |
| 输出质量 | 主观指标   | 人工评分、LLM-as-Judge         | PromptFoo / LangSmith | 开发     |
| 系统性能 | 延迟     | TTFT、P95、P99              | APM 监控               | 生产     |
| 经济性  | 成本     | 单任务成本、月度总成本                | 日志分析                 | 生产     |
| 稳定性  | 格式合规率  | JSON 解析成功率、Tool Call 成功率   | 自动化验证                | 开发 / 生产 |
| 安全性  | 拒答率 / 越狱率 | Prompt Injection 防御成功率 | Red Team 测试          | 上线前    |

**LLM-as-Judge 的适用场景与陷阱**：
- 适用：主观任务（文风、创意）、快速迭代阶段
- 不适用：事实准确性（Judge 也会幻觉）、需要严格可复现的场景
- 最佳实践：LLM-as-Judge + 人工抽检（10-20% 样本）

**A/B 测试设计清单**：
- 控制变量：只改一个维度（示例数量 / 示例顺序 / temperature）
- 样本量：至少 50+ 样本才有统计意义
- 统计显著性：用 t-test / 卡方检验，而非"感觉更好"

### 5.2 迭代流程与失败模式分析

**迭代闭环**：
```
1. 定义任务 + 验收标准
   ↓
2. 初始 Prompt（参考模板库）
   ↓
3. 执行 20-50 个测试样本
   ↓
4. 分析失败模式（分类统计）
   ↓
5. 针对性修改（一次改一个维度）
   ↓
6. 回归验证（确保未引入新问题）
   ↓
7. 固定版本 + 监控上线
```

**常见失败模式分类与修复**：

| 失败模式  | 表现                  | 根本原因          | 修复方向               | 优先级  |
| ----- | ------------------- | ------------- | ------------------ | ---- |
| 输出过载  | 输出冗长、偏离主题           | 缺少长度约束 / 任务边界模糊 | 加 max_tokens / 明确输出范围 | 高    |
| 指令漂移  | 多轮对话后偏离初始指令         | 上下文累积 / 权重稀释   | 定期重申约束 / 简化历史     | 中    |
| 格式错误  | JSON 解析失败 / 字段缺失     | 示例不够 / 约束不明确   | 补充示例 / 用 Schema 强制 | 高    |
| 幻觉    | 编造事实 / 不存在的 API     | 缺少知识 / 过度自信    | RAG / 降低 temperature  | 高    |
| 拒答过度  | 安全约束下拒绝合理请求         | 约束过严          | 放宽边界 / 增加澄清机制      | 中    |
| 性能退化  | 之前正确的 case 突然失败     | Prompt 改动副作用    | 回归测试 / 版本管理        | 高    |
| 成本失控  | 单次调用成本超预期           | 输出过长 / 多轮浪费    | 控制 output / 路由优化    | 中    |

### 5.3 前沿工具与自动化

**Prompt 工程工具链（2024-2025）**：
- **开发阶段**：PromptFoo（A/B 测试）、LangSmith（trace + 评估）
- **生产监控**：LangFuse（可观测性）、Helicone（成本分析）
- **安全测试**：Garak（Prompt Injection 检测）、Red Team 平台
- **Prompt 优化**：DSPy（自动化 Prompt 优化）、Prompt Perfect（压缩 + 改写）

**自动化评估示例流程**：
```python

for prompt in prompts:
    results = evaluate(prompt, test_suite, metrics=["accuracy", "f1", "cost"])
    if results.accuracy > 0.9 and results.cost < threshold:
        deploy(prompt)
```

## 核心要点

1. **本质认知**：Prompt 工程是"收敛概率分布"的系统化方法，不是"调参艺术"
2. **ICL 机制**：示例质量 > 数量，3-5 个通常最优（边际收益曲线）
3. **成本意识**：Output token 贵 3-5 倍，缓存可降 90%（System Prompt 设计要考虑缓存）
4. **分层设计**：身份 → 工具 → 约束 → 格式 → 示例（信息密度控制，每块 < 200 tokens）
5. **评估闭环**：定义验收标准 → 执行 → 失败分析 → 针对性修改 → 回归验证
6. **前沿趋势**：Constitutional AI、Prompt Compression、Multi-turn System Prompt
