# Lesson 1 故事线大纲

## 核心逻辑
- 故事来自开发 AI CR Agent 过程中的真实困惑，不是为章节配例子
- Part 1 用 `"请 review 这段代码"` 作贯穿示例，建立基础直觉；子节通过 CR 场景回扣工程含义
- Parts 2–5 每个 Part 开头锚定一个开发过程中真实遇到的问题，章节内容是解答；子节在工程视角末尾简短回扣 CR 场景
- Part 6 纯动手，开头点出本地部署对 CR 合规场景的意义
- 视角：全程"你"

---

## 开场白
*插入位置：核心主线图之后*

你搭了一个 AI CR 工具，在 PR 合并前自动 review 代码。

跑了一段时间之后，几件事让你想搞清楚——它为什么会漏掉某些 bug？它为什么对你们自己定义的 API 总是说错？它为什么每次都要等一下才开始出字，但追问却快了很多？

这节课就跟着这些问题，把大模型拆开来看清楚。


## 第一部分：模型架构
*开头钩子：先不急着回答那些问题。在搞清楚"为什么"之前，先跟着一条请求进模型走一遍。就用这一条：「请 review 这段代码」*

- 1.1 统一范式 → CR 场景对比：传统静态分析 vs LLM 统一范式
- 1.2 Tokenizer → CR 回扣：PR diff 中空行/缩进的隐形 token 消耗，diff 预处理降本
- 1.3 Embedding → CR 回扣：用 Embedding 检索团队历史 review 经验作为 CR 上下文
- 1.4 Attention → CR 回扣：Lost in Middle——长文件 CR 中间部分问题易被漏掉
- 1.5 Transformer → CR 回扣：小模型抓语法问题，大模型才能发现跨函数逻辑漏洞


## 第二部分：训练机制
*开头钩子：AI CR 上线没多久，你发现了一个规律：它对标准库的用法很准，但对你们自己定义的工具函数经常说错。*

- 2.1 预训练 → CR 回扣：为什么懂 try-catch 但不懂你的自定义注解——预训练数据里没有
- 2.2.1 CPT → 已隐含：Coder 模型为什么比通用模型 CR 效果好
- 2.2.2 SFT → CR 回扣：工具调用微调让 CR 工具能调 linter、返回结构化结果
- 2.2.3 Alignment → CR 回扣：Alignment Tax 导致 review 结论保守（"建议考虑"而非"这里有 bug"）
- 2.3 工程视角 → CR 回扣：15 度夹角——CI 集成、规范定制、评估体系是不会被模型内化的 CR 工程


## 第三部分：推理机制
*开头钩子：还有一件事你一直没搞清楚——每次发出请求，都要等一下才开始出字；但同一个 PR 里追问，第二个问题明显快了。这不是网络抖动。*

- 3.1 Prefill/Decode → 已由开头钩子覆盖
- 3.2 KV Cache → CR 回扣：同 PR 追问更快的原因；prompt 前缀设计（规范在前、diff 在后）最大化缓存命中
- 3.3 加速与降本 → CR 回扣：Batch API 打包 CR 请求享 50% 折扣，CR 不需要实时响应


## 第四部分：模型选型
*开头钩子：工具跑了一段时间，你开始认真想这个问题——现在用的模型是当时随手选的。专门的 Coder 模型和现在用的差在哪？有没有更合适、更划算的选择？*

- 4.1 为什么不直接用最强 → CR 回扣：约束排除先行（数据合规、高频成本）
- 4.2 判断维度 → CR 回扣：路由策略——Haiku 扫风格 + Sonnet/Opus 审逻辑，降本 60%+
- 4.3 实践三步 → 已隐含：选型流程直接适用于 CR 工具选模型


## 第五部分：参数配置
*开头钩子：模型选定了，但还有两件具体的事没解决——review 结论有时太模糊，有时又跑去讨论和当前 PR 无关的问题；开了推理模式之后，某几次账单比预期高出不少。这是参数的问题。*

- 5.1 temperature → CR 回扣：推荐 0.1–0.3，避免结论不一致或模板化；可复现需加 seed
- 5.2 max_tokens/stop → CR 回扣：CR 输出建议 2048–4096，配合 stop 防止多余解释
- 5.3 logit_bias → 已隐含：工具调用控制
- 5.4 Thinking → CR 回扣：默认关闭，对核心/安全模块自动开启
- 5.5 配置速查 → CR 回扣：起点配置 Sonnet + temp 0.2 + 4096，跑 10 个历史 PR 校准
