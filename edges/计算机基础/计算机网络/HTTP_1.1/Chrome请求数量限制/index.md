在 Chrome 浏览器中，请求并发限制取决于 HTTP 协议版本和域名数量，以下是详细分析（基于 Chrome 稳定版 2024 年数据）：

---

### 🌐 **单个域名的并发请求限制**
| **HTTP 协议** | **最大并发请求数** | 说明 |
| --- | --- | --- |
| **HTTP/1.1** | **6 个** | 经典限制（RFC 规范未强制，但浏览器统一实现） |
| **HTTP/2** | **无硬性限制** | 多路复用突破连接数限制（实际受服务器/客户端资源约束） |
| **HTTP/3** | **无硬性限制** | 同 HTTP/2，基于 QUIC 协议进一步优化 |


> ✅ **验证方法**：  
在 Chrome DevTools 的 **Network** 面板：  
>
> + HTTP/1.1：观察同一域名下最多 6 个请求同时处于 `Loading` 状态  
> + HTTP/2：所有请求并行发送（无排队现象）
>

---

### 🔢 **多域名并发请求限制**
Chrome 对**不同域名**的并发请求采用独立计数规则：

1. **每个域名独立队列**  
    - 若使用 3 个域名，则总并发数 = 3 × 6 = 18（HTTP/1.1）
    - 示例：  

```bash
# 域名分片策略
static1.example.com  # 可并发6个
static2.example.com  # 可并发6个
static3.example.com  # 可并发6个
```

2. **全局总连接数上限**  
    - HTTP/1.1：**约 256 个**（Chrome 默认值，包含所有域名）  
    - HTTP/2/3：**约 1000 个**（理论无上限，但受操作系统/内存约束）

---

### 🚀 **性能优化策略**
#### 1. **HTTP/1.1 优化方案**
+ **域名分片（Domain Sharding）**：  
将资源分散到多个子域名（通常 2-4 个），突破单域名 6 请求限制  

```html
<!-- 示例：静态资源分域名加载 -->
<img src="https://static1.example.com/logo.png">
<img src="https://static2.example.com/banner.jpg">
```

#### 2. **HTTP/2/3 最佳实践**
+ **避免域名分片**：  
HTTP/2 多路复用下分片反而增加 DNS 开销和 TCP 连接成本  
+ **合并小文件**：  
减少请求数比并行加载更高效（如 Webpack 打包 JS/CSS）

---

### ⚠️ **关键注意事项**
1. **HTTP/2 的隐式限制**：  
虽然无硬性并发数限制，但服务器可主动设置：  

```nginx
# Nginx 配置单个连接的最大并发流数（HTTP/2）
http2_max_requests 1000;  # 默认值
```

2. **浏览器差异**：  

| 浏览器 | HTTP/1.1 并发数 |
| --- | --- |
| **Chrome** | 6 |
| Firefox | 6-8 |
| Safari | 6 |


3. **长连接影响**：  
超过 300 秒未活动的连接会被 Chrome 强制关闭（可通过心跳保持）

### 📊 **实际测试数据**
在 HTTP/1.1 下测试（Chrome 115+）：  

1. 单域名加载 100 张图片 → 前 6 个并行，后续排队  
![](https://via.placeholder.com/600x200?text=DevTools截图：HTTP1.1下请求排队)  
2. 分片到 3 个域名 → 18 个请求并行加载

---

### 💡 **总结建议**
| 场景 | 策略 |
| --- | --- |
| **传统项目 (HTTP/1.1)** | 使用 2-4 个域名分片 + 资源合并（雪碧图、文件打包） |
| **现代项目 (HTTP/2+)** | 专注减少请求数 + 启用 HTTP/2（无需分片） + 升级 HTTP/3 体验更佳 |
| **混合环境** | 通过 `feature detection` 动态判断协议支持（如 H2 则禁用分片） |


> 终极方案：  
>

```nginx
# Nginx 配置同时支持 HTTP/1.1 和 HTTP/2
listen 443 ssl http2;  
```
