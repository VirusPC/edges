# HTTP队头阻塞
请求-应答 的模式加剧了HTTP的性能问题。



因为当顺序发送的请求序列中的一个请求因为某种原因被阻塞时，在后面排队的所有请求也一同被阻塞了，会招致客户端一直请求不到数据，这也就是“队头阻塞”。



虽然HTTP/1.1有持久连接，但对于串行请求，需要排队等待，会出现队头阻塞问题。



HTTP/2.0通过多路复用解决了这个问题



# TCP队头阻塞
Tcp报文也要求按序交付。

HTTP/3.0 通过将传输层协议替换为UDP，解决问题



### 与 HTTP 层队头阻塞的区别
+ **TCP HoL Blocking：** 发生在**传输层（TCP）**。一个 TCP 连接上的**任何**数据包丢失，都会阻塞该连接上后续**所有**已到达但顺序靠后的数据包的应用层交付。
+ **HTTP/1.1 的 HoL Blocking：** 发生在**应用层（HTTP）**。HTTP/1.1 允许在同一个 TCP 连接上发送多个请求，但这些请求的**响应必须按请求发出的顺序返回**。如果第一个请求的响应很慢（例如需要查询数据库），即使后续请求的响应早已准备好，浏览器也必须等待第一个响应返回后才能开始处理后续响应。HTTP/2 通过引入**多路复用**解决了这个应用层队头阻塞（多个请求/响应流并行交错传输）。

### 如何解决 TCP 队头阻塞？
TCP 协议本身的设计（可靠、按序）决定了它无法从根本上消除队头阻塞。主要的解决思路是“**绕过**”或“**减轻**”其影响：

1. **建立多条 TCP 连接：**
    - **原理：** 将资源分散到多个独立的 TCP 连接上传输（如浏览器对同一域名默认建立 6 条连接）。
    - **效果：** 一条连接上的 HoL Blocking 不会直接影响其他连接上的数据传输。
    - **缺点：** 建立/维护连接开销大，竞争带宽可能导致整体拥塞。
2. **使用 UDP 及基于 UDP 的协议：**
    - **原理：** UDP 本身是不可靠、无连接的，没有内置的按序交付机制，因此天然没有 TCP 的 HoL Blocking 问题。
    - **应用：**
        * **QUIC (HTTP/3 的底层协议)：** 这是最主要的解决方案。QUIC 在 UDP 之上实现了：
            + **独立的、可靠的流：** 在单个 QUIC 连接内建立多个逻辑上的“流”。每个流内部保证可靠性和顺序性。
            + **关键突破：** **一个流上的数据包丢失或延迟，只会阻塞该流本身的数据交付，不会影响连接内其他流的数据交付！** 这彻底解决了 TCP 的 HoL Blocking 问题。
            + 快速握手、连接迁移、改进的拥塞控制等。
        * **WebRTC：** 主要用于实时通信，使用 SRTP/SCTP over UDP，也避免了 TCP HoL Blocking，更适合容忍少量丢包的音视频传输。
3. **应用层优化：**
    - 对延迟敏感的数据使用更高优先级（如 TCP 的优先级调度，或 QUIC 的流优先级）。
    - 对非关键数据允许丢包（如部分视频帧）。
