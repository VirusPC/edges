这篇文章的关键结论是：与其为每个领域重复造“专用智能体”，不如用“Agent Skills”（技能）把领域知识封装成文件和脚本，让一个通用智能体通过技能变成各行各业的“专科医生”。[1]

## 文章核心观点

- 智能体本身已经足够强大，关键瓶颈从“能力不足”转为“缺少领域经验和组织知识”。[1]
- Agent Skills 把流程、最佳实践、脚本等打包成可复用的文件集合，让通用智能体在具体领域表现得像专业人士。[1]
- 技能是开源标准，可在不同平台间通用，形成可共享的技能生态系统。[1]

## 为什么从“专用 Agent”转向“技能”

- 过去大家认为需要为编程、金融、营销等分别打造不同 Agent，但随着模型和工具变强，这种拆分变得低效。[1]
- 研发者发现：用一个通用 Agent（如 **Claude Code**）+ 合适的代码接口，已经能覆盖大部分数字化工作，缺的是结构化的专业知识沉淀。[1]

## Agent Skills 是什么、长什么样

- Skill 本质是一个文件夹：包含 SKILL.md、说明文档和脚本，比如品牌规范、PPT 模板脚本等。[1]
- 这种“用文件打包知识”的设计非常简单：可用 Git 管理、存网盘共享，也方便非工程师参与编辑和维护。[1]

## Progressive disclosure（渐进展开）

- 为避免一次性把所有技能内容塞进上下文，技能只先暴露很短的元数据（名称和描述）。[1]
- 当智能体判断需要某个技能时，再读取完整 SKILL.md；如果还不够，再按需读取更大体量的参考文档，既节省上下文又支持上百个技能共存。[1]

## 技能可以内嵌脚本工具

- 与传统“工具插件”相比，技能中的脚本更易被模型理解、修改和复用，也不必常驻在上下文中。[1]
- 文中举例：让智能体把经常生成的 PPT 美化脚本固化成 apply_template.py，并在说明文档里指导如何调用它，形成可持续复用的“品牌技能”。[1]

## 正在形成的技能生态

- 出现了三类主要技能：  
  - 基础技能：处理文档、表格、演示文稿等通用办公场景。[1]
  - 合作伙伴技能：如 **Notion**、Browserbase、K‑Dense 等公司，通过技能暴露自己服务的专业能力给 Agent 使用。[1]
  - 企业技能：企业内部把流程、合规要求、内隐知识等固化为私有技能，让 Agent 真正符合公司“做事方式”。[1]

## 发展趋势与复杂度提升

- 技能从简单“查文档”进化到复杂多步工作流，比如自动做财务模型或 RNA 测序整套流水线，代码量从百行到数千行不等。[1]
- 技能与 MCP 服务器（统一工具接入标准）自然结合，一个技能可以同时调动外部搜索、内部数据库、Slack 历史、Notion 页面等资源协同工作。[1]

## 更广泛的人群在创建技能

- 不再只有工程师，产品经理、分析师和各类领域专家也能用向导工具在 30 分钟内创建首个技能。[1]
- 官方在优化模板和工具，让任何人都能把自己的经验“打包”为技能，供团队和社区共享。[1]

## 新的通用 Agent 架构

- 文章提出一个分层架构：  
  - Agent loop：负责“思考与决策”。  
  - Agent runtime：负责代码执行和文件系统。  
  - MCP servers：接入外部工具和数据源。  
  - Skills library：提供领域知识和步骤指南。[1]
- 例如增加一个前端设计技能，就能立刻显著提升智能体在前端排版、色彩与动效方面的表现，而且只在相关任务时被激活。[1]

## 在各行业的落地案例

- 金融服务领域：提供 DCF 模型构建、可比公司分析、财报解读、尽调和路演材料等专用技能，让金融从业者直接用 Agent 做专业工作。[1]
- 医疗与生命科学领域：提供生信流程、临床试验方案撰写、科研选题、FHIR 开发及事前授权审核等技能，降低合规和技术门槛。[1]

## Agent Skills 标准与未来愿景

- **Agent Skills** 被发布为开放标准，希望像 MCP 一样在行业内通用，一个技能可以在 **Claude** 或其他平台上复用。[1]
- 理想状态是：用户初次使用 Agent 时，它已经通过技能“预装”了团队关心的知识，而社区里别人做好的技能也能立刻让你的智能体变得更强、更稳、更贴近业务。[1]
