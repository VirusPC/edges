这篇文章的核心结论是：大部分实际可落地的 AI Agent 系统，都可以用三种**工作流模式**（顺序式、并行式、评估-优化式）来搭建；应优先从最简单的单 Agent 或顺序工作流开始，只在“确有瓶颈且可量化收益”的前提下，再引入并行和评估-优化，以在质量、延迟和成本之间取得平衡。[1]

## 文章结论与整体思路

- 真正在生产中常用的 Agent 工作流只有三种主模式：顺序（Sequential）、并行（Parallel）、评估-优化（Evaluator-Optimizer），可以视作可组合的“积木块”。[1]
- 选型的核心是任务结构（是否有依赖）、质量要求（是否需要迭代打磨）和资源约束（延迟、Token 成本），不要过度设计：能用单 Agent 解决就不要上工作流，能用顺序解决就不要上并行，首稿质量够好就不要上评估-优化循环。[1]
- 这些模式是可组合、可演进的：先从简单顺序开始，遇到瓶颈再在关键节点插入并行或评估-优化环节，而无需重写整个系统。[1]

## 顺序工作流（Sequential）

- 定义：任务按预先设定的固定顺序一步步执行，前一步的输出是后一步的输入，形成线性“流水线”。[1]
- 适用场景：多阶段流程且步骤有明显依赖，例如文档抽取 → 校验 → 入库，或营销文案生成 → 翻译 → 审核等；通过让每个 Agent 专注于单一子任务来换取更高的准确性。[1]
- 不适用：单个 Agent 就能可靠完成任务，或任务本身需要多 Agent 协同而不是单向传递时，强行拆成顺序只会增加复杂度和延迟。[1]
- 作者建议：先把整条流程写成“一个 Agent 的长提示词”，如果效果已经够好，就不要再拆多步；只有当单 Agent 不稳定或质量不够时，再拆成顺序工作流。[1]

## 并行工作流（Parallel）

- 定义：将互相独立的子任务分配给多个 Agent 同时运行，最终在某个聚合步骤把结果合并（类似分布式系统里的 fan-out/fan-in）。[1]
- 适用场景：  
  - 各子任务彼此独立，不需要前后依赖，且希望缩短整体响应时间。  
  - 需要对同一内容从多个维度评估（例如质量、多种安全检查、多种风险检查），或做“多 Agent 投票”。[1]
- 代价与风险：Token 成本更高，需要设计清晰的结果聚合策略（多数表决、平均置信度、优先信任最专业的 Agent 等），且不适合需要共享上下文或逐步累积信息的任务。[1]
- 作者提醒：在实现前先设计好“如何合并不同 Agent 的输出”，否则只会得到一堆冲突结果而无决策机制。[1]

## 评估-优化工作流（Evaluator-Optimizer）

- 定义：至少两个 Agent 循环协作：一个负责生成（Generator），另一个负责评估（Evaluator），评估结果再反馈给生成者进行改写，如此迭代直到达到质量阈值或达到最大迭代次数。[1]
- 关键洞察：生成与评估是性质不同的“认知任务”，拆分后可以让生成者专注“写”，评估者专注“按标准打分”。[1]
- 适用场景：  
  - 有清晰、可度量的质量标准（安全、性能、风格、完整性等），且首稿质量与目标质量之间差距足够大，值得为了提升质量付出额外 Token 和延迟。  
  - 典型例子：带具体规范的代码生成、严肃对外沟通、API/技术文档撰写、SQL 生成并检查效率和安全性。[1]
- 不适用：  
  - 首稿已经“足够好”，再迭代收益有限。  
  - 需要实时响应的应用、简单规则任务（如基础分类）、评价标准高度主观而 AI 难以一致执行，或已有更确定性的工具（如 linter）。[1]
- 作者提醒：务必预先设定“停止条件”（最大迭代次数、清晰的及格标准），否则可能掉入昂贵但收益有限的“无休止微调循环”。[1]

## 模式选择与组合原则

- 决策顺序：先试单 Agent；如果不够好，再问：  
  - 是否有明确的前后依赖？是 → 用顺序工作流。  
  - 子任务是否可独立并行且延迟是瓶颈？是 → 在部分节点引入并行。  
  - 质量是否能通过结构化迭代大幅提升？是 → 引入评估-优化循环。[1]
- 需要同时考虑：失败处理（重试、降级）、延迟与成本预算（可并行 Agent 数量、可承受迭代次数）、以及如何度量相对于“单 Agent 基线”的真实提升。[1]
- 组合示例：顺序工作流中的某一步可以并行多个子检查；评估-优化流程中的“评估”本身可以并行多个维度的评估 Agent。[1]

## 行动指南（落地建议）

如果你要在团队里落地或重构 Agent 系统，可以按下面顺序操作：

1. 先做“单 Agent 基线”  
   - 把完整任务流程写进一个较长提示词中，让单个 Agent 处理全程。  
   - 记录质量、延迟、成本三个指标，作为后续对比基线。[1]

2. 判断是否需要工作流  
   - 如果单 Agent 已满足业务需求：先上线，不要引入工作流。  
   - 如果不满足，写下失败的具体原因（例如：某步经常出错、整体太慢、合规风险等），用这些原因来选模式。[1]

3. 优先尝试顺序工作流  
   - 将任务拆成 2–5 个“天然分段”的步骤（比如：理解输入 → 规划 → 执行 → 汇总），每一步只做一件事。  
   - 在每步之间明确输入输出格式，便于调试和监控质量。[1]

4. 只有在“延迟成为瓶颈”时再加并行  
   - 审视顺序链路中的哪些子步骤可以完全独立、无前后依赖（例如多维度评估、多项规则检查、多份文档分析）。  
   - 仅在这些节点做并行 fan-out/fan-in，并提前设计好聚合策略（投票、打分加权、优先高级 Agent 等）。[1]

5. 质量不达标且可度量时，引入评估-优化  
   - 明确评估标准：例如“是否完整覆盖接口”、“是否符合安全规范 X”、“是否满足公司语气指南”。  
   - 单独训练/设计一个评估 Agent，只输出结构化反馈，然后让生成 Agent 依标准改写。  
   - 为这一循环设定最大轮次和及格线，例如“最多 3 轮，只要所有关键检查项通过就停止”。[1]

6. 为每个模式加上工程“护栏”  
   - 为顺序与并行步骤设计失败重试和降级策略（如：某一步失败则跳过或调用简化版规则引擎）。  
   - 对评估-优化循环设置超时与预算上限，防止无限迭代。  
   - 持续对比“当前工作流”与“单 Agent 基线”的指标，只有在观测到真实收益时才保留新增复杂度。[1]

7. 渐进式演进，而非一次性大改  
   - 从最简单的顺序链路开始，逐步在瓶颈处插入并行和评估-优化环节。  
   - 每次变更控制在“小步可回滚”的粒度，方便回退到上一个稳定版本。[1]
