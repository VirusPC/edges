这篇文章的核心结论是：新的 skill-creator 升级，把“写技能”这件事变成一件可测试、可度量、可持续改进的工作，让不会写代码的**技能作者**也能像软件工程师一样做自动化测试、基准对比和触发率调优，从而保证技能在模型频繁迭代时依然可靠好用。[1]

## 核心变化与价值

- skill-creator 现在支持直接帮你写 eval（测试用例）、跑 benchmark（基准测试），并持续监控技能在新模型上的表现，无需写代码。[1]
- 文章把技能分成两类：提升模型能力的“能力增强型”（capability uplift）和编码团队流程的“偏好/流程型”（encoded preference），并强调这两类需要不同侧重点的测试与维护。[1]
- 通过 evals 和 benchmark，作者可以：及时发现质量回退、判断基础模型是否已经“学会”原本由技能提供的技巧，从而决定这个技能是否还值得维护。[1]

## Evals：让技能可测试、可回归

- Evals 是一组针对技能的测试：你给定一些典型 prompt（可带文件）、描述“好结果长什么样”，工具会自动判断 Claude 的输出是否符合预期。[1]
- 文中举例：他们的 PDF 技能在非可填表单上曾经难以在无字段提示的情况下精准定位文本，通过 evals 把失败场景隔离出来，最后改成按抽取文本坐标定位，从而修复问题。[1]
- Evals 的两个关键用途是：  
  - 发现质量回退：新模型或基础设施升级后，快速看技能是否“变坏”；  
  - 判断模型进步：如果“不开技能”也能通过 eval，说明技能中的技巧已经被模型内化，可以逐步淘汰该技能。[1]

## Benchmark 与多 Agent：更快、更客观的评估

- 新的 benchmark 模式基于你的 eval 集合做标准化评估，记录通过率、耗时和 token 使用量，方便你在模型升级或修改技能逻辑后快速对比前后版本。[1]
- 引入多 Agent 支持：每个 eval 用独立 Agent 并行执行，在干净上下文中运行，避免测试之间的“串味”，同时显著加快评估速度。[1]
- 还新增了“比较 Agent”（comparator agents），可以对比“两版技能”或“有技能 vs 无技能”的输出，而且在不暴露是哪一侧的前提下做盲评，帮助客观判断改动是否真的带来提升。[1]

## 触发逻辑：让技能在“正确的时机”被调用

- 文章强调：输出质量再好，如果技能在该触发时不触发，或乱触发，都没用，因此技能描述的准确性变得非常关键。[1]
- skill-creator 现在可以根据一组示例 prompt 分析你当前的技能描述，并给出修改建议，以减少“误触发”（false positives）和“漏触发”（false negatives）。[1]
- 官方在自家文档创建类技能上试用后，6 个公开技能中有 5 个的触发表现得到改善，说明这个调优工具在实践中是有效的。[1]

## 未来方向：从“实现计划”到“规格描述”

- 当前的 SKILL.md 更像是“实现方案”，详细告诉 Claude 要**怎么做**（步骤、模版、约束等）。[1]
- 作者认为，随着模型能力提升，未来可能只需要用自然语言描述“技能应该**做什么**”，模型便能自动推导出实现细节，技能会更像一份高层规格说明。[1]
- 这次发布的 eval 框架已经在朝这个方向前进：eval 本质上是在精确描述“什么叫做好”，未来这套“好坏标准”本身就有机会变成技能定义的一部分。[1]

## 如何开始使用这些更新

- 所有更新已在 Claude 和 Cowork 中提供；你可以直接让 Claude 使用 skill-creator 来创建和评估技能。[1]
- 如果你用 Claude Code，可以安装官方插件，或者从 GitHub 仓库下载并在本地/CI 中集成这些 eval 和 benchmark 工作流。[1]

## 行动指南（给技能作者/团队）

1. 明确你的技能类型  
   - 将现有技能分为“能力增强型”和“偏好/流程型”，对前者多关注“模型是否已经内化”，对后者多关注“是否忠实还原业务流程”。[1]

2. 为关键技能补齐 eval 集合  
   - 为最常用、最关键的 3–5 个技能先写 eval：覆盖高价值场景与典型边界案例，清晰写出“理想输出标准”。[1]

3. 建立固定的 benchmark 节奏  
   - 在模型更新前后或修改技能逻辑后，跑一遍 benchmark，记录通过率、耗时和 token 使用量，为“要不要继续维护/重写一个技能”提供数据支持。[1]

4. 利用多 Agent 与对比评估做 A/B 实验  
   - 修改技能前后，用 comparator agents 做盲评，避免主观偏见；同时保持每个 eval 在干净上下文中运行，以保证结果可复现。[1]

5. 系统性调优技能描述，提升触发质量  
   - 使用 skill-creator 的描述分析功能，对触发异常（乱触发或不触发）的技能重点调优 description；每次调优后再跑一轮 eval 检查触发情况是否改善。[1]

6. 把 eval 与现有工程实践结合  
   - 将 eval 结果接入你已有的仪表盘或 CI 流水线，在模型版本切换或部署脚本中加入“跑一轮技能 eval”的步骤，形成自动回归保护网。[1]

7. 逐步向“用规格定义技能”靠拢  
   - 在写 eval 和技能说明时，有意识地用更抽象、面向业务目标的语言描述“什么是好结果”，为未来仅靠自然语言规格就能定义技能做好准备。[1]
