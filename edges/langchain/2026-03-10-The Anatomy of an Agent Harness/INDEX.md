**结论优先总结**

这篇文章的核心观点是：**智能在模型里，用处在 harness 里**。 换句话说，真正决定一个智能体是否能“干活”，不只是选什么模型，而是你如何设计围绕模型的一整套系统（harness）。[1]

***

## 什么是 Agent Harness？

- Harness 指除模型本身以外的所有代码、配置和执行逻辑，是把“会推理的模型”变成“能完成任务的工作引擎”的关键。[1]
- 它包括系统提示词、工具/技能/MCP 描述、文件系统和沙盒等基础设施、编排逻辑、以及各种 hooks/middleware 用来做压缩、续写、lint 等确定性控制。[1]

***

## 为什么需要 Harness？

- LLM 只能“输入多模态、输出文本”，天生做不到：持久化状态、执行代码、访问实时信息、搭环境等，这些都必须由 harness 提供。[1]
- Harness 的目标是：从“想要的代理行为”出发，反推需要什么系统能力，再通过文件系统、工具调用、环境配置等工程手段，把这些能力变成真实特性。[1]

***

## 核心组件：文件系统、代码执行、沙盒、记忆与搜索

- **文件系统**：为代理提供持久存储和工作空间，用来读写数据/代码、保存中间结果、跨会话保持状态，也是多人与多代理协作的共享面板；配合 git 可做版本管理与回滚。[1]
- **Bash + 代码执行**：作为“通用工具”，让代理通过写代码自己造工具，而不是只能依赖预定义工具；这本质上是“给模型一台电脑”。[1]
- **沙盒与工具链**：提供安全、可扩展的执行环境，预装语言运行时、包、git、测试工具、浏览器等，并通过日志、截图、测试等支持自我验证。[1]
- **记忆与搜索**：利用文件（如 AGENTS.md）做持续学习，把过往经验注入上下文；通过 Web Search/MCP 获取训练截止之后的最新知识。[1]

***

## 对长任务、上下文衰减与未来趋势的观点

- Harness 通过上下文压缩、工具输出 offload、技能的渐进披露等手段，对抗“context rot”（上下文变长导致推理变差）。[1]
- 对于长跨度、自主执行（如自动写软件），Harness 依赖：文件系统+git 追踪进度、Ralph Loop 强制继续任务、规划与自验证保持轨道。[1]
- 模型训练和 harness 设计正在耦合：模型在特定 harness 中后训，会对该 harness 的工具逻辑“过拟合”，但这并不意味着“官方 harness”对你的任务一定最好，调整 harness 本身就能大幅提升表现。[1]
- 未来模型会吸收更多能力（规划、自验证、长程一致性），但就像 prompt engineering 仍然重要一样，harness engineering 会长期存在，因为需要为模型构建合适的环境和系统。[1]

***

## 对你有用的行动指南（落地建议）

如果你在做/准备做 agent 系统，可以按下面的顺序逐步落地：

1. **先划清边界：模型 vs harness**  
   - 明确：模型只负责“思考”，其余一切（记忆、工具、环境、安全、编排）都属于 harness。[1]
   - 在设计阶段就把“想要的代理行为”写成列表，再反推需要哪些 harness 能力（文件、工具、环境等）。[1]

2. **优先搭好文件系统与持久状态层**  
   - 给 agent 一个真实的 workspace（文件系统 + 规范目录结构），支持读写代码、文档和中间产物。[1]
   - 接入 git（或等价机制），让代理可以查看历史、回滚错误、为多人/多代理协作打基础。[1]

3. **提供通用代码执行能力，而不是堆工具**  
   - 首选提供安全的 bash/代码执行工具，让模型可以通过写脚本/程序自己扩展工具，而不是为每个动作手写一个工具。[1]
   - 在此基础上再添加高价值的专用工具（如特定 API 客户端），而不是一开始就设计几十个工具。[1]

4. **用沙盒封装执行环境，预设“好用的默认值”**  
   - 所有代码在隔离沙盒中执行，支持按需创建和销毁，避免在本机或长驻单环境运行。[1]
   - 预装语言、依赖、git、测试框架、浏览器等，让 agent “开箱即用”；同时考虑白名单命令和网络隔离策略。[1]

5. **实现最小可用的记忆与搜索机制**  
   - 采用简单的“记忆文件”标准（例如类似 AGENTS.md），在启动时自动注入上下文，形成持续学习。[1]
   - 为需要实时信息的任务，集成 Web Search / MCP 类工具，避免死在知识截止上。[1]

6. **设计上下文管理策略，避免 context rot**  
   - 实现：  
     - 对历史对话/日志做摘要与压缩。  
     - 对超长工具输出只保留首尾 token，并把完整内容写入文件系统。  
     - 通过“技能/插件的渐进载入”减少启动时一次性注入的说明文档。[1]

7. **为长任务加入“持续推进 + 自验证”机制**  
   - 使用类似 Ralph Loop 的模式，在模型想“退出”时检查目标是否完成，必要时重启一个干净上下文继续工作。[1]
   - 强制规划文件（plan file）+ 测试/检查环：每个阶段产出后运行测试或自评，失败则携带错误信息重新进入模型循环。[1]

8. **把 harness 当成一等优化对象持续迭代**  
   - 不只调模型或 prompt，也要系统地做 harness A/B：改文件布局、工具接口、沙盒配置、上下文策略，并通过基准数据集（如 Terminal Bench 这类基准）观测效果。[1]
   - 接入 trace/日志分析，让 agent 能“看自己的轨迹”，发现并修正 harness 级别的问题。[1]

如果你愿意说明当前在用什么框架 / 云环境（如 LangChain、LlamaIndex、自研等），可以进一步给一份更贴近你栈的 harness 设计 checklist。
