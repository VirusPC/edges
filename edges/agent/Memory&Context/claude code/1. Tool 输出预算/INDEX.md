# Tool 输出预算 — 整体总结

## 问题

Agent 调工具时，输出可能非常大（Bash 日志、Grep 结果、MCP 数据等）。若全量塞进上下文，会撑爆窗口、拖慢推理、浪费 token。

## 解法：三层递进兜底

```
工具执行 → ① 工具内截断 → ② 单条持久化 → ③ 单轮聚合预算 → 发 API
```

不是每层都必然触发，而是**谁超限谁处理**，层层兜底。

---

### ① 工具内截断（执行时，部分工具有）

各工具自带上限，在**执行阶段**就处理：

| 工具 | 策略 | 典型上限 |
|------|------|---------|
| Bash / PowerShell | 截断 + 提示剩余行数 | 30K 字符 |
| Read | 超限报错，引导分段读 | 25K tokens |
| MCP | 截断或落盘 | 25K tokens |
| Task | 截断尾部 + 给文件路径 | 32K 字符 |
| Agent / Grep 等 | **无硬截断** | — |

**特点**：截完后若已低于后续阈值（如 Bash 30K < 50K），后面两层通常不会再动这条结果。

---

### ② 单条 result 持久化（发 API 前）

- **阈值**：默认 50K 字符（`DEFAULT_MAX_RESULT_SIZE_CHARS`）
- **实际值**：`min(工具声明的 maxResultSizeChars, 50K)`，可被 GrowthBook 覆盖
- **硬上限**：约 100K tokens（~400KB）
- **行为**：超限 → 全文落盘到 `tool-results/` → 模型只收到 **2KB 预览 + 文件路径**
- **入口**：`processToolResultBlock()` → `maybePersistLargeToolResult()`

**主要兜谁**：没有工具内截断、但单条输出很大的工具（Agent 子任务、Grep 大结果等）。

---

### ③ 单轮聚合预算（发 API 前）

- **阈值**：200K 字符（`MAX_TOOL_RESULTS_PER_MESSAGE_CHARS`）
- **范围**：**同一轮**并行返回的所有 `tool_result` **加总**
- **行为**：合计超限 → 把最大的几条再落盘，换成预览，直到整轮 ≤ 200K
- **入口**：`query.ts` → `applyToolResultBudget()` → `enforceToolResultBudget()`
- **开关**：GrowthBook flag `tengu_hawthorn_steeple`

**主要兜谁**：单条都不大（如各 45K），但并行 5 个加起来 225K 的累积效应。

---

## 三层关系（一张表）

| 层级 | 管什么 | 典型值 | 触发场景 |
|------|--------|--------|---------|
| ① 工具内 | 单工具执行输出 | Bash 30K | 命令输出太长 |
| ② 单条 | 单条 tool_result | 50K | 无截断工具返回超大结果 |
| ③ 聚合 | 一轮所有 tool_result 之和 | 200K | 并行多工具累积超限 |

**递进逻辑**：
- Bash 先截到 30K → ②③ 通常不再处理
- Grep 一次 80K → ① 不管，② 落盘
- 5 个工具各 45K → ①② 都不管，③ 落盘最大的几条

---

## 核心设计原则

1. **不丢数据**：截断/落盘，不是直接丢弃；完整内容在磁盘，模型可按需 Read
2. **预览 + 路径**：模型知道「有完整内容在哪」，自己决定要不要读
3. **保护 prompt cache**：替换决策按 `tool_use_id` 冻结，同轮重放结果一致
4. **图片例外**：含 image block 的结果不落盘，原样发送

---

## 整体总结

> Tool 输出有三层预算：工具内截断（Bash 30K 等）→ 单条 50K 落盘 → 单轮 200K 聚合落盘。不是每层都走，而是递进兜底。有截断的工具截完就结束；没截断的大输出走 50K；单条不大但并行加起来太大走 200K。核心是**落盘换预览，保护上下文，不丢数据**。
