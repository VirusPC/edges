课次 0001 · Mission · 骨架速查

Changelog 不是 git log

你要写的是给人看的「值得注意的变更清单」，不是把提交历史贴进仓库。

这一课你能带走什么

能判断一段文字该不该进 CHANGELOG.md，并亲手起一个符合约定的空文件骨架。

不要把提交历史贴进去

Keep a Changelog 2.0.0 把 changelog 定义成一份经过挑选的、对读者值得注意的变更记录，按版本倒序排列。 它明确反对把 git log 当 changelog。

三个关键词先记住：

  • 经过挑选：有取舍，不是仓库的全量过程记录。
  • 值得注意：对使用或依赖这个项目的人有意义，不是每一次内部改动。
  • 按版本倒序：最新的发布（以及尚未发布的 Unreleased）放在最上面。

两份给人看的来源，职责不同

git log 记录的是开发过程里发生了什么：常含 merge、措辞含糊的提交、内部改动。 Changelog 记录的是对读者可见的差异——往往跨过好几次提交，并用读者语言写出来。

把提交历史贴进 CHANGELOG.md，文件会充满噪声，把真正值得注意的变更淹没掉。

机器（含 LLM、从提交生成的工具）可以起草，但必须筛选：能进 changelog 的，是用户侧或依赖方需要知道的变化，不是 merge / 重构 / 内部工具噪声。

和 commit、release notes 各管什么

一次提交是过程里的一个点记录；某条 changelog 条目常常从多条提交里抽出，再润色。 Release notes 可以在对外宣布时再加工语气，但仓库里的 CHANGELOG.md 应先成为权威源：先写清「改了什么、该不该升级」，再决定要不要另写营销向文案。

亲手起一个最小骨架

在自己的项目根目录放一份 CHANGELOG.md，先只要约定声明和空的 [Unreleased]：

# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

用来边开发边记下条目。没有真正发布前，不要虚构版本号和日期。完整六节标题见 骨架速查。

课后动作（约 2 分钟）

  1. 选一个自己的仓库，打开或新建 CHANGELOG.md。
  2. 把 ## [Unreleased] 放在已发布版本的上面。
  3. 六个分类小题可以暂且只留空节；还没想好先记哪类，下节再分。

做完把你选的仓库名和第一行标题告诉我即可。

精读材料

精读 Keep a Changelog 2.0.0（约 10–15 分钟）： 先读 What is a changelog、Guiding principles、Don’t dump git logs。

对照 中文版 找表述；约定冲突时以 2.0.0 英文为准。

卡住了？问我。 把你现在的 CHANGELOG.md 草稿——哪怕只有骨架——丢过来就行。
