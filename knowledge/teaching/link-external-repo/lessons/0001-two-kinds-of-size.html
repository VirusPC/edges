关联外部仓库：先分清两种「体积」

「不想占体积」里藏着两个不同的体积——分清它们，四个方案的选择就变成查表。

这一课你能带走什么

能把「外部仓库关联进来但不占体积」翻译成明确需求，并选出对应方案（今天就能回答你自己的问题）。

两种体积，别混在一起

说「不希望它占用体积」时，先问自己担心的是哪一个：

  • 主仓库 .git 历史：任何提交进主仓库的东西都永久留在历史里，删掉工作区文件也删不掉历史。edges 是公开仓库，克隆体积随历史单调增长。
  • 本地磁盘占用：工作区里实际检出的文件。它不进主仓库历史，只占你这块盘。

「关联外部仓库」的四个方案，差别就在它们动的是哪个体积：

  • git submodule：主仓库只存一个 gitlink（mode 为 160000 的目录条目，指向外部仓库的某次提交）加一份 .gitmodules 配置。内容完全不在主仓库历史里——gitsubmodules(7) 就是这么定义的。主仓库体积成本约等于零，同时关联（URL + 提交号）可追溯、可 review。
  • git subtree：把外部仓库内容真正合进主仓库历史。克隆即得、协作者无感，但主仓库体积实打实增长——--squash 可以不带外部全历史，可每次更新的快照仍在主仓库里（git-subtree.adoc）。与「不占体积」相反。
  • gitignore + 本地 clone：把外部仓库 clone 到固定位置（或 symlink 进来）并 gitignore。主仓库零成本，但关联只存在你机器上，别人 clone 后一无所知。
  • partial clone / sparse-checkout：这是「使用方」克隆外部大仓库时省本地磁盘的手段（GitHub Blog），跟往主仓库里关联是两个维度，可以叠加在前三者之外。
回到你最初的问题：要「关联可追溯 + 主仓库不涨体积」，标准答案是 submodule； 如果只是你本地参考、不需要别人复现，gitignore + clone 更省事。四方案完整对比见 选型速查。

「不占体积」的另一面

submodule 的省，正是靠「默认不给内容」换来的：别人 clone 主仓库后，子模块目录存在但为空， 要 git submodule update --init（或克隆时加 --recurse-submodules）才拉到内容。 Pro Git 把这列为 submodule 最常见的协作坑： 忘了 init 就看到空目录，不是坏了，是设计如此。CI、Agent 会话同理，需要在流程里显式 init。

更新外部版本也不难：进子目录 checkout 新提交，回到主仓库提交——diff 只有一行 SHA 变更。

亲手验证（约 3 分钟，用一次性仓库）

别在 edges 上做实验。在 /tmp 建个 lab，眼见为实：

mkdir /tmp/submod-lab && cd /tmp/submod-lab
git init && echo hi > README.md && git add . && git commit -m init

git count-objects -vH        # 记下 size-pack

# 关联一个很小的公开仓库
git submodule add https://github.com/octocat/Hello-World.git vendor/hello
git commit -m "add submodule"

git ls-files -s vendor/hello  # 第一个字段 160000：gitlink，指向提交而非 blob
cat .gitmodules               # 主仓库里真正新增的东西：这个文件 + 一行 gitlink

git count-objects -vH         # 对比：主仓库几乎没涨
du -sh .git                   # 外部内容在 .git/modules 里，属于本地磁盘，不进主仓库对象库

做完 rm -rf /tmp/submod-lab 即可。
