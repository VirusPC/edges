# 2026-03-01--XSCT方法论与AI评测范式转变.md

> Ingested on 2026-03-01

【讨论主题】
围绕 XSCT methodology（XSCT Benchmark）方法论展开讨论。核心议题是：传统 AI benchmark 与真实 AI 产品能力之间存在差距，而 XSCT 试图通过“真实任务场景评测”来更准确衡量 AI 系统能力，特别是面向 Agent 与实际应用场景的能力评估。

【主要结论】
1. 传统 AI benchmark（如 MMLU、GSM8K、HumanEval）主要是“做题式评测”，即模型回答标准化问题并计算正确率。
2. 真实 AI 产品能力通常涉及多步骤任务执行，包括推理、工具调用、上下文跟踪等，与单题答案型 benchmark 不同。
3. XSCT 方法论尝试以“任务场景”而非“单题问题”作为评测单位，更接近真实产品使用环境。
4. XSCT benchmark 将能力划分为多个维度，例如：hallucination 控制、prompt injection 防御、agent task 执行、SQL 能力、推理链等。
5. XSCT 在评测流程中采用“被测模型 + 评分模型（LLM-as-judge）”的结构：
   - Step1：模型完成任务
   - Step2：评审模型依据 rubric 对结果打分
6. XSCT 评测覆盖多个领域，包括语言生成（xsct-l）、图像生成（xsct-vg）和 Web 生成（xsct-w）。
7. 每个测试任务设有 Basic / Medium / Hard 的难度分层，以观察模型能力曲线。
8. 数据规模约为 846 个测试案例，规模相对有限。
9. LLM-as-judge 评测方式可能存在评分偏差，不同模型作为评审时结果可能不同。

【认知更新】
1. AI benchmark 正在从“模型能力评测（model benchmark）”向“系统能力评测（system benchmark）”转变。
2. 未来评测对象不再只是单一 LLM，而是“LLM + tools + memory + planner”的完整 Agent 系统。
3. 真实 AI 产品能力更接近“AI worker”，即执行复杂任务的能力，而不是单次问答能力。
4. LLM-as-judge 可能成为复杂任务评测的主流方法，因为许多现实任务不存在唯一标准答案。
5. 评测体系正在从“问题-答案结构”转向“任务-执行质量结构”，即从 QA Benchmark 走向 Task Benchmark。

【行动指南】
1. 在评估 AI 产品或 Agent 系统时，应优先关注真实任务完成能力，而不仅是传统 benchmark 分数。
2. 设计 AI 评测体系时，可采用“任务 + rubric + LLM judge”的结构，以支持复杂任务评分。
3. 在产品测试中引入关键能力维度，如 hallucination 控制、上下文跟踪、工具调用能力等。
4. 在内部测试中设置不同难度层级任务（Basic / Medium / Hard），观察系统能力边界。

【补充说明】
1. XSCT benchmark 数据集目前规模较小，但强调任务复杂度而非题目数量。
2. Web generation benchmark 涉及前端工程能力（如 dashboard、form、animation、responsive layout），体现 AI 在软件开发场景的能力。
3. 该方法论体现了 AI evaluation 从学术测试向产品工程测试演进的趋势。
