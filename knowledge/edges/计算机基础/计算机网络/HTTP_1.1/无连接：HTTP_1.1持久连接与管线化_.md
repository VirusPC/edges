HTTP/1.1 相比 HTTP/1.0，利用持久连接与管线化：

1. **无连接**：HTTP 协议的初始版本中，每进行一次HTTP通信就要**断开一次TCP连接(不设置keep-alive时)**
2. **问题**：在请求HTML页面时，如过页面里还包含很多其他资源（如图片），还需要请求这些其他资源。假设这个HTML页面有n个图片，就需要进行n+1次http请求，进行n+1次的TCP连接。因此，每次的请求都会造成无谓的TCP连接建立和断开，增加通信量的开销。
3. **解决方法**：**持久连接**。在HTTP/1.1中，所有连接默认都是持久连接。
4. **持久连接**：特点：只要任意一端没有明确提出断开连接，则保持TCP连接状态。
5. **管线化**：持久连接使得多数请求以管线化方式发送成为可能。不等响应就发出下一个请求。但是，服务端还是要按序接收请求，客户端还是按序接收响应。但是，存在应用层的队头阻塞问题，实际并没有推广开来。

但 HTTP/1.1 还是有性能瓶颈: 见另一篇

HTTP/1.1 的持久连接（也称为 `Keep-Alive` 连接）**默认开启**，目的是避免为每个请求/响应对都建立新的 TCP 连接，从而提高性能。但这个连接**不会永久保持**，会在以下情况下断开：

### 📌 主要断开时机

1. **Keep-Alive 超时：**
   * 服务器（有时客户端）会设置一个**空闲超时时间**。如果在**一段时间内**（例如 Nginx 默认 `keepalive_timeout 75s`，Apache 默认 `5s`，Tomcat 默认 `20s`）**没有新的 HTTP 请求**通过这个连接发送，服务器（或客户端）就会主动关闭 TCP 连接以释放资源。
   * **这是最常见的断开原因。** 连接处于“空闲”状态太久。
2. **显式关闭指令 (**`Connection: close`**):**
   * **客户端：** 客户端可以在其发送的 HTTP 请求头中包含 `Connection: close`。这明确告知服务器：“在处理完这个请求后，请关闭这个连接，不要再等待新请求了”。
   * **服务器：** 服务器在其发送的 HTTP 响应头中包含 `Connection: close`。这明确告知客户端：“这个响应是最后一个，之后我将关闭这个连接”。
   * 任何一端发送了这个头字段，都意味着该请求/响应对是这个连接上的**最后一个**操作，完成后连接即被关闭。
3. **错误或异常：**
   * 在传输过程中发生任何 TCP 级别的错误（如网络中断、超时重传失败、RST 包）。
   * 服务器或客户端进程崩溃或重启。
   * 服务器在处理请求时遇到严重错误（如后端服务不可用导致返回 5xx 错误，有时可能伴随关闭连接）。
4. **达到最大请求限制：**
   * 服务器可以配置一个连接上允许处理的**最大请求数量**。达到这个上限后，服务器会在最后一个响应后关闭连接（即使连接还没空闲超时）。
   * 虽然 HTTP/1.1 规范没有强制规定这个上限，但一些服务器实现（或代理）可能有此限制（例如 Nginx 的 `keepalive_requests` 默认是 `100` 个请求）。
5. **客户端主动关闭：**
   * 客户端浏览器标签或应用关闭。
   * 客户端认为不再需要该连接（如用户导航离开页面，客户端缓存策略决定关闭空闲连接）。

### 📌 理解关键点

* **“持久”是相对的：** 它仅意味着**同一个 TCP 连接可以被用于发送多个 HTTP 请求/响应**，而不是每个请求都需要新连接。它**不是**指连接会永远存在。
* **资源管理：** 服务器和客户端都需要管理连接资源（文件描述符、内存）。空闲超时和最大请求限制是防止资源耗尽的关键机制。
* **协议升级或降级：** 如果需要切换到 HTTP/2 或 HTTPS，通常会建立新连接。
* **TCP Keep-Alive：** 注意区分 HTTP 的 `Keep-Alive`（应用层连接复用机制）和 TCP 层的 `KEEPALIVE`（传输层保活探测机制，用于检测“半开”连接）。后者是操作系统层面的，通常探测间隔很长（如小时级），不是 HTTP 连接断开的主要原因。

### 📌 总结表格

| **断开场景** | **触发方** | **描述** |
| :--- | :--- | :--- |
| **Keep-Alive 超时** | 服务器/客户端 | 连接空闲超过设定时间（如 75s），自动关闭以释放资源。最常见原因。 |
| `Connection: close` | 客户端 | 客户端明确要求服务器在处理此请求后关闭连接。 |
| `Connection: close` | 服务器 | 服务器明确告知客户端此响应后连接将关闭。 |
| **TCP错误/异常** | 网络/系统 | 网络中断、RST包、进程崩溃等导致连接强制中断。 |
| **达到最大请求数** | 服务器 | 连接处理的请求数达到上限（如100个），服务器主动关闭。 |
| **客户端主动关闭** | 客户端 | 浏览器标签关闭、应用退出或主动释放空闲连接。 |

### 📌 补充说明

* **现代浏览器行为：** 浏览器通常会为每个主机名打开多个（如 6 个）并行的持久连接，并积极管理它们。它们可能会在标签页不活动一段时间后主动关闭空闲连接，或者在感知到服务器即将超时前发送一个轻量级的请求（如 `ping`）来“保活”连接（如果允许）。
* **服务器配置：** 管理员可以通过调整 `keepalive_timeout`、`keepalive_requests` 等参数来优化服务器的连接管理策略。

**简而言之：HTTP/1.1 持久连接会在空闲超时、收到关闭指令、发生错误、达到请求上限或客户端主动关闭时断开。** 💻 理解这些机制对于优化网络性能和调试连接问题非常重要。
