这篇文章主要说明了在构建智能体时，Skills 和 MCP 各自的角色，以及如何配合使用，让 Claude 按团队自己的工作流程稳定地使用外部工具。[1]

## 核心观点

文章把 MCP 比作“工具超市的货架”，负责安全、标准化地连接外部系统（如 GitHub、Salesforce、Notion、内部 API 等）；把 Skills 比作“懂行的店员”，负责把这些工具串成符合团队规范的多步流程，定义“该做什么、按什么顺序做、做到什么标准算完成”。[1]

## Skills 与 MCP 的分工

- MCP：提供对外部系统的访问能力，比如查 Notion、读 Slack、查数据库、调各种 API，属于“能访问什么”。[1]
- Skills：提供流程与领域知识，比如先查哪个页面、结果如何过滤、输出用什么结构和语气，属于“该怎么做”。[1]

文章强调：MCP 的说明应保持通用（如接口用法），而 Skills 负责具体业务流程、格式和校验标准，避免两边给出冲突指令（例如返回 JSON 还是 Markdown）。[1]

## 二者结合的效果

当同时使用 Skills 和 MCP 时，可以得到：明确的信息来源策略（清晰的“先查 A 再查 B”）、可重复的多步编排（每次走同一流程）、以及符合团队标准的稳定输出（结构、细节和语气统一）。[1]

## 真实案例

文章给了两个示例：Anthropic 财务分析技能 借助多个金融数据 MCP 服务器自动做可比公司估值，从选源、取数、套用估值方法到合规检查都由 Skill 定义；Notion Meeting Intelligence 则通过 Notion MCP 连接自动完成会前材料与议程的搜索、整理、生成和保存，严格符合团队格式要求。[1]

## 何时用 Skills，何时用 MCP

- 适合用 Skills：多步工具流程、需要高度一致性的流程（如季度财报分析、合规审查）、需要沉淀和共享的领域知识（研究方法、代码评审标准、写作规范等）。[1]
- 适合用 MCP：需要实时数据、要在外部系统执行操作（建 issue、更新任务、发通知）、文件读写或连接没有原生支持的服务时。[1]

简单记忆：如果是在讲“怎么做”，用 Skill；如果是为了“能访问到某个系统或数据”，用 MCP。[1]

## 快速对照表结论

文章最后用表格总结：Skills 是流程和方法论，按需加载、保存上下文，最适合标准化工作流；MCP 是工具与数据连接，一旦接好就始终可用，最适合数据访问和外部动作。 开发者通常应先接好 MCP，再为关键流程编写对应的 Skills，把组织的隐性经验固化为可复用的智能体能力。[1]
