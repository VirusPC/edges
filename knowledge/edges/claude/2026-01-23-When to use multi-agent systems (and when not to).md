这篇文章的结论是：大多数团队不需要多智能体系统，应优先用**单一智能体**配合好工具和上下文工程；只有在明确存在“上下文污染”“可并行子任务”“需要专业化工具/角色”这三类约束时，多智能体才值得引入其额外复杂度和成本。[1]

## 总体结论与原则

- 单智能体配合合适工具，往往能完成远超预期的工作，多智能体常被过度使用，且在实践中会带来 3–10 倍 token 开销和更多故障点。[1]
- 多智能体应被视为“解决特定瓶颈的架构优化”，而不是默认起点：先用最简单的单智能体方案，只有在证据表明遇到单智能体的硬约束时，再引入多智能体。[1]

## 何时优先单智能体

- 多智能体带来额外协调成本：多份 Prompt 维护、上下文丢失、代理间消息传递与结果总结，都显著增加复杂度和 token 消耗。[1]
- 实践中很多“计划-执行-审核-迭代”式的流水线多智能体架构，最终表现不如一个设计良好的单智能体加上合适工具和上下文压缩策略。[1]

## 多智能体真正擅长的三种场景

1. **上下文保护（context protection）**  
   - 当子任务会产生大量与主任务无关的上下文（如订单长记录、文档全文）时，用子代理在独立上下文中处理，并只把精简摘要传回主代理，可以避免“上下文污染”。[1]
   - 典型例子是把订单查询、长文档检索等封装为子代理，主代理只接收几十 token 的关键摘要，而非上千 token 的原始信息。[1]

2. **并行化（parallelization）**  
   - 在搜索和调研中，主代理把问题拆成多个相互独立的“研究面”，各子代理并行检索和归纳，再由主代理综合，可以覆盖更大的信息空间，提高全面性和准确率。[1]
   - 代价是总 token 变多、整体计算时间通常更长，因此并行化的主要收益是“更全面”，而不是“更快”。[1]

3. **专业化（specialization）**  
   - 当单个代理工具过多（如 20+）、跨多个完全不同领域，或者新增工具让原有任务表现变差时，应按工具域拆分专业代理，并用一个编排代理负责路由请求。[1]
   - 也包括按系统提示和领域知识专业化：例如为 CRM、营销自动化、消息通知各建一个专门代理，而不是让一个通才代理掌管几十个异构 API 工具。[1]

## 何时说明你已经“长大到该用多智能体”

- 经常接近上下文窗口上限且质量明显下降，即使用了上下文压缩等手段仍有压力。[1]
- 一个代理要管理 15–20+ 工具，模型在理解与选择工具上消耗了大量注意力，且加入新工具会显著拖累原有任务表现。[1]
- 任务天然可以拆成互不依赖的子任务，适合并行执行（如多市场、多组件的独立测试等）。[1]

## 如何正确拆分代理：以“上下文”为中心

- 文章强调要用**上下文中心（context-centric）**而非“问题类型中心（problem-centric）”的拆分方式。[1]
- 不推荐按“规划/实现/测试/审查”这类顺序阶段拆代理，因为需要共享的上下文太多，导致“传话游戏”，每次交接都会丢失信息，协调 token 甚至超过实际工作。[1]

### 推荐的拆分边界

- 彼此独立的研究路径（如“亚洲市场趋势”与“欧洲市场趋势”）。[1]
- 拥有清晰接口的独立组件（如前端和后端通过良好 API 合同解耦）。[1]
- 黑盒式验证任务：只需要看结果是否符合规范，而不需要完整实现历史的上下文。[1]

### 不推荐的拆分边界

- 同一特性从规划到实现到测试，这些阶段高度共享上下文，不宜拆成多个代理。[1]
- 紧耦合组件，需要频繁来回沟通和共享状态的工作。[1]
- 任何需要多代理持续同步内部“心智模型”的场景。[1]

## 验证子代理（verification subagent）模式

- 一个相对稳健、在很多领域都适用的模式，是让主代理完成工作后，交由专门的验证代理做测试与校验（比如运行测试集、合规检查、格式校验等）。[1]
- 验证代理只需看到成果与验证标准，而不需要全部实现历史上下文，因此天然避免“传话游戏”问题，适合做质量、安全、合规、事实核查等各类“黑盒验证”。[1]

### 典型用法与注意事项

- 用在代码质量保证、合规审核、输出格式与约束验证、事实核查等环节，由主代理生成工件，验证代理只负责判定是否满足明确标准。[1]
- 最大风险是“过早宣布成功”：验证代理跑了少量用例就说“通过”。为此需要在指令里写清：必须跑完整测试集、覆盖多个场景与边界条件，并要求验证代理显式报告执行了哪些检查。[1]

## 作者给团队的最终建议

- 在引入多智能体前，先确认确有“上下文限制、可并行子任务或专业化需求”等真实约束，而不是为了架构炫酷而拆分。[1]
- 以上下文为核心来设计代理边界，并在合适位置引入可独立工作的验证子代理，通过明确验证标准来提高整体可靠性。[1]
