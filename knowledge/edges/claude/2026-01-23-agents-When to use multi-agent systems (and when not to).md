多智能体系统只在少数场景下比单智能体更好用：当需要隔离上下文、防止“污染”；当任务能高质量并行；以及当工具或领域专业化能显著提升正确性，其余多数情况下应优先用一个设计良好的单智能体系统。[1]

## 文章核心结论（结论优先）

- 默认选择：先用**单智能体**配合合适工具，很多团队高估了多智能体的必要性，结果只是增加复杂度和成本。[1]
- 多智能体的价值主要体现在三类问题：  
  1）上下文污染严重，需要**上下文隔离**；  
  2）任务天然可拆成**可并行的子任务**，需要更全面覆盖信息空间；  
  3）需要**工具集 / 系统提示 / 领域的专业化**，单一万能 agent 工具太多、角色冲突或领域过广时表现变差。[1]
- 多智能体的代价：通常会带来 3–10 倍 token 消耗、更高的协调开销和更多失败点，若不满足以上条件，得不偿失。[1]
- 设计多智能体时，应按“**上下文边界**”而不是“工作类型”来拆分；一个稳定有效的通用模式是“**主 agent + 验证子 agent**”。[1]

## 何时优先单智能体

- 单智能体配合工具（包括工具搜索、上下文压缩等）往往足以解决大部分工作流需求，且实现和维护成本更低。[1]
- 多智能体会引入额外 prompts、更多上下文复制与总结，导致协调成本显著上升，实际执行 token 往往远多于单智能体方案。[1]

## 适合多智能体的三大场景

### 1. 上下文保护（防止上下文污染）

- 当某些子任务会产生大量上下文（如千级 token 的订单历史、长文档检索结果），但主任务只需要一个精简摘要时，用独立子 agent 先“吃掉大上下文，再产出摘要”可以让主 agent 上下文保持干净。[1]
- 示例：客服系统中，用一个专门的“订单查询 agent”读取海量订单记录并返回 50–100 token 的关键信息，再交给主支持 agent 处理技术问题，避免主上下文被无关细节稀释。[1]

### 2. 并行化（覆盖更大信息空间）

- 在复杂搜索 / 研究任务中，让一个“主研究 agent”拆解查询为多个独立研究方向，再并行启动多个子 agent 分别检索与总结，可显著提高**覆盖度与完整性**。[1]
- 好处主要在“更全面”，而不是绝对更快：总计算量增加（多路并发、各自上下文与互相总结），经常会比单线程单智能体更慢，但结果更充分。[1]

### 3. 专业化（工具集、提示和领域）

- **工具集专业化**：当一个 agent 挂了 20+ 多工具、且跨好几个领域（CRM、营销、消息平台等），容易选错工具或性能整体下降，此时拆成多个按领域分工的专用 agent 更稳。[1]
- **系统提示专业化**：不同任务需要相互冲突的 persona / 约束（同一个 agent 又要共情客服、又要苛刻审查代码），分拆为不同角色的专用 agent 能保一致性。[1]
- **领域专业化**：如法律分析、医学研究等需要大量领域上下文，集中在单个通用 agent 会“挤爆”上下文，不如做领域专用 agent 承载这些知识。[1]

## 什么时候说明单智能体“已经不够用了”

- 上下文经常接近上限，且质量明显下降，表明上下文压力已成为瓶颈，可考虑通过子 agent 隔离大体量上下文。[1]
- 工具数量过多（15–20+），新增工具后整体表现变差，即模型在“理解和选择工具”上的负担过重，可以考虑工具搜索或拆专用 agent。[1]
- 任务天然可拆成**独立、弱耦合**的子任务，可以并行执行（多地市场调研、多组件独立测试等）。[1]

## 如何正确拆分：按上下文，而不是按岗位

- “按岗位”拆分（一个写代码、一个写测试、一个评审）往往导致频繁交接与信息丢失，各 agent 像玩“传话游戏”，最终协调 token 甚至比实际工作 token 还多。[1]
- 更好的方式是“按上下文边界拆分”：  
  - 谁持有完整上下文，就让谁把相关工作（如实现 + 测试）都做完；  
  - 仅当子工作可以在**上下文隔离**的前提下独立运作时，才拆出去。[1]

**适合拆开的边界示例**：[1]
- 完全独立的研究方向（如按地区拆的市场调研）。  
- 接口清晰的组件（前后端以稳定 API 协议衔接）。  
- 只需黑盒验证的工作（如只跑测试、不关心实现过程）。  

**不适合拆开的边界示例**：[1]
- 同一功能的规划、实现、测试等强相关阶段。  
- 紧耦合、需要频繁互相调整的组件。  
- 需要共享大量状态与背景的任务。  

## 验证子智能体模式

- 一个实践中**稳定好用**的模式是：主 agent 负责产出 artefact（代码、文档、结果），单独的验证子 agent 只负责按明确标准做测试 / 审核。[1]
- 验证 agent 只需看到“要验证的输出 + 明确评判标准”，不需要完整构建过程上下文，因此天然适合上下文隔离，避免“传话游戏”问题。[1]

### 验证子智能体常见用途

- 质量保障：跑测试、lint、schema 校验结果。[1]
- 合规检查：对文档输出做政策与规则符合性核查。[1]
- 输出校验：在交付前检查内容是否满足格式与业务要求。[1]
- 事实核查：单独 agent 对生成内容里的关键事实做查证。[1]

### 主要风险与缓解

- 典型失败模式是“早赢偏差”：验证 agent 跑了少数检查就宣布通过。[1]
- 缓解方式包括：写死“必须跑完整测试集”、要求覆盖多场景和边界情况、明确包含负向测试，以及在提示中强调“未经完整测试不得标记为通过”。[1]

## 行动指南（给你的实践建议）

### 一、先判断：你现在是否真的需要多智能体？

按下面问题自查，如果大部分答案为“否”，先把精力放在一个强大的单 agent + 工具体系上即可。[1]

- 你的任务中，是否有“会产生上千 token 但只需几十 token 摘要”的子步骤？  
- 是否需要同时探索多个互不依赖的信息路径（多市场、多产品线、多假设并行验证）？  
- 你当前单 agent 是否已经挂了 15–20+ 工具，并且频繁工具选错或性能随工具增多而变差？ 
- 是否有明显不同 persona / 约束 / 领域，混在一个 agent 里经常互相干扰？  

### 二、若确实需要，用下面的设计原则搭架子

- 原则 1：**一切以上下文为中心**  
  - 优先识别“上下文可以干净隔离”的地方，例如独立检索、只做验证的任务，再考虑拆 agent。[1]

- 原则 2：**只在三类场景启用多智能体**  
  - 大量上下文但只需摘要 → 建“检索 / 摘要子 agent”。  
  - 自然可并行且彼此弱耦合 → 建“并行研究 / 并行执行子 agent”。  
  - 工具过多、角色冲突或领域庞杂 → 按领域或职责切出专用 agent（如 CRM、营销、消息三类专员）。[1]

- 原则 3：**默认配一个验证子智能体，而不是再拆更多角色**  
  - 主 agent 负责“做事”，验证 agent 负责“验收”，以明确的成功标准和工具来测试，不再额外拆 planner / reviewer 等角色，降低“传话”开销。[1]

### 三、实施时的具体落地步骤（可直接照着做）

1. 先实现一个功能完备的单 agent：配好必要工具、系统提示和上下文压缩/检索机制，收集真实瓶颈数据（上下文长度、错误位置、工具选择情况）。[1]
2. 当发现瓶颈主要来自“长上下文”或“工具过多”或“需要并行覆盖更多空间”，从那一处切入增加一个子 agent，而不是一开始设计全套“规划-执行-评审”多角色体系。[1]
3. 第一批新增的子 agent 优先考虑两类：  
   - 检索/摘要 agent：吃大上下文 → 输出短摘要给主 agent。  
   - 验证 agent：对主 agent 结果做自动化测试/审查，阻断明显错误流入下游。[1]
4. 建立指标：对比多智能体前后在质量、token 使用量、延迟上的变化，若收益不明显甚至变差，应敢于回退到更简单的单智能体架构。[1]

按照这套决策框架与步骤，你可以在保持系统尽量简单的前提下，**只在确有收益的地方**引入多智能体架构，而不是为“酷”而用。
