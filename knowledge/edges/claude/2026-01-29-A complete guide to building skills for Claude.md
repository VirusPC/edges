这篇文档的核心结论是：**Skill 是给 Claude 写“可复用 SOP”的标准格式文件夹，用来把你的流程、规范和工具调用固化下来，从而在多个场景、多个产品中自动触发、稳定复现高质量结果；成功的关键在于：清晰用例 → 严谨 frontmatter → 精简又可迭代的说明 → 体系化测试与分发。**[1]

***

## 结论与关键要点

- **Skill 的本质**：一个包含 `SKILL.md`（带 YAML frontmatter）、可选脚本、参考文档和模板资产的文件夹，用来教 Claude 在特定场景下怎么做事（而不是每次靠临时 prompt）。[1]
- **三大核心原则**：渐进披露（frontmatter → 正文 → 参考文件）、可组合（能与其他 skills 共存）、可移植（Claude 网页、Claude Code、API 一致）。[1]
- **典型三类用途**：文档/资产生成、流程自动化、增强 MCP 连接器（把“工具访问”升级为“完整工作流”）。[1]
- **成败关键点**：  
  - 前期要先选 2–3 个清晰用例与成功指标。  
  - frontmatter 的 `description` 要写清“做什么 + 何时用 + 触发语”。  
  - 指令要具体可执行，有错误处理与示例，不要冗长泛泛。  
  - 要通过触发、功能、性能三个维度测试，不断修订描述和流程。  
- **分发与生态**：Skills 是开放标准，可经 GitHub、Claude.ai、API、企业级部署等方式分发，特别适合与 MCP 集成形成“连接器 + Skills”的完整方案。[1]

***

## 什么是 Skill

- Skill = 一个约定结构的文件夹，核心必需文件是 `SKILL.md`（带 YAML frontmatter），可选包含 `scripts/`（代码）、`references/`（文档）、`assets/`（模板）。[1]
- Claude 使用「三层渐进披露」：  
  - 第 1 层：frontmatter 永远加载，用于判断何时使用该 skill。  
  - 第 2 层：`SKILL.md` 正文，仅在相关时加载。  
  - 第 3 层：引用的其他文件，在需要时再读，控制上下文大小同时保持专业深度。[1]

***

## Skill 与 MCP 的关系

- MCP 提供“专业厨房”（连接外部服务、数据和工具），而 Skills 提供“菜谱”（最佳实践流程和步骤）。[1]
- 没有 Skills 的 MCP：用户知道连上了服务，但不知道怎么设计高价值流程，容易产生大量“怎么做 X”的问答和不稳定结果。[1]
- 有 Skills 的 MCP：典型任务可自动触发预制工作流，统一错误处理与最佳实践，大幅降低学习成本与支持压力。[1]

***

## 规划与设计：从用例出发

- 建议先选 2–3 个具体用例，例如“项目冲刺规划”、“自动生成前端设计”、“客户入职流程”等，写清触发语、步骤和期望结果。[1]
- 文档将 Skill 用例分为三类：  
  - 类别 1：文档与资产创建（如前端设计、文档模版），强调风格指南、模板、质量检查。  
  - 类别 2：工作流自动化（多步过程、可迭代 refinement，如 skill-creator 自己）。  
  - 类别 3：MCP 增强（例如结合 Sentry 的错误监控做 PR 自动修复）。[1]

***

## 技术结构与 Frontmatter 规范

- 文件夹命名：kebab-case（如 `notion-project-setup`），不能有空格、下划线或大写；必须有且仅有 `SKILL.md` 作为主说明文件（不要在 skill 内放 README.md）。[1]
- 最小 frontmatter：  
  ```yaml
  ---
  name: your-skill-name
  description: 做什么 + 何时用 + 关键能力
  ---
  ```  
  `name` 要与文件夹名匹配，`description` 必须说明用途和触发条件，避免过于宽泛或只写技术实现。[1]
- 可选字段：`license`、`compatibility`、`metadata`（作者、版本、关联 MCP 等），frontmatter 禁止使用 `<` 和 `>`，skill 名不能包含 “claude” 或 “anthropic”。[1]

***

## 如何写出有效的 SKILL.md

- 推荐结构：顶部是 frontmatter，然后是简洁的标题、分步骤说明、示例和故障排除。指令要具体到“调用哪个脚本 / 哪个 MCP 工具、需要哪些参数、成功结果长什么样”。[1]
- 好的 `description` 需要同时包含“做什么”和“何时触发”，并列出用户可能说的短语；坏例子包括“太笼统”、“没有触发语”、“只讲内部模型概念”。[1]
- 正文中要包含：明确步骤、错误场景与解决方式、参考文件链接，并将细节文档放入 `references/` 来控制主文件长度。[1]

***

## 测试与迭代方法

- 测试可分三层：  
  - 在 Claude.ai 手工跑用例。  
  - 在 Claude Code 里编写脚本化测试。  
  - 通过 Skills API 做程序化评测。测试强度取决于 skill 的影响范围。[1]
- 推荐围绕三块做验证：  
  - 触发：对“应触发/不应触发”的输入进行测试，看 skill 是否自动加载。  
  - 功能：输出是否正确，工具调用是否成功，错误处理是否生效。  
  - 性能：与无 skill 的 baseline 对比会话轮数、API 失败数、token 消耗等。[1]
- 迭代信号：  
  - 触发不足：用户常手动启用或抱怨“不会自己用”，需要增加触发语和描述细节。  
  - 触发过度：频繁误触发，要增加负触发说明、收窄描述。  
  - 执行问题：结果不稳定或需要频繁人工纠正，则要简化并强化关键指令和错误处理。[1]

***

## 分发、部署与生态

- 当前获取 skill 的方式包括：下载 skill 文件夹并在 Claude.ai “Settings → Skills” 上传，或放入 Claude Code 的技能目录；企业管理员可以工作区级部署统一管理与自动更新。[1]
- Skills 是开放标准，目标是在不同 AI 平台间通用，但作者可在 `compatibility` 字段注明偏向某平台的特性；API 提供 `/v1/skills`、`container.skills` 等接口以便在应用和 agent 中程序化使用。[1]
- 推荐实践：用 GitHub 公共仓库存放 skill 文件夹，在 MCP 文档中链接 skill，提供安装与快速上手指南，并用 outcome 导向（而不是实现细节）描述其价值。[1]

***

## 常见设计模式与排错

- 常见模式包括：顺序工作流编排、多 MCP 协同、迭代式优化、上下文感知工具选择、领域专家逻辑（例如合规、审计流程）。[1]
- 常见问题与解决：  
  - 无法上传：通常是 `SKILL.md` 命名或 YAML frontmatter 语法错误。  
  - 不触发或乱触发：优化 `description` 的触发语和范围说明。  
  - MCP 失败：优先检查连接和认证，再检查工具名。  
  - 指令未被很好遵循：过长、埋得太深或语言模糊，需要压缩、前置关键点并给出明确 checklist。[1]

## 给你的行动指南（实操步骤）

按下面顺序，你可以在 1 次工作块内完成一个基础 Skill 的从 0 到 1：

1. **选用例与目标**  
   - 选 1–2 个你最常重复、最好能调用外部工具的工作流（例如“生成标准需求文档”、“按既定模板做竞品调研”）。  
   - 写下预期成功标准：如“减少 50% 对话轮数、0 手动补充字段、输出结构统一”。[1]

2. **设计文件夹结构**  
   - 创建 kebab-case 文件夹，如 `product-spec-generator`。  
   - 在其中建立 `SKILL.md`，后续视需要添加 `scripts/`（如数据校验脚本）、`references/`（团队规范）、`assets/`（模板）。[1]

3. **写好 frontmatter 与说明**  
   - 在 `SKILL.md` 顶部写最小 frontmatter：  
     ```yaml
     ---
     name: product-spec-generator
     description: 生成符合团队模板的产品需求文档。用户说“写 PRD”、“生成产品需求文档”或上传需求草稿时使用。
     ---
     ```  
   - 在正文中写：  
     - 分步骤流程（输入检查 → 信息补全问答 → 按模板生成 → 自检清单）。  
     - 关键注意事项与硬性校验条件。  
     - 1–2 个完整示例对话与期望结果。  
     - 常见错误与解决方式。[1]

4. **在 Claude.ai 中上传并做小规模测试**  
   - 将文件夹压缩为 zip，上传到 Claude.ai 的 Skills 设置中启用。  
   - 用“明显要触发 / 容易混淆 / 明显不相关”的多组输入测试：  
     - 记录 skill 是否自动触发、输出是否符合结构和质量预期。  
   - 若发现：  
     - 不触发：在 `description` 里补充更接近日常说法的触发语。  
     - 误触发：在 `description` 中显式加上“不用于 X 类问题”。[1]

5. **做对比试验与微调**  
   - 用同一个真实任务，对比“有 skill”和“无 skill”时的对话轮数、是否需要补救、token 用量。  
   - 根据问题类型分别调整：  
     - 多为理解偏差 → 精简并强化指令。  
     - 多为工具失败 → 检查脚本/MCP 调用与错误处理逻辑。[1]

6. **整理成团队/公开版本**  
   - 在 GitHub 创建仓库，将 skill 文件夹放入并写 repo 级 README（介绍价值、安装步骤、示例）。  
   - 若你有 MCP 服务，为其文档增加“搭配 skill 使用”的章节，并提供“下载 / 安装 / 首次尝试”的完整路径。[1]

照这套流程执行，你可以在 15–30 分钟内完成一个可用的初版 Skill，随后通过迭代测试不断让它成为你或团队的“标准化第二大脑模块”。[1]
