# 第一课：大模型基础 — 演讲记忆地图 v2

---

🗺️ **全篇地图**

**主题**：用一段会引发空指针的 TypeScript 代码作为贯穿主线，把大模型从"怎么读代码"到"怎么本地跑起来"完整拆开，建立工程师使用大模型的理性基线。

**章节线**：
开场代码引子 → ① 模型架构（怎么读） → ② 训练机制（能力哪来） → ③ 推理机制（钱花哪了） → ④ 模型选型（为什么不用最强） → ⑤ 参数配置（怎么调） → ⑥ 本地部署（自己跑一个） → 回到那段代码收束

**核心贯穿物**：开头那段 `renderProfile` 函数（`user` 可能为 `null`，第 4 行 `user.name` 会抛 `TypeError`）。整堂课每个小节都会回到这段代码。

## 📘 章节 1：模型架构 — 建立 Token 直觉

> **入口句**：先从第一个问题开始：模型不认识文字，它到底是怎么"读"代码的？跟着一条请求进模型走一遍，看看从你按下发送到第一个字出来，中间经过了哪些步骤。

📍 **路标 1.1：统一范式**
- 论据：原文金句——"LLM 用一个'预测下一个 token'的统一范式，覆盖了几乎所有语言任务。"
- 一句话：以前每个任务一个模型（情感、翻译、问答各一个），规模跨过临界点后"涌现"出新能力，于是一个模型 + 不同 prompt 就能干所有事。
- ⚠️ 提醒：举传统对比是 **Snyk/DeepCode**（语义级静态分析）；强调"涌现"是**没人在训练目标里写过'请学会 review 代码'**；工程含义是"把模型当可替换组件，不要绑死业务逻辑"。

📍 **路标 1.2：Tokenizer**
- 论据：`"user.name" → ["user", ".", "name"] → [882, 13, 2601]`；中文 vs 英文早期 1.5–2 倍 token 差，新词表（GPT-4o/DeepSeek/Qwen）已缩到 1.3 倍甚至 1:1。
- 一句话：模型不认识文字，第一步是切词成 token 再编号，token 直接关系到钱、上下文窗口、显存。
- ⚠️ 提醒：四个工程视角要点——**钱（按 token 计费）/ 容量（128K ≠ 128K 字符）/ 代码冗余（空格缩进、JSON、DOM）/ AI CR diff 预处理**。可推荐 OpenAI Tokenizer Playground 现场演示。

📍 **路标 1.3：Embedding**
- 论据：3 维玩具例子——`user.name [0.9, 0.1, 0.1]` + "安全防御"维度 → `user?.name [0.9, 0.1, 0.9]`；类比向量算术 `user.name - callback() + callback?.() ≈ user?.name`。
- 一句话：Token ID 只是编号没语义，Embedding 把它映射成向量，让"语义相近的词在向量空间也近"，这就是 RAG 能工作的根本原因。
- ⚠️ 提醒：真实维度是几百到几千；要点出 Cursor 整库向量化 vs Claude Code 的 **Agentic Search**。

📍 **路标 1.4：Attention（Q/K/V）**
- 论据：同一段代码里两个 `!` 含义相反——非空断言 vs 逻辑取反；`user.name` 的 Q 去对前面 `const user = res.ok ? ... : null` 的 K 打高分，吸收 V 里"可能为 null"的信息。
- 一句话：静态词向量分不清多义词，Attention 让当前位置去"查询"前文、按相关性加权汇总，于是 `user.name` 能回头发现 `user` 可能是 null。
- ⚠️ 提醒：两个工程要点——**O(n²) 复杂度**（所以长上下文难、有 GQA/MQA/稀疏注意力）和 **Lost in the Middle**（开头结尾被多读，中间被忽略，长文件 review 要按函数拆段）。论文：*Lost in the Middle* (arxiv 2307.03172)。

📍 **路标 1.5：Transformer**
- 论据：原文金句——"Attention 是开会讨论，FFN 是独立思考"；浅层抓语法、中层抓语义、深层抓推理。
- 一句话：Transformer 把 Embedding + Attention + FFN + 残差连接堆 N 层，浅层捕语法、深层做跨行推理，所以小模型能发现缺 `?.`，但只有大模型能真懂三元表达式的分支语义。
- ⚠️ 提醒：现代 LLM 全是 **Decoder-Only**（GPT/Claude/Gemini/DeepSeek）；用"闭卷考试 vs 即兴接话"两个比喻区分 Encoder-Decoder 和 Decoder-Only；Decoder-Only 自回归 → 串行生成 → 为下一部分讲"为什么 output 贵"埋伏笔。

↗️ **过渡 → 章节 2**
> "到这里，第一个问题有了答案……但架构只解释了'怎么处理'，还没回答'为什么它懂空指针风险'——这是训练决定的。"

## 📘 章节 2：训练机制 — 能力从何而来

> **入口句**：第一部分走完了模型从切词到推理的完整机制，但只解释了"怎么处理"——还没解释"为什么理解"。它为什么能够"理解"代码中的空指针报错？为什么可以遵循我的指令和一步步思考？**能力到底从何而来？** 答案藏在训练过程里。

📍 **路标 2.1：Pre-training**
- 论据：反例——给 Base 模型一段代码加"请 review 以上代码"，它会续写成"请 review 以上代码的测试覆盖率。请 review 以上代码的文档完整性……"以为你在列 checklist。
- 一句话：在海量无标注文本上做 next-token prediction，学会语言本身、世界知识，但**只是文本补全器**，不懂指令、不懂对话。
- ⚠️ 提醒：工程视角一句话——**不要直接用 Base 模型**，除非要做微调。

📍 **路标 2.2.1：CPT（持续预训练）**
- 论据：Qwen2.5-Coder vs 通用 Qwen2.5 在代码任务上的差距来自代码 CPT；CPT 喂海量 GitHub + Stack Overflow，学 if-else/try-catch 深层语义、跨几百行函数依赖、跨语言等价写法（`list.append` vs `vector.push_back`）。
- 一句话：Base 模型对专业领域只是"扫过"，CPT 用领域数据做"浸泡式"深化，先把知识打厚，再交给 SFT 雕刻行为。
- ⚠️ 提醒：CPT 是**模型厂商的事不是应用开发者的事**；**知识截止日期** = RAG 存在的根本原因。

📍 **路标 2.2.2：SFT（监督微调）**
- 论据：核心金句——"SFT 不改变模型知道什么，而是改变模型的行为模式"；SFT 教的是"怎么回答"不是"懂什么"。
- 一句话：从"续写"切换到"响应指令"，覆盖四个方向——**指令微调 / CoT 微调 / 工具调用微调 / 代码微调**——分别决定一类能力。
- ⚠️ 提醒：三个易踩的坑——① 专用 Coder 模型显著优于通用 ② **不要给推理模型加"请一步步思考"**（o1/R1 已内置，会干扰）③ SFT 修行为补不了知识。

📍 **路标 2.2.3：Alignment（对齐）**
- 论据：两条路径——**RLHF/DPO**（GPT-4、Claude 走偏好对齐）和 **RLVR**（DeepSeek-R1、o1 用编译器/测试用例当客观裁判，所以代码数学很强）；**对齐税**就是 review 老说"建议考虑是否……"而不直接说 bug。
- 一句话：SFT 后会回答但质量不齐，对齐通过"好回答 vs 差回答"的偏好让模型选更符合人类期望的那个；副作用是变保守。
- ⚠️ 提醒：**为什么代码任务最适合 RLVR**——代码是少数"答案对错极度明确"的领域；缓解对齐税的工程招——降 temperature、prompt 强制要求、强制输出 JSON 用枚举值（`severity: "BLOCKER" | "WARNING" | "NIT"`）。

📍 **路标 2.3：15度夹角（延伸思考）**
- 论据：原话——"0 度（做模型即将内化的事）→ 下一代模型淘汰你；90 度（和 AI 完全无关）→ 借不到 AI 杠杆；15 度（构建模型增强但不会替代的能力层）→ 模型越强你越值钱"。Respect To 秒哒产品经理 2026 年 2 月访谈。
- 一句话：理解了能力来源后想想哪些工程投入不会被模型吞掉——领域私有数据、外部系统集成、评估可观测性、判断"哪些问题值得用 AI 解决"。
- ⚠️ 提醒：这一节是**离题反思**，可短可省，但金句"15 度夹角"非常出彩，值得保留。最后用"Pre-train 打基础，CPT 补知识，SFT 教行为，Alignment 调偏好"一句话收束整章。

↗️ **过渡 → 章节 3**
> "前两部分回答了模型怎么'读'代码、能力边界在哪。第三个问题关于钱：output token 为什么比 input token 贵好几倍？追问为什么比首次提问快？如何优化 token 消耗和性能？这是推理机制决定的。"

## 📘 章节 3：推理机制 — 成本因何而生

> **入口句**：前两部分回答了模型怎么"读"代码、能力边界在哪。第三个问题关于钱……这是推理机制决定的。

📍 **路标 3.1：Prefill vs Decode**
- 论据：原文金句——"处理输入和生成输出是两个瓶颈完全不同的过程"；Prefill 瓶颈在 **GPU 算力**，关键指标 **TTFT**；Decode 瓶颈在**显存带宽**，关键指标 **TPS**。
- 一句话：输入是并行的（一锅炖完算所有 KV），输出是串行的（一个 token 一个 token 吐），所以 output 比 input 贵 3–5 倍。
- ⚠️ 提醒：四个日常体验都能在这里被解释——**长 prompt 等更久 / output 贵 3–5x / Thinking 模型贵 / 流式不加速生成只是体验**。

📍 **路标 3.2：KV Cache + Prompt Cache**
- 论据：无 KV Cache 是 O(n²)，有 KV Cache 是 O(n)，代价是显存膨胀几十 GB；Claude Code 的缓存命中只算原价 **~10%**；Kimi 用激进 KV Cache 管理实现"首次慢、后续快"。
- 一句话：单次推理内 KV Cache 避免重算，多次请求间 Prompt Cache 复用相同前缀，所以追问比首问快、成本骤降。
- ⚠️ 提醒：四个工程启示——① **稳定内容前置、变化内容后置** ② 首次最慢最贵 ③ 长上下文不免费 ④ AI CR 把团队规范放最前面、diff 放最后；这是为下一部分"模型选型/参数"作铺垫。

📍 **路标 3.3：加速降本技术全景**
- 论据：表格里 10 项技术——**量化（FP16→INT8→INT4，显存降 2–4x） / GQA-MQA / Prompt Cache（Agent 降本 90%+） / 推测解码（2–3x） / ASIC（TPU、Groq LPU） / Continuous Batching / Paging（vLLM） / MoE（DeepSeek、GPT-4） / 蒸馏 / DualPath（DeepSeek 吞吐近 2x）**。
- 一句话：作为 API 调用者你不用实现这些，但要懂——好挑推理服务商、好理解同模型不同平台价格差异、好做私有部署的精度/成本权衡。
- ⚠️ 提醒：金句——"INT4 量化的 70B 模型可能比 FP16 的 7B 模型效果好且成本相当"。最后用三问三答收束——output 贵是因为 Decode 串行；追问快是因为 Prompt Cache；优化要稳定内容前置 + 控制输出长度。

↗️ **过渡 → 章节 4**
> "前面三部分建立了理性基线——你知道了模型怎么处理代码、能力边界在哪、成本花在了哪里。现在回到第四个问题：为什么不直接用最强的模型？你的 AI CR 工具每天跑上百个 PR，全用 Opus 一个月账单可能比招一个人还贵——这就是选型要解决的问题。"

## 📘 章节 4：模型选型

> **入口句**：前面三部分建立了理性基线……现在回到第四个问题：**为什么不直接用最强的模型？**

📍 **路标 4.1：为什么要选型**
- 论据：5 类场景反例——高频简单任务用 Opus 千次成本失控 / 延迟敏感不达标 / 中文 token 多 1.3x+ / 私有数据不能出境 / 垂直专项任务小模型不输 Opus 但便宜数十倍。各家旗舰强项不同：Claude（长上下文+Agent 编码） / GPT（结构化+视觉） / o3-o4（数学推理） / Gemini（1M+上下文+视频） / DeepSeek（成本极低+中文）。
- 一句话：旗舰模型代表能力上限但不是工程默认，五类约束都比"质量最高"优先级更高。
- ⚠️ 提醒：金句——"AI CR 全用 Opus 一个月账单可能比招一个人还贵"；推荐参考站 OpenRouter 单模型详情页 + Chatbot Arena 任务排名。

📍 **路标 4.2：需求定义**
- 论据：8 个维度——输入模式 / 上下文长度 / 提示词价格 / 延迟 / 吞吐量 / 部署模式 / 任务场景 / 显存硬件；两个配套策略——**知识策略**（Prompt → Long Context → RAG → SFT 逐级升级）和**路由策略**（Anthropic 多模型路由指南、按任务复杂度分流可省 50%+）。
- 一句话：选型前先把需求写成可检查的 8 个问题，再叠加"知识策略"和"路由策略"两条配套决策。
- ⚠️ 提醒：AI CR 路由典型——**Haiku 扫风格 + Sonnet 啃复杂逻辑，成本降 60%+**。强调"能塞下 ≠ 都能用好"。

📍 **路标 4.3：怎么选（三步走）**
- 论据：**Step 1 聚合平台初筛**（OpenRouter 三个入口：rankings、models、单模型详情页 + 4 类定价：Input/Output/Cached Input/Thinking Token）；**Step 2 从模型名字辅助选型**（9 类名字线索 + 显存粗估公式：FP16=参数×2、INT8=×1、Q4=×0.5），举例 `Qwen2.5-Coder-7B-Instruct-Q4_K_M.gguf`；**Step 3 真实数据评测**（50–100 个真实 case + LLM-as-Judge + 10–20% 人工抽检 + 注意 position bias）。
- 一句话：快速选型 → 本地可行性 → 真实数据评测，不要先看公开 Benchmark 再决定评测谁，约束筛完已经够少。
- ⚠️ 提醒：金句——"50 条真实样本的评测结果比任何榜单都更能预测模型在你任务上的表现"；**Apple Silicon 统一内存**别按总容量满载，留 30%+；公开 Benchmark 只作背景参考（AIME/Codeforces 推理、SWE-bench/OSWorld Agent、GPQA Diamond 专家认知；MMLU/HumanEval 已饱和）。

↗️ **过渡 → 章节 5**
> "模型选好了，第五个问题：选定模型后如何调参？但在回答怎么调之前，先问一个更基础的问题——参数到底影响多大？答案可能出乎你意料：**大多数时候，影响不大**。"

## 📘 章节 5：参数配置

> **入口句**：模型选好了，第五个问题：选定模型后如何调参？

📍 **路标 5.1：影响层级 + temperature**
- 论据：金句结构——**80% prompt + 15% 上下文 + 4% 参数 + 1% 模型瓶颈**；temperature 表：0–0.2 代码/JSON、0.3–0.5 CR/技术问答、0.6–0.8 对话、0.9–1.2 头脑风暴。
- 一句话：先建立预期——参数是锦上添花不是救命稻草；先改 prompt → 补上下文 → 调参数 → 换模型；temperature 控随机度，CR 推荐 **0.1–0.3**。
- ⚠️ 提醒：三个坑——① `temperature=0` 不等于完全确定（要 `seed`） ② 低温不等于更正确，只是更坚定地选错答案 ③ 代码任务推荐 0.1–0.2 而非 0（贪心解码会陷入重复模式）；`top_p` 保持 1.0、`top_k` 不要碰。

📍 **路标 5.2：max_tokens + stop**
- 论据：场景表——分类 50–200 / JSON 预期×1.5 / 函数级代码 4096–8192 / Agent 工具调用 4096–8192 / 长文档 16384+；最常见 bug 是输出被截断（JSON 没闭合、代码缺 `}`）。
- 一句话：max_tokens 是硬上限不是目标，stop 是结构化解析的"断路器"，二者把 AI 从聊天模式切换到工具模式。
- ⚠️ 提醒：CR 视角金句——"防火墙 + 断路器 = 工程化鲁棒性"。

📍 **路标 5.3：logit_bias + prefilling**
- 论据：**Manus 的做法**——保持 prompt 不变控制输出（因为删工具会破坏 KV Cache 命中率，参见 3.2）；两条路：logit masking（需底层支持）和 **Response prefilling**（API 直接支持，把回复前缀预填为 `browser_`，模型只能续写浏览器工具）。
- 一句话：Agent 限制工具子集时不要从列表里删工具，用 prefilling 控制输出，保护 KV Cache 命中率。
- ⚠️ 提醒：日常用 stop 或 prefilling 就够了，logit_bias 维护成本高轻易别碰。

📍 **路标 5.4：Thinking 模式**
- 论据：金句——"思考 token 按 output 价格计费，动辄数千 token——用错场景成本翻 5–10 倍效果几乎不变"；Claude `budget_tokens` 复杂任务 10000–20000、中等 5000–8000；表里：复杂算法/跨文件 bug/数学推理✅，简单补全/格式转换/长文档摘要❌。
- 一句话：默认关闭，只在多步推理时开；如果问题来自上下文不足，开 Thinking 没用——它只是想得更久没新信息。
- ⚠️ 提醒：CR 实操——**默认关闭，对"核心模块/安全相关"路径自动开启**。

📍 **路标 5.5：速查表 + 收束**
- 论据：6 行配置速查表（代码生成 / CR / Agent 工具调用 / 数据提取 / 头脑风暴 / 复杂架构），每行给出模型、temperature、max_tokens、thinking 推荐；金句——"**Max Tokens 必须覆盖 Thinking Budget**"；CR 起点配置 `Sonnet, T=0.2, max_tokens=4096, thinking 关`。
- 一句话：从模板出发 → 跑 5–10 个真实 case → 一次只改一个参数 → 对比效果；这些是起点不是终点。
- ⚠️ 提醒：四参数分工总结句——temperature 控随机、max_tokens+stop 防截断兼控成本、thinking 默认关、logit_bias/prefilling 用于 Agent 工具子集且不破坏 KV Cache。

↗️ **过渡 → 章节 6**

## 📘 章节 6：本地部署

> **入口句**：最后一个问题：前面讲了这么多，能不能不花钱、不申请 API key，自己跑一个模型试试？

📍 **路标 6.1：硬件 + 模型选型**
- 论据：**模型大小 ≤ 总内存 70–80%**；档位表——8GB→3B / 16GB→7B / 24GB→14–33B / 32GB+→32–34B / 64GB+→70B+；首选家族 Qwen2.5-Coder。
- 一句话：先看芯片和内存，再按"速度/质量/硬件三者平衡"挑模型；只想跑通 3B、日常 7B、追极致 32B、最好效果直接用 API。
- ⚠️ 提醒：命令——`sysctl -n machdep.cpu.brand_string` 和 `sysctl -n hw.memsize`；强调本地部署的真正意义是**免费 + 隐私 + 合规**。

📍 **路标 6.2：Ollama 跑通**
- 论据：3 步——`brew install ollama` → `ollama pull qwen2.5-coder:7b` → `ollama run qwen2.5-coder:7b`；验证 API：`curl http://localhost:11434/api/chat ...`。
- 一句话：装、拉、跑、验证四步走，把开头那段 `renderProfile` 喂给本地模型试试看。
- ⚠️ 提醒：退出命令 `Ctrl+D` 或 `/bye`；机器小就换 `qwen2.5-coder:3b`。

📍 **路标 6.3：OpenCode 接入**
- 论据：4 步——`brew install opencode` → 项目目录建 `opencode.json`（`provider: ollama, model: qwen2.5-coder:7b`） → `cd ~/your-project && opencode` → 发第一条编码指令；建议**先本地跑通再切 API 对比**。
- 一句话：OpenCode 是终端 AI 编程助手，本地能跑通就说明环境搭好了。
- ⚠️ 提醒：切云端只需 `export ANTHROPIC_API_KEY=...` 再改 provider。

📍 **路标 6.4：对比实验**
- 论据：三档配置同一任务——`qwen2.5-coder:3b` vs `qwen2.5-coder:7b` vs 你常用的云端 API；对比响应时间、代码质量、是否一次通过。
- 一句话：不是分胜负，是建立"什么叫够用"的体感；现在你不只会调 API，还多了一个不走外网的选项。
- ⚠️ 提醒：这一段是落地体验，**最好在演讲现场真的把 ollama 跑起来给观众看**。
