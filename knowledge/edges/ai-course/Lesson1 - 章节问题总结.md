# 第一课：大模型基础 — 各章节核心问题总结

> 全课主线：理解大模型"能力从何而来、成本因何而生"，为工程决策提供理性基线。

---

## 第一部分：从语言任务到大模型——能力从何而来

### 1.1 统一范式：预测下一个 Token
- **LLM 和传统 AI 模型的核心区别是什么？** 从"每个任务一个专用模型"到"一个模型通过预测下一个 token 覆盖所有语言任务"的范式转移。
- **什么是涌现（Emergence）？** 模型规模跨过临界点后，突然冒出从未被显式训练过的能力（推理、类比、零样本完成新任务）。
- **这对工程意味着什么？** 不再需要为每个任务搭专用模型；好的架构应把模型当作可替换组件。

### 1.2 Tokenizer：文本切分与基础单元
- **模型怎么"读"文本？** 先用 Tokenizer 把文本切成子词单元（token），再映射为数字 ID。
- **Token 跟钱有什么关系？** API 按 token 计费；中文通常比英文消耗更多 token；代码缩进、空行、长 JSON 都是隐形消耗。
- **上下文窗口的实际容量是多少？** 128K 上下文 ≠ 128K 字符，实际取决于分词效率。

### 1.3 Embedding：词的向量化与语义表示
- **token ID 怎么变成模型能理解的"含义"？** Embedding 把每个 token ID 映射为高维向量，语义相近的词在向量空间中距离也近。
- **这跟 RAG 有什么关系？** RAG 的核心逻辑——语义搜索——就是靠 Embedding 的"语义相近 → 向量距离近"来实现的。

### 1.4 Attention：捕捉上下文间的关联
- **同一个符号在不同语境含义不同，模型怎么区分？** Attention 机制让每个 token 的表示随上下文动态变化，解决多义词问题。
- **Q-K-V 机制做了什么？** 让当前位置去"查询"前文，按相关性打分并加权汇总信息（Q 问"我在找什么"，K 答"我是什么"，V 传递实际内容）。
- **为什么长文件中间的问题容易被漏掉？** Attention 计算量 O(n²)，且存在 Lost in the Middle 现象——模型对开头和结尾关注更多，中间容易被忽略。

### 1.5 Transformer：大模型的网络架构
- **Embedding、Attention 等组件怎么组合成完整模型？** Transformer 把它们组合起来，加上残差连接（解决深层训练困难）和 FFN（在每个位置做独立深层加工），堆叠 N 层实现从语法到推理的逐层深入。
- **为什么现代 LLM 都用 Decoder-Only 架构？** "问答即续写"的统一范式让模型更容易学会逻辑和常识，且推理时可利用 KV Cache 提高工程效率。
- **Decoder-Only 有什么代价？** 逐 token 生成、无法跳步，导致生成速度受限，output token 比 input token 贵。

## 第二部分：训练机制——能力从何而来

### 2.1 预训练（Pre-training）
- **模型的基础能力从哪来？** 在海量无标注文本上做 next-token prediction，学会语法、语义、常识和世界知识。
- **为什么预训练后的模型不能直接用？** 它只是文本补全器，不理解"指令"，也没有对话意识。

### 2.2.1 持续预训练（CPT）
- **通用模型在专业领域为什么不够深？** 预训练数据中专业领域占比有限。CPT 用大量领域数据做深化训练，打厚知识基础。
- **为什么同规模下 Qwen2.5-Coder 比通用 Qwen2.5 代码能力强？** 前者经过了代码领域的 CPT。
- **模型为什么会"幻觉"你的内部 API？** 知识截止在预训练结束那一刻，这是 RAG 存在的根本原因。

### 2.2.2 SFT（监督微调）
- **模型怎么从"续写"变成"听指令回答"？** SFT 改变行为模式，不改变知识储备——教的是"怎么回答"，不是"懂什么"。
- **SFT 具体教了哪些能力？** 指令跟随、链式思维推理、工具调用、代码生成。
- **为什么不要给推理模型加"请一步一步思考"？** 它们已内置推理链，手动加反而干扰。

### 2.2.3 Alignment（对齐）
- **模型怎么从"能回答"到"回答得好"？** 通过偏好对齐（RLHF/DPO）或客观验证（RLVR），在多个可行答案里选更符合人类期望的。
- **为什么 DeepSeek-R1 在代码任务上特别强？** 代码是"答案对错极度明确"的领域，天然适合 RLVR 强化学习。
- **什么是 Alignment Tax？** 过度对齐让模型变得保守（"建议考虑……"而非直接指出 bug），这是训练机制带来的，不是 prompt 能完全解决的。

### 2.3 工程视角：哪些投入不会被模型吞掉
- **怎样的工程投入不会被下一代模型淘汰？** 与模型方向保持"15度夹角"——领域私有数据管理、外部系统集成、评估体系、判断"哪些问题值得用 AI 解决"的能力。

## 第三部分：推理机制——成本因何而生

### 3.1 Prefill 与 Decode
- **为什么发出请求后要等一下才出第一个字？** Prefill 阶段并行处理全部输入 token，输入越长首字延迟（TTFT）越高。
- **为什么 Output token 比 Input token 贵 3-5 倍？** Decode 阶段逐 token 串行生成，每个 token 都要过一遍模型，GPU 利用率低。
- **流式输出能加速生成吗？** 不能，生成速度由 Decode 决定，流式只是让你提前看到已生成的部分。

### 3.2 KV Cache 与 Prompt Cache
- **Decode 阶段怎么避免重复计算？** KV Cache 缓存已算过的 Key/Value，将每步计算量从 O(n²) 降到 O(n)，代价是显存随序列增长膨胀。
- **为什么同一个 PR 追问第二个问题更快？** Prompt Cache 跨请求复用共同前缀的 KV Cache，缓存命中的 token 只有原价 ~10%。
- **怎么设计 prompt 才能最大化缓存命中？** 稳定内容（system prompt、规则）放前面，变化内容（用户输入）放后面。

### 3.3 加速与降本技术全景
- **有哪些技术在降低推理成本和延迟？** 量化、KV Cache 优化（GQA/MQA）、Prompt Cache、推测解码、专用芯片、连续批处理、Paging、MoE、蒸馏。
- **API 调用者需要关心这些吗？** 不需要实现，但理解它们有助于评估服务商技术栈、理解价格差异、做私有化部署决策。

## 第四部分：模型选型

### 4.1 为什么不直接用最强模型
- **旗舰模型是工程默认选项吗？** 不是。高频简单任务成本失控、延迟敏感场景响应慢、中文效率低、数据合规要求、垂直专项任务有更划算的选择。
- **选型第一步是什么？** 排除超出约束的选项，而不是从最强开始往下找。

### 4.2 判断维度：选型看什么
- **选模型要考虑哪些维度？** 任务类型、部署模式、硬件显存、成本上限、延迟要求、输出格式。
- **知识不够怎么补？** 先 Prompt → 不够加 RAG → 行为仍不稳定才 SFT。
- **同一系统必须用同一模型吗？** 不必。路由策略——规划用强模型，批量任务用快模型，80% token 消耗控制在低成本层。

### 4.3 实践三步：初筛 → OpenRouter 比较 → Benchmark
- **怎么从模型名字做初筛？** 读参数规模、MoE 标记、指令对齐、任务域变体、量化精度等信息，粗估显存占用。
- **怎么比较候选模型？** 用 OpenRouter 统一 API 平台做功能过滤、实时比价、经济性校验。
- **Benchmark 怎么用才理性？** 当"入围赛"排除明显差的，优先看 Chatbot Arena / LiveBench，只关心 pass@1，分数差 1-2% 不值得换模型。

## 第五部分：参数配置

### 5.1 采样参数：temperature
- **temperature 控制什么？** 输出的随机程度。越低越确定性，越高越多样发散。
- **代码任务推荐多少？** 0.1–0.3。temperature=0 不等于完全确定，也不等于更正确。

### 5.2 输出控制：max_tokens 与 stop
- **max_tokens 是什么？** 输出的硬性上限，不是目标。输出被截断（JSON 没闭合）通常就是它不够。
- **stop 参数有什么用？** 指定终止字符串，防止模型在结构化输出后继续"解释"。

### 5.3 logit_bias：限制输出范围
- **怎么精确控制模型能输出哪些内容？** logit_bias 直接调整特定 token 的生成概率；Response prefilling 预填回复前缀限制续写范围——两者都能在不改变 prompt（不破坏缓存）的前提下控制输出。

### 5.4 Thinking 模式：何时开启推理增强
- **什么时候该开 Thinking？** 复杂算法设计、跨文件 Bug 追踪、数学逻辑推理。简单补全、格式转换、长文档摘要不需要。
- **开了 Thinking 就一定更好吗？** 不一定。如果问题来自"上下文不足"，开 Thinking 无济于事——改善上下文比让模型"想得更久"更有效。

### 5.5 常见任务配置速查
- **调参的正确方法是什么？** 80% 的输出质量问题来自 prompt。先改 prompt，再调参数，最后才考虑换模型。从模板出发，跑真实 case，一次只改一个参数对比效果。

## 第六部分：模型部署

### 6.1–6.4 本地部署实操
- **怎么在自己 Mac 上跑模型？** 用 Ollama 拉取模型 → 验证对话和 API → 用 OpenCode 连接本地模型做编码辅助。
- **怎么选本地模型大小？** 模型大小不超过总内存的 70-80%。核心原则是速度、质量、硬件约束三者平衡，不是"越大越好"。

### 6.5 对比实验
- **本地小模型 vs 本地中模型 vs 云端模型差多少？** 实验目的不是分胜负，而是建立"什么叫够用"的体感。
