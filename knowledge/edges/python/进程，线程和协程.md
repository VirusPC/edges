一、30 秒开场框架
进程是 OS 分配资源的单位，线程是 CPU 调度的单位，协程是用户态调度的轻量并发。三者解决不同问题：进程为隔离 + 并行，线程为共享内存的并发，协程为单线程内的高并发 I/O。Python 因为 GIL 的存在，纯 CPU 密集场景多线程拿不到真并行,所以才有 multiprocessing 和 asyncio 两条互补路线。
讲完这段直接给出对比维度，主动权就在你这边。
二、核心对比表（背下来）



| 维度  | 进程                | 线程           | 协程         |
| --- | ----------------- | ------------ | ---------- |
| 资源  | 独立地址空间            | 共享进程内存       | 共享线程栈      |
| 切换  | μs，syscall        | μs,内核调度      | ns,函数调用级   |
| 调度  | OS 抢占             | OS 抢占        | 协作式（await） |
| 并行  | ✅                 | I/O 和 C 扩展可以 | ❌          |
| 通信  | IPC + 序列化         | 共享变量 + 锁     | 共享变量,几乎不用锁 |
| 隔离  | 崩溃独立              | 一损俱损         | 一损俱损       |
| 量级  | 几十~几百             | 几千           | 十万+        |
| 模块  | `multiprocessing` | `threading`  | `asyncio`  |

三、必考三块
1. GIL（一定问）
	•	是什么：CPython 解释器的一把全局互斥锁,任意时刻只有一个线程执行 Python 字节码。不是语言规范,是 CPython 实现细节(Jython 没有,PyPy 有)。
	•	为什么:简化引用计数的内存管理、保证 C 扩展线程安全、单线程性能更好。
	•	何时释放:I/O 系统调用、time.sleep、大多数 C 扩展(numpy/lxml/加解密/压缩)、Python 3.2+ 每 ~5ms 强制切换。
	•	影响:CPU 密集多线程无效甚至变慢(锁竞争);I/O 密集多线程有效;C 扩展密集可真并行。
	•	绕过方式:多进程、C 扩展释放 GIL、Cython nogil、Python 3.13+ free-threaded build (PEP 703) 可选关闭 GIL。
2. 选型决策(最容易考”如果让你做 X 怎么选”)
	•	纯 Python CPU 密集 → 进程
	•	网络/磁盘 I/O 为主,生态全 async → 协程
	•	I/O 为主但要用同步库 → 线程
	•	跑不信任代码、要崩溃隔离 → 进程 + 容器
	•	数值计算 → C 扩展(numpy)+ 线程
记住一句:协程不能加速 CPU,只是更便宜的并发抽象。
3. 协程实现原理(senior 岗加分)
	•	演进:生成器 yield(雏形)→ 3.4 asyncio + @coroutine → 3.5 原生 async/await。
	•	本质:事件循环 + 状态机。await 把当前协程挂起,注册回调,让出控制权;I/O 就绪后由 loop 唤醒。
	•	底层 I/O:epoll(Linux)/kqueue(macOS)/IOCP(Windows),非阻塞 + 多路复用。
	•	为什么快:用户态切换(ns 级)、无 GIL 竞争、无锁开销、无独立栈。
四、高频追问



| 问题                      | 关键点                                                                     |
| ----------------------- | ----------------------------------------------------------------------- |
| 进程间通信方式                 | Pipe、Queue、shared_memory、Socket、Manager、文件                              |
| 线程同步原语                  | Lock / RLock / Semaphore / Condition / Event / Barrier                  |
| 死锁四条件                   | 互斥、请求和保持、不可剥夺、循环等待                                                      |
| fork vs spawn           | fork 快但继承锁/线程状态有坑;spawn 慢但干净;3.14 起 fork 不再是 Linux 默认                   |
| 进程池 vs 线程池              | `ProcessPoolExecutor` / `ThreadPoolExecutor`,统一 `concurrent.futures` 接口 |
| `run_in_executor`       | 在 async 里跑阻塞代码的标准做法,不阻塞 event loop                                      |
| `gather` vs `TaskGroup` | TaskGroup(3.11+)是结构化并发,异常用 `ExceptionGroup`,失败自动取消兄弟任务                  |
| asyncio 比线程快在哪          | 用户态切换、无 GIL 竞争、无锁、内存小                                                   |
| 协程一定比线程快吗               | 不一定,**高并发 I/O 才快**;低并发或要兼容同步库,线程更合适                                     |
| 线程能 kill 吗              | **不能**,Python 没有可靠的线程取消机制,只能协作式 flag                                    |
| daemon 线程               | 主线程退出时自动结束,适合后台任务                                                       |

五、加分项(主动提)
	•	Python 3.13 free-threaded(PEP 703):可选关闭 GIL,单线程性能损失 ~10%,生态迁移中。这是近年最大变化,主动提显示你跟进社区。
	•	Sub-interpreters (PEP 684 / 734):3.12+ 每个解释器独立 GIL,3.13 提供 concurrent.interpreters API,介于线程和进程之间的新选项。
	•	结构化并发:TaskGroup、asyncio.timeout()(3.11+),对比 trio 的 nursery 模型。
	•	uvloop:基于 libuv 的事件循环替代,比内置快 2-4x。
	•	区分”并发”与”并行”:concurrency 是结构(同时处理多件事),parallelism 是执行(同时做多件事)。协程是并发不是并行。
	•	GIL 的内存语义:CPython 的 dict、list 操作在 GIL 保护下”看起来”原子,但跨操作仍要加锁。free-threaded 下这些假设全部失效。
六、容易翻车的陷阱题
	•	“Python 多线程是真线程吗?” → 是 OS 原生线程,不是绿色线程,只是受 GIL 限制。
	•	“asyncio 是单线程还是多线程?” → 单线程(默认)。
	•	“GIL 是 Python 的问题?” → 是 CPython 的问题。
	•	“为什么 multiprocessing.Queue 比 queue.Queue 慢?” → 跨进程要序列化 + IPC。
	•	“为什么 fork 多进程后子进程卡住?” → 父进程持有的锁被复制到子进程,但持锁线程没了 → 死锁。这是 macOS 默认改 spawn 的原因。
