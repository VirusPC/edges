# ssh 下的 keychain问题

好，这次我们不讲命令，讲“系统经验”。

一句话总结：

这是一次“默认假设冲突”的事故。不是 Docker 坏了，是环境假设变了。

⸻

1️⃣ 本质经验：GUI 世界 ≠ 自动化世界

macOS 的安全模型默认假设：

访问凭证时，人类在场，可以点弹窗。

而你当前 session（终端、tmux、SSH）属于：

非交互环境。

当系统无法弹窗，就直接失败。

这不是 bug，是设计选择。

经验提炼：

在 macOS 上，只要涉及 Keychain、GUI、权限提升，都要警惕 session 类型。

⸻

2️⃣ 技术经验：Docker 并不“只做你看到的事”

你只是 pull 一个 public 镜像。

但 Docker 实际流程是：  
    •	读取 config  
    •	尝试读取凭证  
    •	调用 credential helper  
    •	调用系统 keychain

很多工程问题来自：

“隐式调用链”带来的副作用。

调试时要习惯问：  
    •	它背后调用了谁？  
    •	它是否依赖系统组件？  
    •	它是否假设有 GUI？

⸻

3️⃣ 安全模型经验：Keychain 是独立加密系统

Keychain 不是文件。

它是：  
    •	加密数据库  
    •	独立进程管理  
    •	有锁定状态

而且：

锁定状态是“会话级”的。

这意味着：

同一台机器，不同 session 访问权限可能不同。

这个认知在做自动化部署时非常重要。

⸻

4️⃣ 工程经验：本地开发机 ≠ 自动化执行环境

macOS + Docker Desktop 很适合：  
    •	人类本地开发  
    •	图形界面操作  
    •	偶发命令

但不适合：  
    •	长期后台任务  
    •	AI agent orchestration  
    •	自动化 pipeline

如果你未来做大量自动化构建：

Linux VM 或远程 Linux 机器，稳定性更高。

不是情怀问题，是系统哲学不同。

⸻

5️⃣ 解决策略经验：优先修机制，不要打补丁

这次你用的是：

security unlock-keychain

这是修机制。

而删除 credsStore 是绕过机制。

长期复利角度：

优先修底层模型，避免未来反复踩坑。

⸻

6️⃣ 调试思维模型总结

以后遇到类似问题，可以走这条路径：  
    1.	是否权限问题？  
    2.	是否 session 上下文问题？  
    3.	是否系统服务依赖？  
    4.	是否 GUI / 非 GUI 差异？  
    5.	是否凭证管理系统？

这五个问题能解决 70% macOS 开发奇怪问题。

⸻

7️⃣ 更宏观一点

现代操作系统的安全设计趋势是：

把“人类可见交互”作为信任锚点。

但自动化时代正在弱化这个假设。

你遇到的是这种设计冲突的一个缩影。

技术成长的一个标志就是：

开始意识到工具背后的假设，而不是只会执行命令。

你现在已经跨过“会用工具”的阶段，开始进入“理解系统”的阶段。

这比 pull 成功本身更有价值。
