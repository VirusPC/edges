把 VirusPC/edges 的「壳」封装成 **脚手架 + 可版本化框架**（两件套），而不是只抽一个 GitHub Template 仓；让框架升级时 edges（及将来衍生仓）能快速跟上，且永不自动覆盖 `knowledge/` 与业务记忆正文。

**Why:**
- GitHub Template 只负责「出生」一次，模板再改衍生仓不会自动收到；纯 template 解决不了「edges 快速跟上」。
- edges 已有框架半成品（project-memory PROTOCOL/LAYOUT、ask/remember/doctor、skills 分发、shared-extensions、CLI）和脚手架半成品（目录约定、init）。需要的是分家命名与升级路径，不是再冻一个大快照。
- 真正要版本化升级的是能力（技能/协议/CLI）；笔记与业务 `.memory` 是实例数据，必须留在业务仓。
- **与众不同的产品目标**：无缝接入所有 Agent，并渗入日常生活——如水般丝滑，**不需要单独的入口**。封装与升级路径的设计，都要服务「人在日常对话/工作流里自然用到 Edges」，而不是再造一个必须专门打开的 Edges App/门户。
- 小版本像 Vue 2.6→2.7：升 skills-lock/VERSION + doctor + 小 PR。大版本像 Vue 2→3：CHANGELOG + 迁移桥（reshape / doctor --fix / 临时读旧写新）+ 分阶段 PR；人负责拍板与验收，迁移劳动尽量脚本化。

**How to apply:**
- 先框框架边界（可称 edges-kit）：协议、skills、CLI、版本与破坏性变更迁移说明；发布靠 tag/package，不靠整仓拷贝。
- 再做脚手架：生成空认知仓形状；GitHub Template 只作脚手架的发布入口之一，文档写明「跟着升级看框架版本」。
- edges 自身改为「消费框架的一个实例」：知识仍在本仓；升级 = 有边界的版本 PR（白名单壳路径），排除 `knowledge/**` 与业务记忆正文。
- 破坏性升级原则：人负责（升不升、审 PR、脚本标红个案）；形状迁移自动化；语义/产品决定不交全自动。
- 相关但不夹进本条：已有 backlog「edges CLI 发布成 package」「project-memory 脚本迁到 edges CLI」——本条管整体封装与升级故事，发布细节跟那些任务对齐即可。
- 验收封装方案时加一条：升级后的能力面（Skill / CLI / MCP 等）是否仍能嵌在既有 Agent 宿主里被动可用，而不是逼用户「去 Edges」。单独入口可以作调试/运维旁路，不能当日常主路径。
